# wiki-maintain

这个仓库分两层：**raw 层**（`公司/`、`专栏/`、`项目/` —— 原始面经和笔记）和 **wiki 派生层**（`wiki/` 下你维护的压缩层：公司画像、技术主题、追问题库、索引、dashboard）。维护知识 = 往 raw 层加原料，然后让派生层跟上，且双链、frontmatter、索引始终自洽。这个 skill 是「加内容」的唯一标准流程。

**动手前先读一遍** [`wiki/使用指南.md`](wiki/使用指南.md) 对应章节和 [`CLAUDE.md`](CLAUDE.md)——它们是这个库的 SOP，本 skill 是它的可执行版。

## 第一步：判断这是哪类维护

| 用户给的东西 | 操作 | 写到哪 | 起手模板 |
|---|---|---|---|
| 一段面经原文（录音转录 / 牛客·朋友圈 copy / 手敲） | **A. 加面经** | `公司/<公司>/<BU>/<标题>.md` | [`wiki/模板/录音转面经.md`](wiki/模板/录音转面经.md) |
| 一个跨 ≥3 家公司的考点，想建专题 | **B. 加技术主题** | `wiki/技术主题/<主题>.md` | [`wiki/模板/新主题文章.md`](wiki/模板/新主题文章.md) |
| 仓库第一次出现某公司 | **C. 建公司画像** | `wiki/公司/<公司>.md` | [`wiki/模板/新公司画像.md`](wiki/模板/新公司画像.md) |
| 简历某项目被多家公司追问 | **D. 建项目追问库** | `wiki/追问/<项目>.md` | [`wiki/模板/新追问QA.md`](wiki/模板/新追问QA.md) |
| 只是让派生层跟上 raw 的变化 | **E. 更新派生层** | 现有 `wiki/` 文件 | 无（直接编辑） |

一次请求可能连着做好几步：加一篇新公司的面经 = A +（新公司则 C）+ E（更新画像那一行）。按需组合。

## 铁律（每一步都适用，先记住再动手）

1. **照活文件写，别盲信模板。** 模板和 CLAUDE.md 里的字段清单会漂移（真实例子：`wiki/公司/字节.md` 的 frontmatter 只有 `title/type/updated`，并没有模板 README 里写的 `tier/passed/failed`）。所以**写任何文件前，先打开一个最近的同类活文件**（比如要加面经就打开 `公司/快手/` 下某篇，要建画像就打开 `wiki/公司/字节.md`），照它此刻的真实 frontmatter 和排版来写。模板给结构，活文件给口径，冲突时**以活文件为准**。
2. **双链写法**（错了 lint 会红）：
   - 指 raw 面经 / 专栏 → 全路径：`[[公司/字节/财经/字节财经一面]]`、`[[专栏/后端/Java并发编程]]`
   - 指 wiki 主题 / 追问 → 裸名：`[[Java并发集合]]`、`[[追问/西门子RAG]]`
   - 指索引 / 画像 → `[[索引/主题]]`、`[[公司/字节]]`
   - 简历 PDF 不进 wikilink
3. **简历是 ground truth。** 项目细节（西门子 RAG / 用友 / 黑马点评 / RPC 等）和 [`wiki/我的简历/`](wiki/我的简历/) 冲突时，以简历为准，别自己编数据指标。
4. **别碰算法。** 算法在另一个仓库，本库不补算法内容；遇到算法真题只在面经正文如实记录，不往 wiki 建算法页。
5. **收尾永远跑 lint。** 改完调用 `/wiki-lint`（或 `python3 wiki/scripts/lint_wiki.py`），必须 0 broken link 才算完。这是本 skill 的验收线。
6. **由浅入深，不许只写层③。** 用户是后端工程师，**不要用生活比喻，直接讲技术**；但**每个术语先判断他学没学过，默认没学过**。术语分三档：**A 已掌握**（`wiki/技术主题/` 有专题 或 他在面经里答对过）直接用；**B 见过不牢** 用+跟一句定义；**C 没学过**（仓库搜不到，`grep -rl "术语" wiki/ 公司/` 验证）必须先立定义再用。文件里的技术解释按四层排：**①技术定义（准确、不比喻，只用 A 档词汇写）→ ②不用它会怎样（具体坏结果）→ ③机制细节 → ④面试 30 秒口语稿 + 预备追问**。禁用「众所周知/显然/其实很简单」。**完整协议见 [`CLAUDE.md`](CLAUDE.md) 「讲技术问题时的分层协议」——最高优先级，覆盖本 skill 的任何排版建议。**
7. **画图一律用 mermaid，禁止手画 ASCII 框线图。** 流程 / 链路 / 分支判断用 ```` ```mermaid ```` + `flowchart TD`（或 `LR`），状态机用 `stateDiagram-v2`，时序用 `sequenceDiagram`。Obsidian 原生渲染，ASCII 图换字体就错位、也改不动。例外只有 mermaid 画不了的内存布局 / 字节排列。
   - **节点标签写两行：第一行「做什么」（大白话），第二行「具体是哪个文件 / 函数 / 参数」**，用 `<br/>` 隔开。例：`["平时只记流水账，不做判断<br/>~/.codex/sessions/*.jsonl"]`。**抽象和具体并置在同一个节点里，读者不用在图和表之间来回对照**——不要为此在图下面单独摆一张「大白话 → 磁盘上是」的映射表，那是多余的一次跳转。
   - 路径里的 `<占位符>` 在 mermaid 里会被当成 HTML 标签，**用 `*` 代替**（`~/.claude/projects/*/memory/*.md`）。
   - **但别把参数清单塞进节点**——三行以上说不完的属性（完整阈值表、全部配置项）还是该放图后面的正文或表。
8. **Agent / LLM 类内容：先查最新源再落笔，且必须在文件里留下出处。** 这块日新月异，**你的训练数据和这个仓库的旧笔记都会过期**——凡是涉及 agent 产品内部机制（Claude Code / Codex / OpenClaw / Cursor…）、框架实现、某个 API 的行为，**不许凭记忆直接写进文件**。
   - **必查（至少覆盖前两项）**：① **GitHub 仓库**——源码 / issue / release notes / CHANGELOG，看最近 commit 和 tag ② **WebSearch 最近几个月**的逆向分析和博客（社区逆向常比官方文档细）③ 官方文档 / 更新日志 ④ **`专栏/` 下的旧笔记只当线索，不当结论**，必须用新源交叉验证
   - **落到文件里的写法**：Agent 相关的事实性断言后面挂一句 `<!-- 来源: 官方文档 | 源码 | 社区逆向 | 推断 ・ 查证于 YYYY-MM-DD -->`，或在段末用 `> 📌 出处：… ・ 2026-07 查证` 标注。**理由：这个文件几个月后还会被读，那时分不清哪行是查的、哪行是猜的。**
   - **推断就明说是推断；查不到就写「未查到」，不许用「逻辑上应该是」填空。** 已有翻车实例：把 ContextCollapse 当成失败模式写，就是凭常识填空填错的。
   - **完整协议见 [`CLAUDE.md`](CLAUDE.md)「Agent 类问题必须先查最新源」——最高优先级。**
9. **逐题复盘时先只列「当时的回答」，不要抢先给改进版。** 三步：①列原话（忠实原文，只标事实不加评价，最多标一句「这里卡壳/这里说了没细究」）②**等用户先判断**该怎么改 ③再一起打磨出定稿话术。**一次只上一题。**
   - **理由**：用户的核心短板是「知识有但取不出来」（阿里云→微信支付同题两次答崩；快手分水岭题的答案他上一题刚说过）。**先摆改进版，他就只会点头，那份答案永远是你的不是他的。**
   - 用户说「按我原本的回答列出来」= 明确要这个模式，**别夹带改进版**。
   - **写文件时不受此限**——面经文件本来就是「当时的回答 + 改进后的回答」双栏对照，两栏都要写全。**这条只约束对话，不约束文件。**
   - 完整协议见 [`CLAUDE.md`](CLAUDE.md)「复盘讨论的形式」。
9. **系统/产品类主题用五段式，架构必须先行。** 铁律 6 那个四层是讲**单个概念**用的；写**一个系统或多个系统**（Agent 记忆、上下文压缩、某框架实现）时按下面五段排，**顺序不许调**：
   1. **架构先行**——每个系统**各讲各的、先不比较**。每段：一句大白话 → mermaid 流程 → 3-5 条要点。**具体文件名/函数名写进 mermaid 节点的第二行**（见铁律 7），跟大白话并置，**不要另摆映射表**。
   2. **具体细节**——文件格式、字段、参数、阈值、真实路径
   3. **为什么这样设计**——权衡与约束推导（「不是谁更先进，是约束不同」）
   4. **横向对比**——**到这里才允许摆三家对照表**
   5. **常见问题**——怎么管理 / 合并 / 遗忘 / 污染 / 已知失败模式
   - **判断标准**：读者在看到某个文件名或内部术语时，**是否已经知道这个系统是怎么运转的**。答案是"否"就说明第 1 段没写够。**翻车实例**：`Agent记忆三家实现对比.md` 初版上来就是三家 × 一堆文件名的对比表，被用户指出「根本没有由浅入深」。
   - **不要用行数当验收标准。** 判断一篇写得好不好看的是「读者能不能顺着读下来」，不是多少行。**该砍的是重复和绕弯的表达，不是内容。** 如果发现在为了凑短而删有用的东西，说明标准用错了。

## A. 加面经（最常用）

1. 找用户给的三要素：来源（我面试 / 网上转载）、公司、BU、轮次、日期、结果。缺的就问，或按模板规则填「未知 / 约 YYYY-MM」。
2. 读 [`wiki/模板/录音转面经.md`](wiki/模板/录音转面经.md)，**按它里面的 prompt 模板**把原文格式化成标准面经。要点：
   - **我自己面的** → 双栏对照：每题「当时的回答（粗糙）」+「改进后的回答」。参考范本 `公司/快手/大数据平台方向/` 下的一面面经。
   - **网上 copy 的别人的** → 没有「当时的回答」，只写问题清单 + 答题骨架（3-5 bullet/题）。参考范本 `公司/快手/支付方向/快手Java开发日常实习生（支付方向）一面（挂）.md`。
3. frontmatter 照活面经写：`title / type: 面经 / company / bu / round / date / verdict / source / tags`（tags 3-8 个，转载的 `source: 未知` 或 `网上转载`、`verdict: 未知`）。
4. 正文里提到的考点，末尾用双链回主题文章（MVCC→`[[MySQL-MVCC与隔离级别]]`、缓存击穿→`[[Redis缓存三大问题]]`、ConcurrentHashMap→`[[Java并发集合]]`、RAG→`[[RAG优化全链路]]`、MCP→`[[Agent设计模式与MCP]]`）。不确定某主题裸名叫什么就 `ls wiki/技术主题/` 核对，别硬编不存在的名字。
5. 存到 `公司/<公司>/<BU>/<标题>.md`（BU 不知道就放 `公司/<公司>/`）。多篇就重复本节。
6. **收尾（E）**：在对应公司画像 `wiki/公司/<公司>.md` 顶部「面经文件」区加一行 `[[公司/…/新面经]] —— 一句话主旨（这场考了啥）`；如果是新公司先做 C。跑 lint。

### A+. 「我自己面的」额外要做的两件事（2026-08 起，用户明确要求）

只对 `source: 我面试` 生效。转载的面经不做。

**① 每题打三个标签：题型 + 四项评分 + 原话。**

题型三选一——**答题策略完全不同，必须标出来**：

| 题型 | 是什么 | 评分重心 |
|---|---|---|
| **A 项目叙述** | 「讲一下你在 X 的项目」 | 60 秒内讲清 问题 → 我做了什么 → 结果 |
| **B 项目机制** | 「你这个 X 是怎么做的 / 为什么这么做」 | 设计有没有**理由和取舍** |
| **C 通用知识** | 「业界一般怎么解决 X」——**跟公司无关，换一家还会问** | 知不知道**业界标准答案**，能不能报出名字 |

四项评分（每题都过一遍，扣哪项写哪项）：

| 项 | 判据 | 典型扣分 |
|---|---|---|
| **① 落点** | 前 20 秒有没有给出结论 / 说清「我做什么」 | 铺垫超过两句 |
| **② 诊断** | 有没有说出**这个设计的代价 / 取舍** | 只描述现状，段②空缺 |
| **③ 机制** | 方案有没有**裁决者和判据** | 「会检查」「给反馈」是愿望；「谁拿什么判、不过怎么办」才是机制 |
| **④ 口径** | 数字 / 术语 / 有没有说被弃用的说法 / 有没有踩保密红线 | 同场两个打架的数字 |

**② 文件末尾加一张「原答案速查表」**——把每题的**转录原话**（浓缩但保留原措辞，别改写成书面语）连同题型和扣分项列成一张表。
**理由：用户复习时要按原话回顾，看自己当时到底说了什么、然后自己重答一遍。改写成书面语就失去这个用途了。** 正文里的「改进后的回答」是给答案，速查表是给练习——两者都要有，不能互相替代。

**③ 已知的复发毛病，每次入库都要对照检查一遍**（命中就在自评里点名，别当新问题写）：
- 用「没有 / 没做到 / 不是我做的」开局 —— 「没有」必须讲成「取舍」
- 上一题讲过的机制，下一题取不出来 —— 检索失败，不是记忆缺失
- 给了愿望不给机制（缺裁决者）
- 讲在职项目时直呼内部框架名（保密红线）
- 报了追问库里已弃用的数字

## B. 加技术主题

门槛：一个考点在 **≥3 家公司**出现过才值得单独成文（否则塞进相邻主题即可）。
1. 读 [`wiki/模板/新主题文章.md`](wiki/模板/新主题文章.md)，并打开一个活主题（如 `wiki/技术主题/Redis缓存三大问题.md`）照其排版。
2. 结构：一句话要点 → 高频问法（**每条挂 ≥1 个 raw 面经双链证明真出过**）→ 答题骨架 → 易错点&追问 → 深入阅读（链回 `专栏/…` raw）。整篇 ≤250 行，是「面试前压缩版」不是教科书。
3. 存到 `wiki/技术主题/<主题>.md`，frontmatter 照活主题：只有 `title / type: topic / updated`（**注意：活文件并没有模板里写的 `domain` 字段，别自己加**——这正是「照活文件不照模板」的典型）。
4. **收尾**：在 [`wiki/索引/主题.md`](wiki/索引/主题.md) 对应领域段加一行；顺手在来源面经的公司画像补双链。跑 lint。

## C. 建公司画像

触发：raw 里第一次出现某公司。**先判断是不是大厂**，决定建独立页还是并入其他公司：
- **知名大厂 / 你明确当目标的公司**（美团、滴滴、拼多多、小米这类，迟早会面）→ **即使只有 1 篇也单独建** `wiki/公司/<公司>.md`，方便以后持续往里塞。
- **小公司 / 一次性 / 不熟的**，只有 1-2 篇 → **别单独成文**，并进 [`wiki/公司/其他公司.md`](wiki/公司/其他公司.md)，攒够约 3 篇再拆出来单独建页。
- 拿不准算不算大厂 → 问用户一句，或先放 `其他公司.md`（并入比拆分好回退）。

1. 读 [`wiki/模板/新公司画像.md`](wiki/模板/新公司画像.md)，并打开 `wiki/公司/字节.md` 照它的真实排版（概览 / 面经文件 / 考察重点按次数排序 / 真题摘录 / 复习清单双链）。
2. 密度 = 「面试前 30 分钟扫一眼」，每条一句话能讲清。考察重点按出现次数排，真题摘录每条挂出处双链。
3. 存到 `wiki/公司/<公司>.md`。
4. **收尾**：在 [`wiki/索引/公司.md`](wiki/索引/公司.md) 加一行。跑 lint。

## D. 建项目追问库

触发：简历某项目被多家公司追问，需要集中题库。**前提**：`wiki/我的简历/<对应项目>.md` 必须已存在做 ground truth。
1. 读 [`wiki/模板/新追问QA.md`](wiki/模板/新追问QA.md)，参考活文件 `wiki/追问/西门子RAG.md`。
2. 分清边界：**通用原理**（如「Lua 如何原子」）→ 指向主题文章；**项目特定细节**（如「这里为什么选 Lua 不用事务」）→ 留在本页。每个 Q 配 3-5 bullet 骨架 + 出处双链。
3. 存到 `wiki/追问/<项目>.md`，双链区链回 `wiki/我的简历/<项目>`。跑 lint。

## E. 更新派生层

raw 变了、但派生层没跟上时（hook `wiki_refresh_hint.sh` 也会提醒）：把新面经登记进公司画像那一行、必要时更新「考察重点」次数排序和「真题摘录」、在索引补链。**只动 wiki/ 层，不改 raw 面经的原文内容。** 跑 lint。

## 边界：什么时候不该用这个 skill

- **用户刚面完、想复盘自己答得怎样** → 那是 `/new-review`（个人复盘，AI 不替用户填）。本 skill 管的是「把面经知识入库」，不是「反思这场表现」。两者可先后做：先 new-review 复盘，再把值得沉淀的考点用本 skill 收进主题/画像。
- **用户只想跑健康检查 / 看 wiki 状态** → 那是 `/wiki-lint`，直接跑别绕。
- **用户只是查『X 公司爱考什么 / 我该看哪些 wiki』** → 是「读」不是「写」，直接读公司画像 + dashboard 回答，不要新建文件。
