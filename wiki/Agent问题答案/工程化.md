## Q24 — 项目中 AI 贡献的代码占比

> 原题：项目中 AI 贡献的代码占比

**答题骨架**

- **使用方式**：Copilot / Claude Code 主要做补全 + 局部重构；不是把整体 agent 模式开起来让它一把改完。
- **方法论三步法**（[[微软/Bing图像视频业务实习一面面经]]）：
  1. 让 AI 先做 plan，不直接改代码；
  2. 人工 review 方案、明确改动边界 / 风险点 / 涉及模块再授权执行；
  3. 改完每一行关键代码都要能解释。
- **代码占比**：业务样板代码 / 单测 / 文档 60-70%；架构 / 关键并发 / 性能瓶颈代码 < 20%。
- **底层不能完全交给 AI**（ARM 多线程 bug 案例）：复杂并发逻辑需要先自己读懂，再让 AI 辅助分析；自己不读懂代码，AI 修不好。

## Q28 — 长文本生成的技术方案

> 原题：长文本生成的技术方案

**答题骨架**

- **大窗口直生**：用 200K / 1M context 的模型（Claude / Gemini）+ 流式输出；适合一次性长文本，但成本贵。
- **分段生成 + Outline**：先让模型出大纲，再逐节展开，每节生成时只喂相关上下文 → 避免注意力分散。
- **Map-Reduce**：长输入分块 → 每块单独总结（map）→ 合并总结再生成（reduce）；适合长报告 / 论文综述。
- **Iterative Refine**：先写草稿，再让模型 / 评审 critic 给修改建议，循环优化。
- **流式 + 写入**：边生成边落盘 / 推前端，避免等全部生成完才返回；SSE / WebSocket。
- **token 预算**：留 ≥10% 给输出，避免 stop_reason=length 截断。
> 来源说明：部分内容（Outline / Map-Reduce 长文本生成模式）来自社区共识，非直接面试出处。

## Q29 — Agent skills

> 原题：Agent skills

**答题骨架**

- **结构**（[[专栏/Agent/Skills]]）：
  ```
  skills/<name>/
  ├── SKILL.md      # 入口说明书 + YAML frontmatter（name / description / license）
  ├── scripts/      # 可复用 Python / Shell 脚本
  ├── reference/    # 示例 / 模板 / 格式规范
  └── assets/       # 字体 / 图片 / Logo
  ```
- **触发**：模型读 description 决定要不要"装上"这个 skill；不触发就不进 prompt，省 token。
- **执行**：装上后按 SKILL.md 步骤执行，必要时调 scripts / 引用 assets。
- **vs MCP**：Skill 是本地能力包（带 prompt + 代码 + 资源）；MCP 是协议（拉外部能力）。
- **优势**：把"做某类任务的 SOP"代码化、可复用，比纯 prompt 更可控。
- **常见 skill 例子**：pptx 生成、xlsx 处理、pdf 抽取、obsidian-markdown 创建。

## Q32 — 模型预热机制

> 原题：模型预热机制

**答题骨架**

- **目的**：冷启动时第一次推理特别慢（模型加载 / cuda graph 编译 / KV cache 分配），生产环境用户首条请求会感受到。
- **方案**：
  1. **启动期 warm-up**：服务启动后立即跑几条无害 prompt（"hello"），让 vLLM / TensorRT-LLM 完成 cuda graph capture 和权重加载。
  2. **健康检查打 warm**：k8s readiness probe 跑实际推理，未通过不流量。
  3. **常驻热请求**：低 QPS 时定时发 keep-alive，避免被框架自动卸载。
- **embedding 模型也要预热**：第一次 batch 嵌入比稳态慢一倍。
- **缓存预加载**：高频文档 / 高频 query 启动时预先 embed 写入 Redis / 本地。
> 来源说明：无直接面试出处，答案基于 vLLM / TensorRT 官方文档对模型预热的明确支持。

## Q33 — NL2SQL 场景下的 SQL 安全防护

> 原题：NL2SQL 场景下的 SQL 安全防护

**答题骨架**

- **执行账户**：给 LLM 用的数据库账户**只读 + 行级 / 表级权限**，绝不允许 DELETE / UPDATE / DDL；防止 prompt injection 删库。
- **SQL 解析白名单**：用 sqlglot / pgsql-parser 解析模型输出，只放行 SELECT；遇到 INSERT / UPDATE / DELETE / DROP / GRANT / EXEC 直接拒绝。
- **资源限制**：`statement_timeout`、`max rows`（LIMIT 强制注入）、临时表大小、连接超时。
- **schema 注入 + 列级 ACL**：prompt 里只暴露当前用户能看到的表 / 列；敏感列（薪资 / 身份证）做掩码。
- **数据脱敏**：返回值过敏感词 / PII 检测，命中就替换成 `***`。
- **审计**：所有 LLM 生成的 SQL + 结果记录可追溯；接 SIEM 告警异常模式。
> 来源说明：无直接面试出处，答案与 [[蔚来/蔚来CICD组AI agent实习生一面面经-详细版]] 慢 SQL 优化部分技术栈相通。

## Q34 — 复杂任务执行准确率提升的评估方法

> 原题：复杂任务执行准确率提升的评估方法

**答题骨架**

- **拆解评估**：把复杂任务分解为多个 step，每 step 单独打分（如检索 → 推理 → 生成），找出瓶颈环节。
- **三维度**：Correctness（结果对不对）、Process（中间步骤对不对）、Cost（耗时 / token / 调用次数）。
- **LLM Judge**：用更强模型当 judge，配合 rubric（评分标准）；用 F1 ≈ 0.8 与人工标注校准（西门子项目做法）。
- **AB 测试 / 回归集**：每次模型 / prompt / 工具改动跑回归集，对比 baseline；防止局部优化全局退化。
- **失败 case 反查**：trace 链路（LangSmith）定位失败环节，归类后批量修复。
- **黄金集 + 长尾**：黄金集保证基线不退化，长尾 case 集每周补充新真实失败样本。

## Q43 — AI 辅助开发的实践经验

> 原题：AI 辅助开发的实践经验

**答题骨架**

- **三步法**（[[微软/Bing图像视频业务实习一面面经]]）：
  1. 让 AI 先出 plan / 设计，不直接改代码；
  2. 人工 review 改动边界 / 风险点 / 涉及模块，再授权执行；
  3. 改完每一行关键代码都要能解释，不留"看不懂的 AI 代码"。
- **场景适配**：
  - 适合 AI：单元测试、样板代码、文档、CRUD、重构 rename、配置脚本。
  - 慎用 AI：底层并发、内核驱动、数据库迁移逻辑、安全相关。
- **避坑**：
  - 上下文不全的 agent 模式经常生成"看似合理但实际错位"的代码 → 复杂场景必须先把项目读懂。
  - AI 容易引入冗余抽象 / 过度设计，code review 时要主动简化（参考本仓库 CLAUDE.md 中的"代码风格"约束）。
- **效果度量**：留意提交粒度、回归测试、代码评审通过率，而不是行数 KPI。

## Q48 — LangGraph 这种图状态机里，怎么捕获每个节点结果实时推前端

> 原题（淘天一面 ⑮）：流式输出这块，后端是 FastAPI + SSE，但在 LangGraph 这种基于图的状态机里，怎么捕获每个节点的执行结果并实时推前端？

**答题骨架**

- **先说清矛盾在哪**：`graph.invoke()` 是**阻塞黑盒** —— 内部跑了 5 个节点花 30 秒，对外只有"进去"和"30 秒后一次性拿到结果"两个时刻，中间态完全不可见。用户盯着转圈圈 30 秒，会以为卡死了去刷新。
- **比普通 LLM 流式难的地方**：普通流式是一次调用、一个数据源、一种数据（token），一条直线。但图里节点性质不同 —— **检索节点要花 3 秒但一个 token 都没有**。前端要的信息横跨三层，且在完全不同的位置产生：
  | 层次 | 例子 | 产生位置 | `stream_mode` |
  |---|---|---|---|
  | 走到哪个节点了 | 「进入检索阶段」 | 图的调度层 | `updates` |
  | 节点内部干到哪了 | 「BM25 命中 12 条」 | 节点函数内部 | `custom` |
  | 模型逐字输出 | 「根」「据」「您」 | LLM 调用内部 | `messages` |
- **解法：`invoke` 换 `astream`，同时订阅多个 mode**（LangGraph 共七种：`values` / `updates` / `messages` / `custom` / `checkpoints` / `tasks` / `debug`）：
  ```python
  async for chunk in graph.astream(
      inputs, stream_mode=["updates", "messages", "custom"], subgraphs=True):
      chunk["type"]  # 哪一层来的
      chunk["ns"]    # () 主图，("node:task_id",) 子图
      chunk["data"]
  ```
- **`custom` 要在节点里主动写**（框架不知道你内部在干嘛）：`writer = get_stream_writer()` 然后 `writer({"msg": "BM25 检索中"})`。
- 🔴 **必须开 `subgraphs=True`**：多 agent 场景下子 agent 通常是子图，不开这个参数**子图内部执行对外完全不可见**，前端只会看到父图那一个节点卡在那里。
- **五个工程坑（这是拿分的地方）**：
  1. **断连检测** —— `if await request.is_disconnected(): break`。不做的话用户关页面后图还在跑、还在烧 token，线上会有一堆幽灵任务
  2. **不能直接 `json.dumps`** —— `AIMessage` / `ToolMessage` / `AIMessageChunk` 不可序列化；且 `updates` 里可能带着几万字的检索结果，**不要原样转发**，只发节点名和状态
  3. **异常不能让 generator 抛出去** —— HTTP 头已经发了、状态码改不了，抛出去前端只看到流莫名断掉。要 catch 住发 `event: error`
  4. **心跳** —— nginx `proxy_read_timeout` / ALB idle timeout 默认 60s，某个节点跑 90 秒没产出就被中间设备掐断。`EventSourceResponse(gen, ping=15)`
  5. **nginx 缓冲** —— 默认 `proxy_buffering on` 会攒着响应体不转发，SSE 事件全卡住。要 `proxy_buffering off` 或响应头 `X-Accel-Buffering: no`，并关 gzip
- 🔴 **最隐蔽的一个**：**Python < 3.11 的 async 下 `get_stream_writer()` 拿不到**（contextvar 传不下去），要改成 `async def node(state, writer: StreamWriter)` 参数注入；同样地旧版本 async 下**调 LLM 必须手动透传 `config`**，否则 `messages` 模式一个 token 都收不到 —— **这是"流式不生效"最常见的原因**。
- **为什么不用 WebSocket**：需求是单向推送，SSE 够了；走标准 HTTP、浏览器原生 `EventSource` 自动重连、不用改代理和网关配置。WebSocket 要额外处理协议升级 / 心跳 / 重连，换来的双向能力我们不需要。

**拓展双链**：[[LangGraph工程实践]]、[[公司/淘天/AI Agent/淘天AI-Agent一面_2026-07-30]]、[[Agent问题答案/MCP与协议#Q47]]（别跟 MCP 层的流式搞混）、[[专栏/Agent/MCP_SSE_文档]]

## Q49 — 子任务失败了（比如数据抓回来是空的），工作流怎么重试或降级

> 原题（淘天一面 ⑭）：子任务如果失败了，比如数据抓回来是空的，工作流怎么重试或降级？

**答题骨架**

- 🔴 **满分点：「数据抓回来是空的」不是异常，`RetryPolicy` 根本不会触发。** 接口 200 返回一个空数组，这是一次**成功的调用**。面试官举这个例子是故意的，上来答「配个 RetryPolicy」就掉坑。
- **先分类**：
  | 类型 | 表现 | 谁来管 |
  |---|---|---|
  | 硬失败 | 抛异常：超时、5xx、连接拒绝 | 框架 `RetryPolicy` |
  | **软失败** | 正常返回但没数据 | **应用层判断 + 条件边路由** |
  | 语义失败 | 有数据但不对（全是 0、时间过期） | 校验节点 |
- **硬失败**：`add_node(..., retry_policy=RetryPolicy(max_attempts=3, initial_interval=0.5, backoff_factor=2.0, jitter=True, retry_on=(...)))`。
  - **`retry_on` 一定要收窄**到超时和 5xx —— 默认全量重试的话参数错误（400）也会被白重试三次
  - **重试是重跑整个节点函数，不是从中断处继续** → 节点内有写库 / 发消息 / 扣额度必须幂等（业务唯一键 upsert，或把副作用拆成单独节点）
  - `jitter=True` 不加的话并发的几十个节点会同时退避、同时重试，形成脉冲把上游打死
- **软失败**：节点里自己判断，**把判断结果和重试计数写进 state** 让条件边能路由：
  ```python
  return {"rows": rows, "fetch_status": "ok" if rows else "empty",
          "attempt": state.get("attempt", 0) + 1}
  ```
  **`attempt` 必须放在 state 里** —— 图里有环就必须有终止条件，`recursion_limit`（默认 25）只是保险丝不是设计。
- **降级是个阶梯，不是"返回错误"**：① 放宽查询（扩时间窗 / 去次要过滤 / 精确改模糊）→ ② 换数据源（备用源 / 缓存 / 历史快照）→ ③ 降精度（日频拿不到拿周频、个股拿不到拿行业均值）→ ④ 部分成功 → ⑤ 显式告知模型。
- **并行子任务的部分失败**：`Send` 动态 fan-out，每分支独立成败，用 reducer 分别累加 `results` 和 `failures`，汇总节点按成功率决定继续还是降级。这里可以接上 BSP：**并行节点的返回值先 buffer、本超步结束才统一归并，所以某个分支失败不会污染其他分支看到的 state，也不需要加锁。**
- 🔴 **第 ⑤ 条最容易漏也最重要**：给模型一个空数组，它会当作"这部分没什么好说的"然后继续编。给它 `{"rows": [], "status": "empty", "note": "该标的自 2026-07-15 起停牌"}`，它才会在最终回答里如实说明。**空数组诱发幻觉，明确的缺失说明抑制幻觉。**
- **什么不该重试**（说出来显得想过边界）：参数错误（模型填错格式）→ 应该把**错误信息回灌给模型让它自己改**，重试同样的调用一百次还是错；鉴权失败 → 重试无意义要告警；合法的空结果（今天确实停牌）→ 这不是失败。

## Q50 — 为什么用 LangGraph 而不是简单的 LangChain

> 原题（淘天一面 ⑯）：最后问了一个选型问题，为什么用 LangGraph 而不是简单的 LangChain。

**答题骨架**

- 🔴 **先纠正问题前提（这一步比罗列优点更能说明你懂）**：**这不是二选一。LangGraph 本身就是 LangChain 生态的一部分** —— `create_agent` 就构建在 LangGraph 上，官方原话是「middleware 不是独立运行时，钩子跑在 `create_agent` 返回的编译好的 LangGraph 里」。真正的对比是 **LCEL 链式编排 vs 图编排**。
- **LCEL 的形状决定能力边界**：`prompt | model | parser` 是一条**有向无环管道**，数据单向流，每一步只能拿到上一步的输出。于是做不了五件事：
  1. **循环** —— agent 的本质就是 while 循环（想 → 调工具 → 看结果 → 再想），LCEL 是 DAG 表达不了
  2. **分支后再汇合** —— `RunnableBranch` 能分支，但分支之后各走各的，再合流很别扭
  3. **跨步骤共享状态** —— 第 5 步想访问第 2 步的中间产物，只能一路手动透传字典
  4. **中断和恢复** —— 跑到一半要人工审批，LCEL 没有"暂停"这个概念
  5. **自定义并行归并** —— `RunnableParallel` 的归并是固定的字典合并，不能定义「两个节点都往 `docs` 里写怎么合」
- **LangGraph 补上的**：State + reducer / 条件边 + `Command` + `Send`（动态 fan-out）/ Checkpointer（断点续跑 + 多轮记忆 + time travel）/ `interrupt()` 人在环 / 七种粒度的流式 / BSP 超步模型带来的无竞态并发。
- **判据一句话**：**需要环、需要跨步骤共享状态、需要中途暂停 → LangGraph；单向数据变换管道 → LCEL 够了。**
- 🌟 **收尾金句**：**「LCEL 管一步怎么算，LangGraph 管步与步之间怎么走。」** 节点内部照样用 LCEL（`chain = prompt | model | parser` 写在节点函数里），两者不冲突 —— 这句一定要说，否则显得你在把它们对立。
- **反向诚实（加分）**：固定的 `prompt → model → parse` 上 LangGraph 是过度设计；图的调试成本比链高，节点多了追一条执行路径不容易；简单 ReAct agent 现在直接 `create_agent()` 就行，不用手搓 `StateGraph`。
- **v1 之后的分层现状（说出来说明跟着版本走）**：`create_agent()` 是高层入口（底下就是编译好的图）；**Middleware** 是新扩展点，内置 `SummarizationMiddleware`（上下文超长自动摘要）、`HumanInTheLoopMiddleware`（指定工具触发确认）、工具重试、模型 fallback、限流、PII 检测；`create_agent` 的 agent 可以直接作为节点嵌进更大的 `StateGraph`。选型阶梯：**单步变换 → LCEL；标准 agent → create_agent + middleware；复杂多 agent 编排 → 手写 StateGraph**。
