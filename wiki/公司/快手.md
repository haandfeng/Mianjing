# 快手

## 概览
- 方向：**三条线** —— 数据平台 Data Agent（Agent 工程）、大数据平台（Flink 向量化加速、Rust/C++）、支付（Java 后端）
- 难度：Data Agent 线**零八股纯 Agent 工程 + 算法**；大数据线偏底层 + AI 提效；支付线偏八股 + 项目深挖
- 一句话画像：**三条线考法完全不同，别混着准备**——Data Agent 只问 harness/context/skill/幻觉治理；大数据看能否下沉到 Rust/Linux 内核；支付线 MySQL/Redis/JUC 八股密度高，秒杀题一定会问

## Data Agent 线考察重点（单独一套，与上面不重合）

出处见 [[公司/快手/DataAgent方向/快手数据平台DataAgent一面_2026-07-29]]（一面）和 [[公司/快手/DataAgent方向/快手数据平台DataAgent二面_2026-08-10]]（二面）。

**一面（零八股，硬追问 + 算法）：**
1. **harness 工程怎么治理幻觉** —— 来源强制引用 + 生成前强校验 + 控制 context 长度（harness = 承载 agent 运行的外层框架，管上下文拼装/工具注册/循环控制/校验门禁）
2. **上下文膨胀与压缩** —— summary 会丢关键信息、offload 到磁盘只留索引、怎么让压缩「按表填空」而非自由复述
3. **skill 执行命中率** —— 三层递进：触发概率（删无关 skill / 写清适用范围）→ prompt 里 XML 写 forbidden → **middleware 强制校验工具调用**
4. **让模型流程可控**（最硬的一题）—— 跳步 / 假执行 / 结果不稳定三症状，要给**工程化**方案而非 workflow、subagent、人工确认
5. **评测体系** —— 分点评分 + 多次取平均只解决打分稳定性；**「不重不漏」问的是测试集覆盖度**，要答长尾采样 / 结构反向生成 / bad case 回流
6. **多 agent 的必要性** —— 不能只说「更准」，要给业务动因（状态叉乘 → 以偏概全）和模型动因（长程注意力衰减 → 幻觉）
7. **记忆系统** —— DeerFlow 的（粗糙，会腐化）和 Claude Code 的（显式指令 / 定时整理 / idle 后 subagent 总结）
8. **算法** —— 中等偏基础两道，本场是 LC53 最大子数组和 + LC78 子集

**二面（项目机制问答为主，追问烈度低但题量大）：**
1. **决策编排/review agent 兜底机制** —— 为什么用、准确率 56%→87%、13% 剩余错误的两个原因（问题没剪枝、评分指标不匹配）
2. **A2A 通信设计** —— agent 当工具调用（loop 看输出是工具信息还是纯文本）、代价是子 agent 拿不到完整历史
3. **subagent 被禁用的原因** —— 任务边界模糊导致派发给 subagent 后超限报错、不可复现、多线程 bug
4. **决策树 vs 预编译 workflow 的适用边界** —— 状态空间能否穷举是分界点（对比另一候选人做 oncall agent 的预编译方案）
5. **评测数据飞轮关键点** —— 数据数量 + 评测速度；**case 集怎么迭代替换**——去 memory 测试剔除已被模型内化的 basic case、按用户差评优先捞新 case
6. **DAG 任务调度器现场设计**（AI 辅助 coding）—— 失败传播语义（下游全停）+ in-flight 任务处理（跑完不打断）

> 💡 **数据平台领域词必须能张口就来**（我的背景里没有）：数仓、数据血缘、数据地图、指标中台、BI、GMV、ROI、Hive / Spark / ClickHouse。

## 真题摘录（值得背的）

> 🔴 **【分水岭题】流程是「取数 → pandas 分析 → 给结论」，模型会跳过分析步 / 给假分析（复用上轮结果）/ 结果每次不稳定，有什么工程化办法？** 出处 [[公司/快手/DataAgent方向/快手数据平台DataAgent一面_2026-07-29]]
> 三个症状同一个根因：**把「过程」也交给了模型自述，而自述不可信**。解法是把关键步骤从「模型说它做了」变成「系统能观测到它做了」——
> ① **跳步** → 门禁校验：分析必须走真实代码执行工具，trace 里查得到调用记录；没有记录直接打回重做（一个 if，零额外模型调用）
> ② **假分析** → 内容指纹：输入数据 hash + 分析代码 hash 与结果绑定，对不上就是复用旧结果，拦截（模型伪造不了系统算的指纹）
> ③ **不稳定** → 算子固化：分析代码第一次让模型写、校验通过后固化成带参数的函数注册进工具库；此后模型只决定「调哪个、传什么参」，不决定「怎么算」
> **⭐ 一句话原则：能用代码校验的不要用 prompt 请求；能沉淀成工具的不要让模型每次现写；能让系统观测的不要信模型自述。**
> 成本/确定性三层：**prompt 提示（免费、不可靠）< 门禁校验（一个 if、100% 可靠）< 算子固化（要开发、锁死行为）**。别一上来就跳到 workflow（不泛化）或 subagent 监督（费 token + 体感差）。

> **怎么保证评测「不重不漏」？** 出处 [[公司/快手/DataAgent方向/快手数据平台DataAgent一面_2026-07-29]]
> 分点评分 + 多次取平均只解决**打分稳定性**，不解决**覆盖度**。长尾要靠：①线上真实 query 按频次分层采样（长尾按比例随机采）②从系统结构反向生成——有多少业务分支就该有多少问题，**把「漏」从感觉变成可计算的覆盖比例** ③bad case 自动回流进测试集。核心：**测试集不该是人想出来的，该是从真实分布和系统结构里长出来的。**

> **数据迁移如何保证一致性？异常如何回滚？** 出处 [[快手/大数据平台方向/快手一面面经]]
> 三阶段：迁移前快照 + 幂等 upsert；迁移中批次内事务 + checkpoint 同事务持久化；迁移后 count + hash 聚合校验。完全回滚优先用快照恢复，比覆盖重刷可靠。

> **可重复读还会不会幻读？举例。** 出处 [[快手/支付方向/快手日常实习（支付方向）面经]]
> 会。两类场景：①事务 A 快照读 → 事务 B 插入提交 → A 更新这条记录后再快照读会看到（trx_id 变成自己的）；②先快照读、再当前读（select for update）会看到 B 新插入的行。要彻底避免就在事务一开始就 select for update，让 next-key lock 兜底。

> **如何判断 AI 生成的 C++ 代码性能足够好？** 出处 [[快手/大数据平台方向/快手一面面经]]
> 两手：代码审查看常见反模式（值传递大对象、循环内 new、该 move 用 copy、该 unique_ptr 用 shared_ptr），加 Google Benchmark 实测吞吐和延迟。
