## 真题摘录（值得背的）

> 🔴 **【陷阱题】MCP 返回的结果支不支持流式？** 出处 [[公司/淘天/AI Agent/淘天AI-Agent一面_2026-07-30]]
> **答"支持，协议就是支持的"会掉坑。** 要分两层：**传输层支持流式，但 `tools/call` 的返回值不支持增量返回。** Streamable HTTP 下 server 可以把 POST 的响应体开成 SSE 流推 `notifications/progress`，但 `CallToolResult` 是一条完整的 JSON-RPC response，schema 里没有任何「部分结果 / chunk」字段。流里的 progress 是**独立的通知消息**，跟 result 不是一个东西，`message` 字段规范定义的就是 human readable 进度描述，给 UI 看的，默认不进模型 context。
> **这是刻意取舍**：工具结果要回灌给模型推理，模型需要完整自洽的一块数据，半截结果反而诱发幻觉；LLM 流式是因为消费者是人。长任务用 `2025-11-25` 新增的 `tasks` 原语（工具上 `execution.taskSupport` 声明），但最终结果依然一次性。

> 🔴 **【分水岭题】子任务失败了，比如数据抓回来是空的，工作流怎么重试或降级？** 出处 [[公司/淘天/AI Agent/淘天AI-Agent一面_2026-07-30]]
> **满分点：「抓回来是空的」不是异常，`RetryPolicy` 根本不会触发**——接口 200 返回空数组是一次成功调用。上来答「配个 RetryPolicy」就掉坑。
> 硬失败（抛异常）走节点级 `RetryPolicy`，但 `retry_on` 要收窄到超时和 5xx，且**重试是重跑整个节点不是断点续跑**，节点内有写操作必须幂等。软失败（空结果）要在节点里自己判断，把 `fetch_status` 和 `attempt` 写进 state 靠条件边路由，**`attempt` 必须在 state 里**否则回环一直转。
> 降级阶梯：放宽查询 → 换数据源 → 降精度 → 部分成功（`Send` 并行子任务用 reducer 分别收集 results/failures）→ **显式告知模型**。最后一条最容易漏：**给模型空数组它会当没这回事然后编，给它「该标的自某日起停牌」这种明确缺失说明它才会如实标注。空数组诱发幻觉，明确的缺失说明抑制幻觉。**

> **两种检索结果的融合逻辑怎么设计的？** 出处 [[公司/淘天/AI Agent/淘天AI-Agent一面_2026-07-30]]
> 关键是说出**为什么不能直接合并分数**：BM25 是无上界的 tf-idf 累加，cosine 在 [-1,1]，量纲不同，相加等于让 BM25 说了算。所以用 **RRF（Reciprocal Rank Fusion）只看排名不看分数**：`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60，天然免疫量纲问题且毫秒级。再接 cross-encoder reranker 精排——**RRF 负责别漏，reranker 负责排得准**。互补机理：长文档里少数关键词的信号会被其余句子的语义稀释，而型号 / 错误码这类 OOV 词恰恰是 BM25 最准的地方。提升发生在**召回环节**，不是生成环节。

> **在 LangGraph 这种基于图的状态机里，怎么捕获每个节点的执行结果并实时推前端？** 出处 [[公司/淘天/AI Agent/淘天AI-Agent一面_2026-07-30]]
> `graph.invoke()` 是阻塞黑盒，改用 `astream()` 并**同时订阅多个 `stream_mode`**：`updates`（节点级增量）+ `messages`（LLM token）+ `custom`（节点内 `get_stream_writer()` 主动写的业务进度）。**必须开 `subgraphs=True`**，否则子 agent 内部对外全黑，前端只看到父图卡住。
> 五坑：断连检测（`request.is_disconnected()`，否则用户关页面还在烧 token）/ LangChain message 对象不能直接 `json.dumps` 且 `updates` 里的检索结果不能原样转发 / 异常不能让 generator 抛出去（HTTP 头已发）要发 `event: error` / 心跳防 nginx-ALB 60s idle 断连 / `proxy_buffering off`。
> **最隐蔽的**：Python < 3.11 async 下 `get_stream_writer()` 拿不到，要用 `writer: StreamWriter` 参数注入；且调 LLM 必须手动透传 `config`，否则 `messages` 模式一个 token 都收不到——这是「流式不生效」最常见原因。

> **大模型在没有 MCP 之前，调用工具的处理流程是怎样的？** 出处 [[公司/淘天/AI Agent/淘天AI-Agent一面_2026-07-30]]
> 两阶段。ReAct 时代靠 prompt 描述工具 + **正则解析** `Thought/Action/Action Input`，极脆，而且**必须设 `stop=["Observation:"]`，否则模型会自己把工具结果编出来**然后基于幻觉继续推理。2023-06 Function Calling 把工具定义变成 API 独立参数（JSON Schema）、调用意图变成独立 `tool_calls` 字段，不用解析且能 constrained decoding，但工具**仍硬编码在应用进程内**。
> **MCP 模型侧一个字节都没改**——还是翻译成 function calling 格式塞给模型、模型返 tool_call、host 执行。它改的是**工具从哪来（硬编码 → 运行时 `tools/list` 发现）和在哪跑（进程内函数 → 独立进程/远程）**，本质是 N×M → N+M。加分：Resources 和 Prompts 是 function calling 里根本没有对应物的原语，控制权不归模型。

> **为什么用 LangGraph 而不是简单的 LangChain？** 出处 [[公司/淘天/AI Agent/淘天AI-Agent一面_2026-07-30]]
> **先纠正前提：不是二选一**，LangGraph 本身就是 LangChain 生态的一部分，`create_agent` 就构建在它上面。真正的对比是 LCEL 链式 vs 图编排。LCEL 是有向无环管道，做不了循环、分支再汇合、跨步骤共享状态、中断恢复、自定义并行归并。
> **收尾金句：「LCEL 管一步怎么算，LangGraph 管步与步之间怎么走」**——节点内部照样用 LCEL。再补反向诚实：流程本来就是固定单向变换的话上图是过度设计，调试成本还更高。
