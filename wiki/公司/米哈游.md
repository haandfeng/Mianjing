## 考察重点（按出现次数排序）

> 分两组看：**A 组**是我自己那场的（LLM 原理与 Agent 运行时），**B 组**是转载那两场的（Agent 场景 + 后端八股）。**三场唯一重叠的是上下文压缩 / summary。**

### A 组 —— 我那场（原理与运行时）

1. **LLM 为什么会错、怎么证明它没错（2 题）** —— 幻觉原理 / 事实度与忠实度。**这两题问的是原理不是缓解手段**，答 RAG 就跑偏了。见 [[幻觉与事实性评测]]
2. **Skill 与 MCP（2 题）** —— 区别 + Skill 有什么特性。**要能报出渐进披露三级和具体数字**（约 100 token / 正文 < 5k / `name` ≤ 64 / `description` ≤ 1024）
3. **Agent 运行时的交互控制（2 题）** —— 用户同时发两条怎么处理 / 怎么实现 steer 续接说话。🔴 **这两题仓库里原来完全没有**，硬结论是「**只有工具执行边界是安全插入点**」「**取消的 `tool_use` 也必须补 `tool_result`**」
4. **AI coding（2 题）** —— 怎么用 + 怎么保证质量。**2026 秋招通用题**，见 [[AI-Coding工程实践]]
5. **可观测（1 题）** —— trace 怎么做、Agent 开发要记什么。**收口在「trace 的价值不是 debug 是评测飞轮」**
6. **开放题（2 题）** —— 游戏 Agent 发展方向 / 你还有什么闪光点

### B 组 —— 转载那两场（场景与八股）

1. **多 Agent 架构（两场都问，共 5 题）** —— 架构长什么样 / 为何从单 Agent 升级 / 其他形态优缺点 / 子 Agent 以什么形式加载 / 主子是否同进程。**「优缺点」和「同进程还是不同进程」是分水岭题**，只答自己的选择不答代价会掉档
2. **记忆系统（两场都问，共 4 题）** —— 存储怎么设计 / 写入异步流程怎么触发 / **为什么这么设计** / **久远信息怎么淘汰**。注意二面问的是「为什么」不是「是什么」
3. **生产真实性验证（二面主线，7 题）** —— 线程池多大 / 观测过吗 / 怎么调的 / 限流阈值是 QPS 吗 / 混合还是分别测 / 阈值多少 / 用户画像分析过吗。**这一类题没有标准答案，只有「说的是不是真的」**
4. **权限与数据安全（两场都问，共 5 题）** —— Agent 保密信息怎么防越权 / 身份参数从哪获取 / 认证态从哪注入工具 / 方法内部之外还有哪些地方 / 数据召回时做过什么处理
5. **后端高并发（一面 5 题）** —— DB 压力大 / 线程池队列打满还要最终消费完 / 重试风暴拖垮 DB 怎么止损 / 缓存维度 / 联合索引
6. **消息队列（一面 4 题，原题问 Kafka）** —— 不丢 / 不重 / 同用户顺序 / 堆积排查与止血。按仓库口径统一用 RabbitMQ 答，见 [[消息队列不丢不重]]

## 真题摘录（值得背的）

> 🔴 **【原理题，最容易答偏】AI 的幻觉原理是什么？** 出处 [[公司/米哈游/米哈游一面（我面试）_约2026-08]]
> **问的是原理不是缓解手段，上来答 RAG 就跑偏。必须两段：**
> **① 预训练**——优化目标是**似然**（给定前文，下一个词该是某个具体词的概率），里面**根本没有「这句是不是真的」这一项**。OpenAI 2025 那篇 *Why Language Models Hallucinate* 把它归约成二分类：模型分不开「错误陈述」和「事实」，统计压力下**必然**产生幻觉，**语料里只出现过一次的事实**（singleton）尤其只能猜。
> **② 后训练之后为什么还在——这段才是那篇论文的新意**：**因为评测在奖励猜测**。多数评测集答错 0 分、说「不知道」也 0 分，那**猜就是严格占优策略**，模型被训练成会蒙题的应试者。修法在改评分：错误扣分、弃答给部分分，让**校准**（说 70% 把握的那批实际正确率就接近 70%）比装懂更划算。
> **③ 补一句接住检索场景**：材料就在上下文里它也可能不用——注意力被稀释。**所以压缩不只省钱，是提准确率的手段。**

> 🔴 **【分水岭在第一句】怎么解决 AI 回答的事实度、忠实度？** 出处 [[公司/米哈游/米哈游一面（我面试）_约2026-08]]
> **第一句必须把两个词掰开**：**忠实度**比对的是**你给它的材料**，**事实度**比对的是**世界真相**。
> **然后给双向背离的例子**：材料错了它忠实照抄 → 忠实度满分、事实度 0；它凭记忆答对但材料没写 → 事实度满分、忠实度低。
> **排序：先死保忠实度**（可控、可自动化、不用标注），**事实度靠语料治理**。三段落地：检索侧提质量 + **召回不到就拒答**；生成侧强制引用 + **给模型一个「无法确定」的合法出口**（没有认输的选项它一定会编，这条直接呼应上一题的评分机制）；生成后做 **claim 级回验**（拆原子断言逐条回材料查，命中比例即忠实度，就是 RAGAS faithfulness 的算法，**reference-free 所以能挂线上跑**）。
> **必须主动说的天花板**：**忠实度指标天然测不出「材料本身是错的」**，剩下那一半只能靠知识库治理。

> 🔴 **【全新题型】用户如果同时发送两个对话，你怎么处理？** 出处 [[公司/米哈游/米哈游一面（我面试）_约2026-08]]
> **开口先澄清两种读法**（并发请求 / 同会话内连发两条），后者才是真问题。四种策略：排队 / 打断重投 / 合并 / 步间注入。
> **核心难点这一句一定要说**：**agent 的一个 turn 不是一次 API 调用，是几十次调用的循环**，所以问题变成「哪些点是安全插入点」——**答案是只有工具执行的边界**，因为那一刻每个 `tool_use` 都配好了 `tool_result`，消息数组自洽；**在一次 API 调用中途插入，消息结构就非法了，下次请求直接 400。**
> 补一条现状：**Claude Code 目前是排队不打断**（工作时按回车只入队，要打断得 Ctrl+C），而且**文档和实现对不上**，社区有多个 issue 在追；真正的 mid-turn steering 还是 open 的 feature request。

> 🔴 **【全新题型】你是怎么实现 AI 的 steer 的？就是续接说话** 出处 [[公司/米哈游/米哈游一面（我面试）_约2026-08]]
> **先立定义**：steer = 在 agent **已经开跑、还没跑完**时插入新指令改变它接下来的行为；「续接说话」= 用户话说一半又补一句，要接进**当前这轮**。
> **四层，从便宜到难**：**① 输入侧聚合**（IM 场景收到消息先等 1~2 秒，期间再来就重置计时一起打包——跟模型无关，能解决大部分场景）→ **② turn 内 steering**（在工具边界追加消息；🔑 **必须是追加不是重写历史，否则 prompt cache 前缀全废**，这跟决策树 append 到消息末尾是同一个道理）→ **③ 硬打断**（🔴 **取消掉的 `tool_use` 也必须补一条 `tool_result` 说「已取消」**，不然消息结构非法下次 400——**这条最能证明真写过**）→ **④ 流式中途插话**（先把已流出的部分落成 partial assistant 消息再接）。

> 🔴 **【开放题别发散】你认为游戏 Agent 有什么发展方向？** 出处 [[公司/米哈游/米哈游一面（我面试）_约2026-08]]
> **先给切分框架再说内容**：agent 在游戏里有**三个位置**——
> **① 玩家侧（作为游戏内容）**：能对话但**不能行动**，门槛不是对话质量，是把语言决策接到游戏状态机上。三个硬约束：**延迟**（帧驱动，秒级响应在战斗里等于卡死 → 慢思考做规划、快策略做执行）、**成本**（DAU 千万时每个 NPC 每句都调模型算不过来）、**可控性**（不能剧透/违规/OOC → **硬门禁不是 prompt 劝说**，跟决策树门禁一个思路）。
> **② 开发侧（作为生产力，短期最确定）**：自动化测试（长程决策 + 状态空间爆炸，人工覆盖不到）/ 内容的**约束生成**（必须落在策划的 schema 和数值区间里）/ 研发答疑（**「文档常年过期只有代码是真的」在游戏项目里比广告平台更成立**）。
> **③ 研究侧（游戏作为 agent 的训练场）——收口在这里**：「游戏提供**可验证、可无限重来、长程**的任务信号，这恰恰是 agent 训练最缺的。**所以对一家游戏公司来说，你的游戏本身就是别人没有的 agent 训练和评测环境**」。

> 🔴 **【2026 通用题】你怎么用 AI coding？怎么保证质量？** 出处 [[公司/米哈游/米哈游一面（我面试）_约2026-08]]
> **第一题给判据不给工具测评**：按控制权分三档（补全 / 对话 / 代理），**判据一句话——给它上下文的成本会不会超过我自己写的成本**。
> **第二题第一句就点破因果**：**模型优化的是「像不像对的」不是「对不对」，所以它的错误天生长成「读起来很顺」那一类，正好是人眼最容易放过的**——所以质量保证**不能建在 review 上**。三层：输入侧先写测试（测试即机器可执行的规格）/ 生成侧限制单次 diff 规模 / 验证侧靠类型检查·测试·lint·CI 这些**不依赖人眼的信号**，**人工 review 只留给安全权限路径 + 「它做了我没让它做的事」**。
> 详见 [[AI-Coding工程实践]]

> 🔴 **【分水岭题】你们生产配的线程池是多大？** 出处 [[公司/米哈游/米哈游提前批二面_约2026-08]]
> **编一个数字会在下一个追问「怎么调的」当场崩。** 正确路径三段：**① 纠正前提**——LLM 应用是 Python 异步/极端 IO 密集，真正的控制量不是线程数是「同时在途的模型调用数」；**② 给公式**——Little's Law（利特尔法则：稳定排队系统里，在途请求数 = 到达率 × 单请求停留时间），单次调用 10 秒要撑 20 QPS 就需要 200 个并发槽位，**这个数跟 CPU 核数完全无关**，所以「线程数 = 核数 × 2」那套在这里彻底失效；**③ 收口**——公式只给初值，真正的数是阶梯加压找拐点、按拐点 70~80% 定线上值。
> **没压过的正确答法**：「我们这个量级还没做正式压测（说清为什么：瓶颈明确在模型侧）+ 如果要我做我会怎么做 + 我在另一个项目做过类似的」。**三段合起来的分数远高于编一个数字。**

> 🔴 **【最有含金量题】你们测出来的数值是 QPS 吗？测的是混合阈值还是分别去测得出的阈值？** 出处 [[公司/米哈游/米哈游提前批二面_约2026-08]]
> **两个子问题都要正面答。① 「是 QPS 吗」——对 LLM 系统 QPS 是个坏指标**：单请求耗时方差极大（简单问题 5 秒、复杂问答几十轮工具调用要几分钟），**QPS 相同的两个时刻实际压着的负载可能差十倍**。真正该管的是**在途并发数**（直接对应资源占用）和 **token 速率**（因为模型网关的配额本来就按 token 计）。QPS 是观测指标不是控制指标。
> **② 「混合还是分别」——两个都要，用途不同**：分别测得到单接口天花板和瓶颈定位，但线上不存在这种情况（各接口共享连接池、DB、下游配额，分别测的数加起来一定超过真实容量）；混合测按线上真实流量配比压，得到系统真实容量。**收口：分别测用来定位瓶颈，混合测用来定线上阈值。** 只做分别测的典型事故是——每个接口单看都没超，合起来把共享连接池打满了。

> 🔴 **【最刁题】你们的这个身份参数是从哪获取的呢？** 出处 [[公司/米哈游/米哈游提前批二面_约2026-08]]
> **唯一正确答案：从请求入口的会话上下文取，不是从模型输出里取。** 必须把话说死——**身份如果是模型填进工具参数的，等于把越权能力交给了一个概率系统**：它可能被提示注入诱导填别人的 ID，甚至只是幻觉就填错了。具体路径：消息本身携带发送者身份 → 网关校验 → 放进**对模型完全不可见**的运行时上下文（既不在 system prompt 里，也不在工具参数表里）→ 框架在执行工具那一层注入。
> **防「那模型怎么知道在给谁服务」的补刀**：模型可以拿到「当前是运营角色」这类**用于调整表达**的脱敏标签，但那不是可用于鉴权的凭证——**能影响表达的信息和能影响授权的信息必须是两份。**
> 加分：业界标准做法是 **on-behalf-of（代表用户行事）流程 + OAuth 2.0 Token Exchange（RFC 8693）**换降权短时凭据。⚠️ **两个身份的位置别说反**——**主体（`sub`）是被代表的那个用户，agent 放在附加的代理字段（`act`）里**；请求侧对应 `subject_token`（用户）+ `actor_token`（agent）。

> 🔴 **【最容易掉的坑】久远的信息，记忆管理会做什么淘汰机制吗？** 出处 [[公司/米哈游/米哈游提前批二面_约2026-08]]
> **第一句就要掰开前提：「久远」和「过时」是两回事。** 用户三年前说「习惯用 pytest」今天依然成立；昨天写的「接口返回字段叫 X」改个版就失效了。**纯按时间淘汰会先删掉最稳定的那批——那恰恰最有价值。** 正确的淘汰信号是**最近被用到的时间**和**用了之后有没有帮上忙**，不是写入时间。
> 三种机制递进：**TTL**（只适合天生有时效性的）→ **使用衰减**（热度分随时间衰减、命中即回补，主力）→ **失效检测**（把记忆和它依赖的事实源关联，最有价值也最难）。打分用**引用次数 + 最近使用 + 被引用后的任务成功率**，第三个是自进化记忆和普通记忆的分界。
> **两级 token 预算别漏**：常驻的描述层要设总预算（每轮都注入，膨胀是慢性中毒）/ 正文层可宽松（按需读）/ 单条设上限。**三个预算防三种不同的膨胀。**
> **收尾金句：淘汰不等于物理删除**——删了就没法回答「上季度的偏好是什么」，更麻烦的是新记忆后来被证伪时滚不回去。标失效（移出检索候选集但记录还在）才对，物理删除只留给明确的污染内容。

> **除了在方法内部做权限处理，还有什么地方吗？** 出处 [[公司/米哈游/米哈游提前批二面_约2026-08]]
> 五层纵深：网关认证 → **工具注册层** → 数据召回层 → 方法内部 → 输出脱敏 + 审计。
> **最该强调第二层，因为它是 Agent 系统独有的：工具的可见性本身就是一个权限点。** 传统系统里接口存在但你调不动；Agent 系统里**只要工具出现在模型的工具列表里，模型就会去尝试调**——即使最终被拒绝，这次尝试也有成本：浪费轮次、报错信息可能泄漏结构、还会让模型基于失败去猜测编造。**正确做法是按角色动态组装工具列表。**
> 再加一层 Agent 特有的：**提示注入防护**——检索回来的代码注释/文档里可能藏着「忽略之前的指令」，**这跟 SQL 注入是同一类问题：数据和指令混在一个通道里传。**

> **数据在被召回的时候做过什么处理？** 出处 [[公司/米哈游/米哈游提前批二面_约2026-08]]
> 四类处理：**权限过滤（必须前置）** → 切分清洗 → 融合精排 → 脱敏。
> **前置 vs 后置过滤是这题的分水岭**：后置过滤（先检索 top-k 再踢掉无权的）有两个问题——① 敏感内容已被取出，日志/缓存/异常信息都可能泄漏 ② 踢完可能只剩两三条，**召回质量塌了却没有任何信号**。前置做法：按权限域分索引/分命名空间，或在切片上挂访问控制元数据参与过滤。
> 另一个易漏点：**脱敏要在入库时做，不是查询时**——入库脱敏一次之后所有查询都安全；查询时脱敏，每条查询路径都要记得做，漏一条就是漏洞。

> **为何升级成多 Agent 架构？其他架构了解吗？优缺点？** 出处 [[公司/米哈游/米哈游提前批一面_约2026-08]]
> **开口先用 Anthropic 官方三条判据**（[[专栏/Agent/什么时候选择多智能体]]）：只有**上下文污染严重 / 任务可并行 / 专业化能改善工具选择**这三种场景下多 Agent 才稳定优于单 Agent，出了这三条协调成本大于收益。
> 🔑 **金句（原文）：「并行化的核心优势在于全面性，而非速度。」** 代价是更高 token + **更长的总执行时间**。
> **这句对自己的项目特别好用**：审核 Agent 不是为了跑得快，是为了拿一个干净上下文——**命中第①③条、没命中第②条并行，时延确实翻倍**。**主动说清命中哪几条、没命中哪条，比笼统说「多 Agent 更好」高一档。**
> 反向一派也要带：Cognition《Don't Build Multi-Agents》主张默认串行（[[Agent问题答案/Agent设计]] Q18 已记）。
> **追问「还了解哪些框架/范式」→ [[Agent问题答案/Agent设计]] Q31 有现成清单**：AutoGPT/BabyAGI · AutoGen · CrewAI · LangGraph · OpenManus/OpenClaw · Anthropic Skill · Cognition Devin。想再高一档就上 [[Agent设计模式与MCP]] 的**「旧范式 vs 新范式」**对比表——**决策树门禁恰好是「新范式 + 校验门禁收敛不确定性」的实例**。

> **上下文逐步膨胀怎么解决？** 出处 [[公司/米哈游/米哈游提前批一面_约2026-08]]
> 同类题 [[公司/蔚来/蔚来CICD组AI agent实习生一面面经-详细版]] 问过「长期/短期记忆 + 大文档 + token 超限」，**是同一题的不同问法**。存货：[[专栏/Agent/Claude Code Context管理]] · [[专栏/Agent/记忆压缩]] · [[专栏/Agent/Harness Engineering]]。
> 先立定义：**context rot（上下文腐化）指的不是 token 超限报错，而是没有任何报错、模型对关键信息的注意力被稀释后悄悄变笨**——静默退化才是它最难的地方。
> 五个手段按侵入性排：**压缩（compaction）/ 卸载（大结果写外部，上下文留句柄）/ 工具结果清理（丢可重取的结果但保留「调用发生过」这条记录，否则模型会重复调）/ 子 Agent 隔离（这是多 Agent 除分工外的第二个动机，很多人只讲第一个）/ append-only（不改写历史，保住 KV-cache 前缀）**。
> 反直觉的坑：**压缩会把早期的约束条件一起压没**，system 级约束要豁免。

> **`select a from t where b=10 and c>20 and d=30` 怎么建索引？** 出处 [[公司/米哈游/米哈游提前批一面_约2026-08]]
> **`(b, d, c)`，再加 a 做覆盖索引变成 `(b, d, c, a)`。** 口诀：**等值在前、范围在后、排序其次、覆盖收尾。**
> 理由要说到 B+ 树的排序结构上：建成 `(b, c, d)` 的话，b=10 定位到一段、c>20 在这段里是连续范围，**但这个范围内 d 是无序的**，所以 d=30 只能逐行过滤。建成 `(b, d, c)` 则两个等值条件直接定位到精确位置，**该位置内部 c 有序**，全程走索引。
> 追问「c 区分度特别高呢」→ **区分度影响「值不值得建」，不影响「等值和范围谁在前」——顺序规则来自 B+ 树结构，跟数据分布无关。**

> **to C 高并发，线程池/队列被打满被拒绝，还想最终消费完，怎么办？** 出处 [[公司/米哈游/米哈游提前批一面_约2026-08]]
> **核心一句：「最终一定消费完」和「任务只存在内存里」是矛盾的，任务必须先落持久化介质。**
> `CallerRunsPolicy`（让提交任务的线程自己执行）值得单独讲，因为它是**背压**的最朴素实现——**背压 = 下游处理不过来时把「慢」的信号反向传给上游让它减速**。但它治标：如果调用线程是 Web 请求线程，会导致接口整体变慢甚至容器线程耗尽。
> 真正答案三段：**落盘优先**（先写 DB 任务表或 MQ，即 Outbox/本地消息表模式，写完就返回「已受理」）→ **线程池降级成纯消费者**（它满了无所谓，任务还在持久层）→ **补偿闭环**（定时扫 pending 超时任务重投）。收尾两句：「最终消费完」= 至少投递一次 + 消费端幂等；**必须有重试上限，不设上限的「最终一致」是事故的开始。**

> **DB CPU 高写入慢，上游超时重试拖垮 DB，怎么止损？** 出处 [[公司/米哈游/米哈游提前批一面_约2026-08]]
> **先叫出名字：重试风暴**——DB 慢 → 上游超时 → 重试 → 负载翻倍 → 更慢，**重试本身成了故障放大器**。所以第一刀往往是砍重试而不是救 DB。
> 止血顺序：**砍重试（改指数退避 + 抖动，加重试预算）→ 入口限流（部分可用远好于全部不可用）→ 熔断（这一步保护的是应用不是 DB，不然 DB 恢复了应用已全线程卡死）→ 杀慢查询 → 降级非核心写**。
> 治本别漏这条：**超时预算要从上游往下传，下游超时必须严格小于上游超时**——否则上游已经放弃了下游还在跑，纯浪费。
