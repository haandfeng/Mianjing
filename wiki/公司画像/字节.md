## 概览
- 公司归档：TikTok（原目录 TT）统一归入字节；SRE、Search Ads 等业务方向分别保留。
- 方向：财经业务（今日头条）、广告中国（巨量引擎/商业化）、广告国际化（TikTok Ads / 国际商业化）、**Commercial AI · Agent Infra（商业化 AI 基础设施，2026-07 新增）**；TikTok 的 SRE、Search Ads 见下方分节。
- 难度：项目深挖 + 操作系统/网络底层；广告国际化最硬，问到 NAT、虚拟内存映射、Redis 删除复杂度

## 考察重点

### A. Agent Infra 线（2026-07 起，与下面的八股线互不重叠）
1. **memory 系统设计九维度** —— 自进化的定义 / 长短期与类别分层 / 存储介质 / 写入时机 / 新旧冲突消解 / 记忆污染 / 交付形态 / agent runtime 迁移。**面试官按这个顺序逐项扫，一题一问不深追，但每一项都要有完整的第一答案**
2. **多 Agent 编排的动机与效果** —— 决策树门禁怎么构建、review agent 看什么信息、消融实验的数字对照
3. **方案伸缩性** —— 业务量涨十倍这套还 run 得动吗（检索层 / 决策树层 / 评测层三层分别答）
4. **AI coding 使用心得** —— 团队明确的用人要求，**是送分展示题不是闲聊**
5. **你所用框架的扩展点**（二面新增，🔴 断点）—— hook 挂在生命周期哪个位置、一共有哪些 hook、能不能拦、能不能改写入参。**这是你项目的说明书，不是课外知识**
6. **单实例 → 平台的完整链路**（二面新增，连问五次）—— 多实例怎么分流 / 只读物料与会话产物分别放哪 / checkpoint 数据库选型（**先算量级再选型，别用「写多→NoSQL」的八股推理**）/ 实例挂了内存里的东西丢不丢
7. **多租户与代码权限**（二面新增，🔴 对方主场）—— agent 用服务账号权限替用户干活 = **confused deputy**；**过滤点必须在工具层做身份透传，不能在输出层删路径**
8. **RAG 存储与检索的原理层**（二面新增，🔴 断点）—— ES vs 专用向量库怎么选、Milvus 的 BM25 是内置函数还是你自己灌 sparse、**BM25 的稀有词靠 IDF（跨文档）不是 TF（篇内频次）**
9. **编码题：agent context manager**（二面）—— `max_token` + `max_turn` 双限制的滑动窗口。**核心考点是「必须整轮丢弃」**，半轮会留下孤儿 `tool_result` 直接触发协议报错
10. **算法一道 Medium** —— 会议室 II（LC253，一面）、统计完全子数组的数目（LC2799，三面）
11. **检索与重排的底层原理**（三面新增，🔴 断点，**而且是同一题在本仓库第二次被考**）—— **embedding 模型 vs reranker = Bi-Encoder vs Cross-Encoder**：区别在**输入方式（分开各编一次 / 拼成一条一起编）和输出类型（向量 / 标量分数）**，**不在预训练目标**。会顺着追「**那个分数是模型自带的还是你们建的**」——答案是 cross-encoder 顶上的**打分头**，用相关/不相关文档对训出来的偏序
12. **能力该做成 skill 还是工具**（三面新增，✅ 全场答得最好的一段）—— **skill / prompt 是建议，模型可以不听；「一次不做就等于系统失效」的能力必须做成带硬校验的工具**
13. **知识源怎么抗过期**（三面新增，✅）—— **文档只写「在哪能找到答案」，不写「答案是什么」**；易变事实从代码现读（后台每 3 小时拉一次代码），**只有稳定的元信息才进文档**

### B. 后端八股线（财经 / 广告中国 / 广告国际化，按出现次数排序）
1. **缓存三大问题 + Redis 内部** —— 击穿/穿透/雪崩、删除复杂度（按数据类型）、跳表为什么不用红黑树、内存淘汰策略、大 Key
2. **Java 并发集合** —— ConcurrentHashMap JDK1.7 vs 1.8、桶为什么是 2^n、扩容时 ForwardingNode 协助迁移
3. **MySQL B+ 树 + MVCC + 索引失效** —— 范围查询、最左前缀、回表与覆盖索引
4. **操作系统底层** —— 国际广告这条线偏爱：虚拟/物理内存映射、TLB、缺页、多级页表、CPU 负载 vs 利用率
5. **TCP/HTTPS/NAT** —— TLS 握手 RTT、CA 数字签名、NAPT 端口映射
6. **消息队列不丢不重** —— Confirm 机制、本地消息表、死信队列
7. **限流熔断 + 链表线程安全** —— 滑动窗口/令牌桶/漏桶、链表删除要锁 prev + cur
8. **RAG 项目链路追问** —— 多语言 query refine、混合检索、增量 embedding、reranker

### C. TikTok 方向考察重点

1. **502 排查 SOP（六步法）** —— 看 Nginx error.log upstream 错误 → 直连验证上游 → ss 看连接状态分布 → ss -lnt 看 Recv-Q 是不是 accept 队列满 → 修配置（超时不要离谱大、调 backlog/somaxconn、启用 keepalive）→ 资源治理
2. **浏览器输 URL 全流程** —— 解析协议域名 → DNS（缓存→hosts→根→TLD→权威）→ TCP 三次握手 → TLS（1.2 两 RTT / 1.3 一 RTT）→ HTTP 报文封装（TCP/IP/MAC 头）→ 网卡/交换机/路由器转发 → 服务器解封 → 浏览器渲染
3. **TCP/HTTPS 全套** —— 三次握手为什么不能两次（防历史连接 + 同步初始序列号 + 避免资源浪费）、四次挥手、滑动窗口、超时/快速/SACK 重传、慢启动/拥塞避免/快速恢复
4. **Linux 性能排查工具链** —— top（load avg / us / sy / wa / id）/ vmstat（r / b / wa / si/so / bi/bo）/ iostat（%util / await）/ free -h（available / swap）/ iotop / strace / netstat
5. **零拷贝** —— mmap（共享 buffer 节省一次 CPU 拷贝）/ sendfile（内核态搬运）/ sendfile + DMA scatter-gather（真正零拷贝，2 次上下文切换 + 2 次 DMA）
6. **CPU load vs 利用率** —— load 包括 R + D（不可中断睡眠 IO 等待）；利用率不高但慢 → 看 wa、b 队列、外部依赖
7. **海量数据 top-K** —— 1 亿条 IPv4 找出现最多 top-K（hash + 小顶堆 / 桶排 / 分治）
8. **K8s + nginx + Service** —— 流量调度算法、为什么用 K8s

> **决策树这套能不能沉淀成 skill？** 出处 [[资料/面经/字节/中国商业化/字节商业化AgentInfra三面_2026-08-14]]（✅ 全场最好）
> 「**可以，但它不一定会调**——我们实测就有不生成决策树的情况，**而我们要求所有任务都必须生成**。所以做成**工具 + 硬校验**：生成回答前必须先有树，树的节点必须填完整。」
> 收口成一条原则：**「大部分时候做了就行」的能力放 skill；「一次没做就等于系统失效」的能力必须放成带校验的工具。** 判据是**漏一次分支，用户拿到的是看起来很有道理的错答案，而且他察觉不了——这种错误比报错危险**。

> **BM25 为什么能发现文档里那些很少出现的词？** 出处 [[资料/面经/字节/中国商业化/字节商业化AgentInfra二面_2026-08-06]]
> **稀有性来自 IDF，是跨文档统计的**——整个语料库里包含这个词的文档越少，权重越高，**跟它在当前这篇里出现几次无关**。三块拆开记：**IDF 决定这个词值不值钱；TF 决定这篇提了几次（有饱和，提 10 次不值 5 次的两倍）；长度归一化防止长文档靠篇幅堆词频**——注意**文档越长得分越低，方向别说反**。
> 用在 RAG 里的收口：手册里的型号、错误码、参数名 IDF 极高，**而这正是 dense embedding 最弱的地方**——500 token 压成一个向量，这几个词的信号会被主体语义稀释掉。

> **写一个 agent 的 context manager：可以一直 add_message，get_context 要同时满足 max_token 和 max_turn。** 出处 [[资料/面经/字节/中国商业化/字节商业化AgentInfra二面_2026-08-06]]
> 三个必须主动说出来的点：①**`add_message` 不做淘汰**——存储和呈现是两件事，历史要全留，限制只作用在喂给模型的那一份 ②**一轮 = 从一条 user 消息到下一条 user 消息之前的全部消息**（中间可以有任意多条 tool call），所以数轮只能**从尾往前扫、遇到 user 就 +1** ③⭐**必须整轮丢弃，不能丢半轮**——半轮会留下没配对的 `tool_result`，OpenAI 和 Anthropic 协议都会直接报错。**这第三点是「不知道就一定写错」的分水岭。**

> **ConcurrentHashMap 桶数量为什么是 2 的 n 次方？** 出处 [[资料/面经/字节/中国商业化/字节跳动中国商业化一面面经]]
> 三个原因：①位运算取模快（hash & (length-1)）；②保证元素均匀分布（length-1 全 1，hash 每位都参与）；③扩容迁移高效（看新增高位是 0 还是 1，要么留原位要么移到原位+旧容量）。不是为了减少哈希冲突——减少冲突要用大质数。

> **十个进程同时跑，虚拟内存和物理内存怎么映射，会冲突吗？** 出处 [[资料/面经/字节/国际商业化/10.13 字节 国际化广告 后端]]
> 不同进程的不同虚拟地址可以映射到同一物理地址（共享库 / 文件页缓存 / 共享内存 / fork COW / 零页），不冲突。每个进程有独立页表，MMU + TLB 做翻译，缺页时由内核分配物理页框并更新页表。

> **Redis 删除一个 key 的时间复杂度？** 出处 [[资料/面经/字节/国际商业化/面经记录_国际商业化创业_3.9]]
> 物理删除，按数据结构：String O(1)；List/Hash/Set O(N) 遍历释放；ZSet O(N·logN)。生产删大 Key 用 UNLINK 异步释放，避免阻塞主线程。

> **外部访问 URL 出现 502 该怎么排查？** 出处 [[资料/面经/字节/TikTok/SRE/TT SRE 牛客]]
> 先确认是哪一层返回 502，再按错误日志、直连上游、连接状态、accept 队列和配置排查；完整命令见 [[Linux与IO模型#10. 502 排查 SOP]]。本场直连验证还包括用 `journalctl` 查进程日志。

> **CPU 利用率不高但系统就是慢，怎么排查？** 出处 [[资料/面经/字节/TikTok/SRE/TT SRE 牛客]]
> 时间花在"等"上：top wa（iowait）高、进程 D 状态多 → 磁盘 IO；vmstat r/b 队列、si/so 换页、bi/bo 块设备读写；iostat %util > 80% / await > 50ms 看磁盘；iotop 看谁在大量读写；free -h 看 swap；strace -p 跟踪系统调用；netstat 看 TCP 是否大量 SYN-SENT/TIME-WAIT/CLOSE-WAIT 等外部依赖慢。

> **redis 做点赞缓存如何避免数据不一致？** 出处 [[资料/面经/字节/TikTok/SRE/TT SRE 牛客]]
> 先更新 MySQL 后删除 Redis：MySQL 写入 >> Redis 删除耗时，正常并发下读请求很难在写完前后那段间隙旧值写回。如果先删后更新反而更容易不一致——MySQL 写入慢，期间读请求会把旧值写回。删除失败兜底：依赖 TTL 过期 / 消息队列重试 / 订阅 binlog + MQ 重试。
