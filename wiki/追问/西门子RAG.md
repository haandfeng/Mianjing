# 西门子RAG

## 一句话介绍
西门子 CT 机操作文档智能问答系统（学城），重构 ETL + 多路混合检索 + 重排，准确率 76% → 92%，嵌入吞吐 ×2。

## 项目级 STAR 自陈
- **S（场景）**：进组时已有基于 LangChain Chat 的基础 RAG（Elasticsearch + 单链路检索 → 喂给 LLM 回答），上游开源框架停止维护，效果不达标，无评测体系。
- **T（目标）**：搭评测流水线 → 重构 ETL/embedding 流水线 → 提升回答准确率到可上线水平。
- **A（动作）**：1）基于 LangSmith 搭测试流水线（200+ 中英文标准问答），跑出基线 76%；2）重写 ETL（XML→Markdown 表格嵌套处理、增量更新、多模型适配），换 BGE-M3 → 千问3，迁移 ES→Milvus 支持 4096 维；3）批量 + 异步 embedding 提升吞吐 ×2；4）Query Refine（多语言改写）+ 三路混合检索（千问3 稠密 + BGE-M3 稀疏 + BM25）+ Reranker（BGE-M3 / RRF）；5）按机型元数据 filter 隔离不同设备文档。
- **R（结果）**：准确率 76% → 92%，相关度/忠实度均 99%+，已上线学城，月访问几千次。

### Q2: 评测系统怎么做？怎么确保 LLM judge 可靠？
**出处**：[[小红书产品工程师一面面经]] · [[小红书产品工程师二面面经]] · [[蔚来CICD组AI agent实习生一面面经-详细版]] · [[Shopee DB Infra 北京平台实习面试问题总结]] · [[Bing图像视频业务实习一面面经]] · [[蔚来/蔚来一面RAG深挖|xhs]]

**答题骨架**：
- 测试中心提供 200+ 问题（中文 180+、英文 90+）+ 标准答案
- 三个维度：correctness（与标准答案一致）、relevance（与问题相关）、faithfulness（忠于检索文档，无幻觉）

- LangSmith 存储测试问答 + trace 整条链路（每节点入参/返回/耗时），失败 case 反查具体哪一段链路的问题
- 数据安全顾虑：LangSmith 走外网有出境风险，正式上线考虑字节扣子等内部部署方案

### Q3: Embedding 模型怎么选的？为什么从 BGE-M3 换千问3？
**出处**：[[小红书产品工程师一面面经]] · [[蔚来CICD组AI agent实习生一面面经-详细版]] · [[Shopee DB Infra 北京平台实习面试问题总结]] · [[蔚来/蔚来一面RAG深挖|xhs]] · [[面试问题总结]]

**答题骨架**：
- 定位瓶颈：跑完测试看具体哪些问题答不出来 → 发现核心问题是相关文档检索不到
- 典型 case：问题多两个字 embedding 偏移严重，BGE-M3 稠密向量在长文段里识别不到一两个关键词，多语言术语对齐能力差
- 选型依据：HuggingFace embedding 榜单，千问3 在 8B/32B 规模霸榜前三，国产、可本地部署
- 千问3 dense 4096 维 vs BGE-M3 dense 1024 维；ES 最大 1024 维放不下 → 迁移到 Milvus
- 最终上线：千问3（稠密语义） + BGE-M3（稀疏向量）双模型并用

### Q4: 为什么换向量库？ES vs Milvus
**出处**：[[Shopee DB Infra 北京平台实习面试问题总结]] · [[蔚来CICD组AI agent实习生一面面经-详细版]] · [[Bing图像视频业务实习一面面经]] · [[面试问题总结]]

通用对比表（最大维度、稀疏向量支持、HNSW vs FLAT）见 [[技术主题/RAG优化全链路]] 第 4-5 节。

**项目里换库的直接触发原因**：千问3 dense 4096 维超过 ES 上限 1024。顺带把 BGE-M3 sparse + BM25 也搬到 Milvus 同一表，按机型元数据 filter 隔离不同设备文档。索引选 HNSW 对比 FLAT 全量扫，延迟降低 80%。

> 🔴 **口径必须加限定词（2026-08-06 订正，字节二面被追过）**：
> - 「ES 上限 1024」**是我们当时那个版本的上限，不是 ES 的固有限制**——**ES 8.11 起 `dense_vector` 上限就是 4096**。说的时候必须带「**我们当时那个版本**」，否则对方只要知道新版本，这条理由当场作废。
> - 「ES 不支持 sparse」**是错的**——ES 有 `sparse_vector` 字段类型（ELSER 用的就是它，8.8 起），**8.9 起还支持 RRF 融合 BM25 与向量结果**。
> - **所以真正站得住的理由要换成**：要做三路召回加融合，**Milvus 对稀疏是原生倒排、对 BGE-M3 这类同时出 dense+sparse 的模型有现成适配**，一套 API 完成。**并且主动承认 ES 也合理**——栈里本来就有 ES 的话，少维护一个组件的价值往往大于向量库那点性能优势。

### Q5: 混合检索怎么设计？为什么不只用稠密向量？
**出处**：[[小红书产品工程师一面面经]] · [[小红书产品工程师二面面经]] · [[Shopee DB Infra 北京平台实习面试问题总结]] · [[蔚来CICD组AI agent实习生一面面经-详细版]] · [[老虎国际一面面经（资讯组）]] · [[Bing图像视频业务实习一面面经]] · [[面试问题总结]]

**答题骨架**：
- 出发点：问题里只有两三个专业术语，在长文档里出现稀疏，纯稠密会被整篇语义稀释
- 三路：千问3 稠密向量（语义） + BGE-M3 稀疏向量（既有语义又有关键词权重） + BM25（纯关键词，IDF + 文档长度归一化）
- 都走 Milvus 一套表，按机型元数据 filter
- 没用更重的多向量方案：算力和工程成本高，混合检索性价比够

> 🔴 **被追到底会问「BM25 为什么能发现那些很少的词」（字节二面，2026-08-06 答反了）**：
> **稀有性来自 IDF（逆文档频率），统计范围是整个语料库**——包含这个词的文档越少，权重越高，**跟它在当前这篇里出现几次无关**。
> 三块拆开：**IDF 决定词值不值钱 / TF 决定这篇提了几次（有饱和，提 10 次不值 5 次的两倍）/ 长度归一化防止长文档靠篇幅堆词频**。
> ⚠️ **别说成「在长文档里只出现一两次所以分高」——长度那一项方向是反的，文档越长同样词频得分越低。**

> ⚠️ **「三路召回」现在要带一句负结果，否则会被问「那第三路带来多少提升」**：
> **实测 BGE-M3 那一路稀疏几乎没有增量**——真正扛事的是 dense + BM25 加重排；而且后来换成千问 3 的 embedding 之后 BGE-M3 不再用，这一路自然废掉。
> **正确讲法是把负结果讲成决策依据**：「**召回路数不是越多越好。** 每多一路，query 侧就多一次编码、多一次检索、多一份要融合的分数；**收益取决于这一路补的洞跟已有的路重不重合**——learned sparse 补的洞跟 BM25 高度重合（都是词面匹配，只是多了 term expansion），所以在 BM25 已经在的情况下增量很小。**如果重来我会先做这个消融再决定选型**，而不是先按能力选了库、再发现那个能力用不上。」
> ❌ **别用「没有意义」收口**——那是把一次有价值的消融讲成了一次失败。

### Q6: Reranker 怎么选？大模型 rerank vs RRF
**出处**：[[小红书产品工程师一面面经]] · [[Shopee DB Infra 北京平台实习面试问题总结]] · [[面试问题总结]]

**答题骨架**：
- 测过两套：千问3 reranker（10 文档加 2 秒）、BGE-M3 reranker（30 文档 2 秒）、RRF 算法（毫秒级）
- 最终上线 BGE-M3 reranker：本地部署，30 取 10 容错率高
- RRF 缺点：把"只在某一路出现且排名靠后但实际是答案"的文档排到 10 名开外，准确率下降
- 大模型 rerank 准确率最好但耗时长，leader 不满意，所以也保留 RRF 选项

> ⚠️ **口径统一（2026-08-14 字节三面的说法更清楚，以后按这个说）**：**同样重排 30 篇，千问3 要 6 秒、BGE-M3 要 2 秒**（两场数据其实一致：千问3 约 0.2 秒/篇、BGE-M3 约 0.07 秒/篇，**三面用同一个文档数对比更不容易被绕**）。**跑分差距不大，目标文档一般都能排进前三前五** —— 所以选了快的那个。

### Q6b: 🔴 embedding 模型和 reranker 到底有什么区别？那个「分数」是哪来的？

**出处**：[[公司/字节/中国商业化/字节商业化AgentInfra三面_2026-08-14]]（🔴 答成「一个词语接龙、一个词语填空」）· [[公司/其他/贝壳/贝壳找房一面面经]]（2026-03-12 已考过同一题，**当时也没答清楚**）· [[公司/腾讯/微信事业群/腾讯WXG后端实习一面]]

> 🔴 **这是本仓库唯一一道「同一题在两家公司都答崩」的题，而且中间隔了五个月。** [[公司/字节]] 画像的第一段就标着字节爱追这个。**它不是冷门题，是已经点名的必考题。**

**❌ 错误口径（本人两次都往这个方向答，别再说）：** 「一个训练时做词语接龙、一个做词语填空」——**这是 GPT vs BERT 的说法，跟这道题无关，而且事实上也不成立**（见下面第三条证据）。

**✅ 定稿三段：**

**① 区别在输入方式和输出类型，不在预训练目标**

| | **embedding 模型 = Bi-Encoder（双塔）** | **reranker = Cross-Encoder（交叉编码）** |
|---|---|---|
| **怎么喂** | query 和文档**分开各编一次**，两次前向互不相干 | query 和文档**拼成一条**一起编，attention 让两边 token 直接交互 |
| **吐什么** | **一个向量** | **一个标量分数** |
| **能不能离线预算** | ✅ 文档向量提前全算好存向量库 | ❌ 分数依赖 query，**只能在线现算** |
| **一次查询几次前向** | **1 次**（只编 query），检索靠向量库做近邻搜索 | **N 次**（每个候选一次） |
| **精度从哪来 / 丢在哪** | 全篇压成定长向量，**细节必然丢** | token 之间不压缩地交互，**所以更准** |

**收口**：**两者不是替代关系，是流水线的两站**——Bi-Encoder 从百万级里粗筛（快但糙），Cross-Encoder 对几十条精排（准但贵）。

**② 分数是模型自带的，不是你建的，也不是从 embedding 算出来的**

- **结构上**：cross-encoder 编码完之后，**顶上接一层线性层（打分头）把整条输入的表示压成一个数**，再用 sigmoid 映射到 0~1。**embedding 模型没有这一层，所以它只能吐向量吐不出分。**
- **训练上**：喂 (query, 相关文档) 和 (query, 不相关文档)，**要求前者分数更高**。所以这个分数是**训出来的偏序，不是几何上的相似度**——这也是它比余弦相似度准的原因。
- **接回自己的架构**（这句才是加分项）：**三路召回（BM25 / 稠密 / 稀疏）各有各的分数，量纲不同、不能直接比大小**。reranker 的意义是**把三路候选拉到同一把尺子上重量一遍**，所以它放在三路合并之后，而不是每路各自截断。

**③ 一条自带的证据，专门堵「是不是 BERT vs GPT」这个追问**

> 「我们两个模型都用过：**BGE 家的 embedding 和 reranker 都是 XLM-RoBERTa 底座（填空式预训练）；千问3 家的 embedding 和 reranker 都是 Qwen3 底座（自回归、接龙式）**。**同一家的两个模型底座是一样的**——所以决定谁做召回、谁做精排的，**从来不是预训练目标，是怎么喂输入、吐什么出来**。」
> <!-- 来源: Qwen3 Embedding 技术报告 arXiv:2506.05176（decoder-only + [EOS] last-token pooling；reranker 走 yes/no token 的 logit）· BAAI/bge-reranker-v2-m3 模型卡（XLM-RoBERTa 底座 · cross-encoder · sigmoid 映射到 [0,1]）・ 查证于 2026-08-14 -->

### Q6c: 那 reranker 排 30 个文档为什么要好几秒？（🔴 三面答成纯推测）

🔴 **当时的答法**：「我理解是自己部署的问题，用 Ollama 部署、底层走 llama.cpp，没用好 GPU……**为什么这么慢我是推测的，我当时也没想过怎么提高**。」——**推测代替定位，而且最后半句是白送的减分。**

**✅ 定稿三段：先算账 → 再列候选原因 → 再说怎么区分它们**

1. **先算账**：重排是 cross-encoder，**30 篇就是 30 次独立前向**，每次输入是 query 拼一篇约 500 token 的文档。6 秒 / 30 = **每篇 200 毫秒**——**问题不是某一步特别慢，是 30 次串行前向的累加。**
2. **三个候选原因**：① **模型体量差一个量级**（千问3-reranker 有 0.6B / 4B / 8B 几档，BGE-reranker-v2-m3 在六亿参数这一档，**3 倍加速跟参数比大致对得上，这条基本可确认**）② **没做 batch**——30 个 pair 一次送进去 GPU 一次前向就算完，逐条调 API 等于把 GPU 当串行 CPU 用 ③ **部署框架**——Ollama 这类工具是给单请求交互式场景用的、不合并请求，vLLM 这类为吞吐设计的会自动攒 batch。
3. **怎么定位**：只看两个数——**GPU 利用率是不是压不满**、**实际 batch size 是不是 1**。「这两个数我当时没测，**如果重来我会先测再决定是换模型还是换部署方式，因为换小模型是拿精度换速度，batch 化是白捡的**。」

> 💡 **术语（C 档，讲之前先立）**：**前向（forward pass）**= 把一条输入从头过一遍模型得到输出，**推理耗时 ≈ 前向次数 × 单次前向成本**；**batch（批）**= 把多条输入拼成一摞一次送进模型，**GPU 算一条和算一摞耗时差不多**（瓶颈在把权重从显存搬到计算单元），所以不 batch 等于闲置大部分算力。

### Q7: Embedding 效率提升 2 倍怎么做的？
**出处**：[[快手一面面经]] · [[阿里云消息团队一面面经]] · [[小红书产品工程师二面面经]]

**答题骨架**：
- 原来串行：一个文档发服务器 → 等返回 → 下一个，同步阻塞
- 改为 batch + 异步：批量发文档做 embedding，异步拿结果分批落库
- 利用 Ollama 等部署框架自带的异步 API
- 增量更新：每篇文档唯一 ID，相同 ID 覆盖，支持单文档删除/更新，避免全量重建
- 文档量大时一次全量要 1-2 小时，全量主要发生在新机型/新数据表初始化，日常多为政策更新增量

### Q8: 持续高频涌入文档（钉钉知识库场景），怎么近实时不丢不漏？
**出处**：[[阿里云消息团队一面面经]]

**答题骨架**：
- 用消息队列把 ETL 各阶段解耦：Queue1（待解析）→ 解析 workers → Queue2（待嵌入）→ Embedding workers → Queue3（待落库）→ 落库 workers → Milvus
- Queue1 只放 `{doc_id, action, ts}`，worker 自己拉文档、转 Markdown、切片
- Queue2 用 prefetch_count 攒批 32 条 + 超时 200ms，批量推理
- 不丢：生产者 confirm + queue/message durable + 消费者手动 ACK + doc_id+chunk_index 幂等 + 死信队列兜底
- 近实时：监控每个 Queue 积压量，目标端到端秒级
- 入口瓶颈不仅 embedding 服务器，S3 拉文档 + 转 Markdown 同样需要扩容

### Q10: 多语言（中英文术语 gap）怎么解决？
**出处**：[[小红书产品工程师一面面经]] · [[小红书产品工程师二面面经]] · [[Bing图像视频业务实习一面面经]] · [[老虎国际一面面经（资讯组）]]

**答题骨架**：
- 文档主体中文，用户习惯混用英文专业术语，embedding 模型对术语翻译/对齐能力有限，数据量也不够做专项微调
- 工程方案：让小模型对问题做改写，生成 5 个左右中英文不同表达版本，一起送去检索
- 代价 ≈ 1 秒延迟，但解决专业术语歧义性价比高

### Q11: 为什么用 RAG 而不是封装成工具让大模型选择性调用？
**出处**：[[蔚来CICD组AI agent实习生一面面经-详细版]]

**答题骨架**：
- 我们的 RAG 用了工具调用，但检索知识库这一步是写死必调的
- 选择性调用风险：模型可能"应该调但没调"产生幻觉
- 医疗行业准确性 > 效率，宁愿延迟高一点也要保证答案来源可追溯
- 实际效果：不相关问题模型会回答"无法从已有知识里获取相关回答"，可接受
- 温度设 0：医疗行业对准确性、幻觉、法律风险要求极高

### Q12: 自部署模型 vs 闭源 API？模型选型对比
**出处**：[[阿里云消息团队一面面经]] · [[蔚来CICD组AI agent实习生一面面经-详细版]] · [[Shopee DB Infra 北京平台实习面试问题总结]] · [[蔚来/蔚来一面RAG深挖|xhs]]

**答题骨架**：
- 数据是医院数据，公司规定开源模型自己部署
- 测过 LLaMA 70B、ChatGPT OSS 20B/120B、千问 36B、DeepSeek 671B、Gemini
- LLaMA / Gemini 中文表现差，无法理解中文专业术语
- 最终用 DeepSeek 671B：参数量最大，中英文都好，符合开源要求
- API 提供商对比：DeepSeek 官方/硅基流动稳定 + Structured Output 好；腾讯云不稳定

### Q13: 长上下文/多轮对话怎么处理？
**出处**：[[Bing图像视频业务实习一面面经]] · [[蔚来CICD组AI agent实习生一面面经-详细版]]

**答题骨架**：
- 简单 summary 压缩：达到 10 轮对话做一次 summary，作为新 prompt 上下文
- 单轮约 5000 token，10 轮约 5 万 token
- 我们当时优化目标主要是单轮问答质量，不是多轮会话能力
- 复杂 Agent 系统涉及长期记忆/短期记忆/大文档处理/TOKEN 超限/异常处理，是后续要补的

### Q15: 如果做外包付费版，怎么进一步优化？
**出处**：[[面试问题总结]]

**答题骨架**：
- 架构层：Agent Loop + 自适应 Query Rewriting（检索→评估→改写→再检索的迭代循环）
- 检索层：Embedding 领域微调 + 优化 chunk 策略（语义/滑动窗口/层次化）+ GPU 加速多向量
- 生成层：上下文压缩 + LongContextReorder + CoT/ToT
- 动态 RAG：高质量问答入库做长期记忆，相似问题命中历史答案
- Graph RAG：实体关系建图，多跳推理

### Q16: 和 LangChain / LangGraph 的关系
**出处**：[[Bing图像视频业务实习一面面经]] · [[蔚来CICD组AI agent实习生一面面经-详细版]] · [[面试问题总结]]

**答题骨架**：
- LangChain/LangGraph 帮做 workflow 状态管理和编排，底层数据库/SDK 调用很多时候自己直接调（封装文档不完善）
- LangChain：组件库 + 简单链式调用，适合快速搭建
- LangGraph：图编排 + 状态管理，支持长流程、可恢复、可回溯、human-in-the-loop
- 复杂生产系统通常自己控制底层实现
