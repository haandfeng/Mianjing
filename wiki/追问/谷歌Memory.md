## 两分钟口语稿

**① 背景（20 秒）**
「组里在全面接入谷歌内部类 Claude Code 的 agent 框架，做 Pixel 的 Agentic Test System。它跟 code agent 最大的差异是要**通过 API 真实操作手机、读真实结果**，相当于 agent 的『阅读网页』变成了『操作设备』。我负责 memory 方向。」

**② 现有系统怎么工作（60 秒——这段讲深，证明你吃透了）**
「现有 memory 是通用插件，两条生成路径：一条是**对话主题结束时**，AI 自动起一个后台 agent 总结对话生成记忆——严格说不算主从关系的 subagent，就是个用户无感知的后台任务；另一条是 **dream 机制**，每天凌晨 4 点定时任务把全天对话汇总成记忆片段。

记忆本身是 **skill 形态**——title 加 description 的固定格式。写入时的合并逻辑相当于一次小型 RAG：拿新记忆的 description 跟存量做**语义相似度检索取 top 5**，候选给模型细读，由模型决定合并、新增、还是矛盾冲突就删除。单条限制 2000 token 防膨胀，条数不限。

它记的是用户偏好和泛泛的成功经验——对 testing 业务场景不适配，这就是我的切入点。」

**③ 我的设计（40 秒——诚实标注「正在做」）**
「目标是 **self-evolve memory**：让 agent 从测试的成功/失败轨迹里自动沉淀教训。设计上对标微软 **SkillOpt**——**把 skill 文档当成可训练参数：模型冻结不动，训练的是那份自然语言文档；每次编辑必须严格提升一个留出验证集的分数才被接受，否则回滚。** 跟通用 memory 的关键差异是**打分维度**：提取记忆时不只按语义相似度，还按这条经验的**历史成功率**联合排序——一条经验被引用后任务成败会回填到它的分数上。

进度上很诚实：轨迹数据还没就绪，我现在在推这一步。」

**验证计划的落地细节（上海 AI Lab 一面新增，被问「怎么验证 Memory 插件到底有没有用」时用）：**
> 「分两步：**先测试提升幅度**——用手上约 200-300 条已精标的数据，对比接入 Memory 插件前后的效果，测试维度两项：agent 生成的操作 step 跟标准流程在语义上是否一致、按这些 step 实际操作真机能否达成目标。**再做持续回归**——全量数据要连真机测、单条耗时长、容易中断，跑不完，所以挑约 20-30 条 golden 子集，配一个每日定时任务，在每次 Memory 改写后自动跑一遍这 20-30 条，持续监控有没有退化。**这是资源受限下的真实取舍**：不是不想测全量，是真机测试的时间成本不允许。」

### 🔴 讲这个项目的最大风险：它还没做完（上海 AI Lab 一面实证）

**可量化的翻车证据**（同一场面试，同一个人，相邻两段）：

| | 字数 | 「可能/我觉得/打算/大概」 | 面试官反应 |
|---|---|---|---|
| **谷歌段** | 1637 | **14 个** | 零追问，直接换话题 |
| **字节段** | 1584 | **2 个** | 「OK，可以，**不错不错**」 |

同样长度，模糊限定词密度差 7 倍，面试官反应差一个档次。**问题不是项目没做完，是讲述方式让它听起来像「还没想清楚」。**

**固定三段结构（讲任何「还在做」的项目都用这个）：**

> **① 已经定死的判断**（完成时，**每条必须带判据——为什么选 A 不选 B**）
> **② 已经准备好的验收手段**（带具体数字：多少条数据、测哪两个维度、多久跑一次）
> **③ 唯一还没验证的那个假设**（一句话，**并且明说为什么它现在还不能有结论**）

落到本项目：

> 「做完的和没做完的我分开说。**已经定死三件事。**
> 第一，现有插件的机制我吃透了，也做过取舍判断——它只做了程序记忆、没做情景记忆，对通用 coding 助手够用，**但测试的价值恰恰全在情景那一半**。
> 第二，架构定了：**叠一层而不是改 prompt**，判据是要不要结构性字段变更——打分、引用计数、淘汰标记装不进 title+description。
> 第三，验收方案定了：两三百条精标做接入前后对照，测两个维度；挑二三十条 golden 配每日定时回归。**挑子集不是偷懒，是真机单条耗时长、容易中断。**
> **没做完的只有一件**：轨迹数据还没就绪，那道留出集门禁现在是设计不是实测。这是我当前第一优先级。
> 我不想说成已经有结论——**这套东西的全部价值就在那道门禁上，门禁没跑过就没有结论。**」

> **自检可量化**：练的时候录一遍，数模糊词，**每 1500 字超过 2 个就重录**。
> **底层原理**：面试官考的不是你把功能做完了没有，是**你有没有做出过判断**。把进度的计量单位从「做完几个功能」换成「定死了几个判断」，一个没上线的项目照样是满分素材。

> 📌 **SkillOpt 事实核对（口径已修正，别再用旧版）**
> ⚠️ 本页早期写的「经验生成 / 技能提取 / 技能消费三段式」**不是 SkillOpt 的原文表述**，是当时的概括，被追问会露馅。**以下为查证后的口径：**
> - 项目：`microsoft/SkillOpt`，定位是**给冻结 LLM agent 训练可复用自然语言 skill 的文本空间优化器**，产出物是一份可部署的 `best_skill.md`
> - 循环六步：**rollout → reflect → aggregate → select → update → evaluate**（rollout = 带着当前 skill 跑一次完整任务并给轨迹打分）
> - 更新方式：优化器模型把打过分的成功/失败批次变成**有界的 add / delete / replace 编辑**，作用在单一 skill 文档上
> - **门禁（最该讲的一点）**：一次候选编辑**只有严格提升 held-out 验证分才被接受**；配套还有文本学习率预算、被拒编辑缓冲区、epoch 级慢更新
> - 数字：GPT-5.5 上直接对话 +23.5 / Codex 循环内 +24.8 / **Claude Code 内 +19.1**；6 benchmark × 7 模型 × 3 harness = 52 格全部最优或并列最优
> - **SkillOpt-Sleep**（2026-06-15 preview）：**给本地 coding agent 的夜间离线自进化伴侣**——回看历史会话、重放重复任务、把过了留出门禁的 skill 固化下来。**这是「dreaming 定时任务」的现成对标物，被问「业界有类似的吗」直接引用。**
>

> 🔴 **消融结论口径（2026-08-06 新增——阿里星一面把这段说反了一半，被追出处会翻车）**
>
> 那场的原话是「什么学习率啊可能是没有特别有效果的……**不管怎么样最重要的是 verify 门禁，别的都不太有用**」，还把名字说成「**Skill Up**」并自陈"我忘了"。**论文的实际结论是「门禁和更新幅度都关键」，不是只有门禁关键：**
> - **textual learning rate（文本学习率）是关键的**——它是**每一步允许改多少条编辑的预算**（一次最多 add / delete / replace 几条），是「学习率」在文本空间的类比。消融显示**有界更新明显优于无界重写**，`L_t = 4` 最优
> - **validation gate + rejected-edit buffer 是核心稳定器**——buffer（**被拒编辑缓冲区**）把没过门禁的候选存下来，让优化器下一轮知道"这些方向试过、被拒了"，避免反复提同一个坏改法。**去掉 buffer 最多掉 4.6 分**
> - 所以正确的收口是：「**每次改写都有腐化风险，所以既要有门禁把关，也要限制单步改动幅度——两个一起才稳。**」
> - **名字和归属必须报准**：`SkillOpt`（不是 Skill Up），**Microsoft Research**（arXiv 2605.23904，2026-05）。⚠️ 这一点尤其重要，因为讲的时候它常跟 **ReasoningBank（Google Research，arXiv 2509.25140）** 挨着出现，**读错名字会被听成同一家**
>

> 📌 **ReasoningBank 口径（同场也说得偏松）**
> 阿里星那场说的是「轨迹成败的分类**其实并没有多大影响**」。**更准的说法是：成败判定用的是 agent 自判（self-judged），不需要 ground-truth 标注，这一点不构成瓶颈；而且失败经验本身就是有价值的一半**——论文的核心主张就是**从成功和失败两侧蒸馏出策略级记忆，效果优于只存成功轨迹的做法**（配合 memory-aware test-time scaling 最高 +34.2% 相对提升、交互步数 −16%）。
> **别说成「成败分类无所谓」**——那会被理解成"标注质量不重要"，跟论文主张是两回事。
> <!-- 来源: ReasoningBank arXiv 2509.25140 + Google Research 博客 ・ 查证于 2026-08-06 -->

**一句话把自进化讲清楚（字节那场缺的就是这句）：**
> **普通 memory 只有写入；自进化 memory 有写入 + 打分 + 回滚。单位从「一轮对话」变成「一条完整轨迹」，裁决者从「模型自己」变成「留出验证集」。**

**④ 方案空间（30 秒——被问「为什么这么做」时的弹药）**
「架构上有两个候选：**方案 A，叠加一个独立的 testing memory 层**在通用插件之上；**方案 B，直接改通用插件的 prompt** 让它偏向记 testing 相关的东西。判断标准是**要不要结构性的 schema 变更**——如果只是『记的内容偏向 testing』，B 最快，零新组件；但 self-evolve 需要成功率打分、引用计数、淘汰机制这些**结构字段**，通用插件的 title+description 格式装不下，所以主案是 A，B 可以当快速验证的 MVP。A 的额外好处是不跟上游插件耦合——它升级不影响我，我也能独立评测回滚。」

### D2: 有分层结构吗？长短期？类别？（🔴 字节那场连着两个「没做」开局）

**铁律：「没有」必须讲成「取舍」，且先讲为什么，最后才讲没有的那个。**

- **长短期为什么没分**：短期记忆就是会话上下文本身，长期是落盘 markdown。**分层的收益要到「短期条目多到需要筛选进长期」才出现**；现在用**离线批处理**绕过了——每天凌晨的 dreaming 任务把全天记忆 merge / 删除 / 改写，**用一次批处理代替了实时分层管理**，写入量不大时这更省。
- **类别为什么没分**：所有记忆都是同一形态（title + description 的 skill 文档），只按业务**分组**做隔离，而且要人为在配置文件里划。
- **用认知心理学那套词给它定位（C 档术语，先立定义再用）**：
  - **工作记忆** working memory = 当前会话上下文，会话结束就没
  - **情景记忆** episodic = 「什么时候发生过什么」，按时间戳索引的经历
  - **语义记忆** semantic = 「什么是什么」，脱离时间的事实
  - **程序记忆** procedural = 「怎么做一件事」，**skill 文档就是它的一种实现**
  - → **所以这套系统「只做了程序记忆，没做情景记忆」——这是取舍不是空缺。** 对通用 coding 助手够用，**对 testing 不够**：测试的价值恰恰在「这个坑我上次在什么环境下踩过」这类带时间的具体经历。
- **收尾必须接到自己的设计**：self-evolve 要给每条经验挂成功率 / 引用计数 / 淘汰标记这些**结构字段**，title + description 装不下——**这就是主案选「叠一层」而不是「改 prompt」的判据：要不要结构性 schema 变更。**

### D4: 什么时候写 memory？（⚠️ 字节那场漏了 dreaming——上一题刚讲过）

**按谁触发分两类，四个时机：**
- **在线（用户会话驱动）**：① 一轮任务闭环时 agent 自主写入（写入规则注入在 system prompt 里，它也会主动问用户要不要记）② 用户显式调管理 skill（如进新仓库跑 `init`）③ 用户指出某条记忆有问题，触发定向改写
- **离线（定时任务驱动）**：④ 每天凌晨 4 点 dreaming 任务，把全天对话汇总重组

> **一句话讲清分工：在线写的是「这次学到了什么」，离线做的是「这些天学到的该怎么合并去重」——前者管召回，后者管精度。**

### D5: 新旧 memory 冲突怎么办？（🔴 字节那场答成「不是我做的，不清楚为什么」）

**现状**：靠 agent 在离线合并时自己判断矛盾，合并成一条，不问用户。
**我的诊断**：把「哪条对」完全交给模型的主观判断——**模型判断新旧是不可靠的**（两条都写着「应该用 X 方式」，它看不出哪条是三个月前的）；合并完原始两条都没了，**错了回溯不了**。
**我会怎么改（两件事，都不需要模型判断）**：
1. **合并不删除，只标失效**——每条挂「何时成立 / 何时被取代」的时间区间，冲突时把旧的标 expired 而非物理删。可回溯，且**新记忆后来被证伪时能滚回去**。
2. **裁决用系统字段**——写入时间、来源可信度（用户显式指定 > agent 自己总结）、作用域（项目级 > 全局级）。**模型只负责「发现这两条矛盾」（语义任务，它擅长），不负责「判定谁赢」（事实任务，它不擅长）。**

> 💡 **业界三条路线（C 档，讲的时候带一句）**：**覆盖式**（Mem0：LLM 查重查矛盾，最新的赢，旧的改写或删掉——**证据链断了**）／**双时间戳失效**（Zep / Graphiti：每条事实带 `valid_at` 何时成立、`expired_at` 何时被取代、`invalid_at` 何时被明确否定，**不删只标失效**，机制最强）／**确定性优先级**（不问模型哪条新，用系统直接可读的字段排序裁决）。2026 年的共识是**别让模型自己判断新鲜度**。
> <!-- 来源: 社区技术博客 + arXiv 2606.01435《Don't Ask the LLM to Track Freshness》・ 查证于 2026-07-31 ・ Mem0/Zep 机制为二手来源，未读源码 -->

### D6: 用户写一句「以后每次都这样称呼我」，会污染上下文吗？（⚠️ 字节那场结论是对的，缺的是把条件讲成机制）

> 📌 **2026-08-14 订正**：本条原来写的是「结论下反了，正确答案是『这个例子正好是会污染的那种』」——**那条订正本身下重了。**
> 当时的原话「如果你不是直接改描述、或者描述里面有这么简单直接的一个操作，我觉得它是不会污染的」，**逻辑上是成立的**。缺的不是结论，是①没说正面判据②没说哪个环节决定它落在哪层。

**判据只有一条：指令内容本身有没有进常驻层。** 不是「这条记忆的主题是不是无条件偏好」——**同一条记忆落在哪一档，取决于抽取器写 `description` 时写的是主题还是内容。**

| `description` 抽成 | 常驻层里是什么 | 污染吗 |
|---|---|---|
| `用户的称呼偏好` | 一个**主题标签**，模型看到它不会改称呼 | ❌ 不污染。要等它判断相关、去读正文才拿到内容 |
| `用户希望被称为「XX」` | **指令内容本身** | ✅ 每轮注入，检索这道过滤器完全绕过 |

**所以两档污染是这么分的：**
- **正文层——影响有限**：常驻上下文的只有**标题 + 描述**，agent 判断相关了才去读正文。写进正文的怪东西**只在语义相关的 query 上被召回**，检索本身就是过滤器。
- **描述层——真问题**：描述是常驻的 = **每轮都注入**，等于永久改写 system prompt。
- **而且它是持久的**：提示注入只污染当前会话，**写进 memory 的每轮都复现，写入时间和发作时间可能隔几个月**，极难归因。

> ⚠️ **不要断言「无条件偏好必然被写进描述」。** 这条推理站不住——「description 只写主题、正文才写内容」是完全可行且常见的实现，这条偏好照样生效且不污染常驻层。**面试时要说的是「在我们这套实现里判据是 X」，不是一个普适断言。**

**反例（证明污染路径由实现决定，不能从「该不该常驻」推出来）**：[[Agent记忆四家实现对比]] §2.4 里 DeerMem 的 `guaranteed_categories: ["correction"]`——**触发无条件注入的是「被归类成 correction」，跟 `description` 写了什么无关。** 换一个实现，攻击面就换一个位置。

**防线（写入侧拦，不在检索侧拦）**：① 描述字段按注入风险审——**不允许在描述里写祈使句式的行为指令**（「以后每次都要……」），这类要么降级到正文、要么走显式用户配置 ② 常驻描述给总 token 预算，超了强制淘汰，防慢性膨胀 ③ memory 是本地 markdown、人可见可改——**这是这套设计最大的优点，出事时人能直接看到是哪一条**，比藏在向量库里强很多。

> 💡 **正式名字（C 档）**：**memory poisoning（记忆投毒）**——往持久记忆层写入误导内容，使 agent 在**之后每一次**交互都行为错误。**与 prompt injection 的区别是时间尺度：后者只影响当前会话，前者持久、且攻击与发作解耦。** OWASP 2026 年列为 Agentic AI Top 10 的 **ASI06「Memory and Context Poisoning」**，2026-06-01 发布 Agent Memory Guard 参考实现（拦截每次读写，做注入筛查 / 密钥与 PII 泄漏检测 / 键篡改检测 / SHA-256 完整性基线 / 体积异常五层）。
> <!-- 来源: OWASP 官网 + Help Net Security 报道 ・ 查证于 2026-07-31 -->

### D7: 这个 memory 怎么交付给用户？

一个**插件**。装完之后：① 在对应 root 路径写入 memory 操作说明（markdown）注入给模型，让它意识到 memory 存在 ② 装一批管理 skill ③ 注册定时任务 ④ 起一个专门的后台层管理 memory 相关 agent，**不影响主 agent 流程**。

### D8: 内部 agent 统一迁到公司框架，怎么理解？

两种暴露方式：**① 暴露成 skill**——把原 agent 的 system prompt 注入进去，让框架理解并模仿它的行为；**② 当 subagent 调**——像调工具一样把 agent 起起来，做完返回结果。
> ✅ **讲这段时拿对方熟悉的系统做锚点**：在字节面试里用 DeerFlow 类比，一句话省三句背景。**这个动作要保留。**
> 💡 **术语（C 档）**：面试官用的 **agent runtime**（agent 运行时——负责循环调度 / 工具注册分发 / 上下文拼装 / 状态持久化的那一层，不是模型也不是业务逻辑）**跟快手面试官全程用的 `harness` 是同一层东西的不同叫法，两个词要能互换着用。**

### D9: 你的 memory hook 挂在 agent 生命周期的哪个点？这个系统还支持哪些 hook？（🔴 字节二面断在这里，四次「没考虑过」）

🔴 **第二问断了**，而且这是**自己项目的说明书，不是课外知识**。

**Claude Code 的 hook 事件清单（公开对标物，2026-08-06 查证），按生命周期报：**

| 位置 | 事件 | 能不能拦 |
|---|---|---|
| 会话开始 / 结束 | `SessionStart` / `SessionEnd` | 只能注入上下文 / 只能做副作用 |
| **用户输入提交后、模型调用前** | **`UserPromptSubmit`** | ✅ 能拦；**memory 注入走的就是这里的 `additionalContext`** |
| 工具调用前 | **`PreToolUse`** | ✅ 能拒绝，**还能改写工具入参** |
| 工具调用后 | **`PostToolUse`** / `PostToolUseFailure` | ✅ 能拦，能改写工具输出 |
| 并行工具批次结束 | `PostToolBatch` | ✅ 能拦 |

| **一轮回答结束** | **`Stop`** | ✅ 能拦——可以判定「你还没干完，接着干」 |
| 上下文压缩前 / 后 | **`PreCompact`** / `PostCompact` | 压缩前能拦 |

**⭐ 收口必须给出设计判断，而不是背清单：**

## 高频追问 Q&A

### Q1: 主题结束是怎么判断的？（⚠️ 星河觉醒答崩点一号，已修复）

**三段式话术（通用机制 → 我的判断 → 声明边界）：**

1. **通用机制三类信号**：**显式结束**（用户主动关会话 / 明确说完了）、**空闲超时**、**上下文切换检测**（新 query 与当前主题 embedding 距离超阈值）。实际系统一般组合使用：显式优先、超时兜底、语义漂移补充。
2. **我们场景的判断（具体信号，内行味在这句）**：testing 场景的天然边界是**代码提交**——agent 发起一个 commit 就意味着这轮任务闭环、主题结束；再加**对话静止超过 1 小时**做超时兜底。语义漂移检测在这个场景用不太上，因为任务边界本身够清晰。
3. **声明边界（一句，不重复）**：框架内部具体用哪种组合我还没读到那段源码。

> 反面教材：银河一面连说三次「没研究过 / 不是我们做的 / 我刚加入」——一次是诚实，三次是防御。

### Q2: 语义相似度怎么实现/存储的？（⚠️ 答崩点二号，已修复）
- 通用骨架必须出口：**embedding 模型把 description 向量化 → 存储（向量库或内存索引）→ 余弦相似度 top-k 检索**
- 再声明「内部封装的具体选型待确认」——先给骨架再声明边界，跟 Q1 同一套话术结构

### Q3: 成功率怎么归因？一条经验被引用、任务成功了，怎么知道是它的功劳？（设计思路，如实说还没实现）
- 设计：检索命中的经验 ID 记录进轨迹 → 任务结束按结果**回填计数**（引用且成功 +1 / 引用且失败 -1）
- 归因噪声用平滑处理：单次成败不定生死，Beta 先验 + 计数更新，引用次数多了分数才收敛
- 冷启动：新经验给中性先验分，靠语义相似度先上场，用成功率慢慢分层
- 结尾要说：「这是我当前的设计，归因的因果性确实是难点——严格说只能拿到相关性，所以用平滑和大数弱化单次误判」（主动说出局限 = 加分）

### Q4: 新旧经验矛盾怎么办？
- 复用通用插件已有的冲突处理路径：合并判断时模型检测矛盾 → 冲突时优先保留高成功率的一条，低分的标记淘汰
- （这是设计推演，被追问就说「沿用现有合并框架，加打分作裁决依据」）

### Q5: 为什么不直接用 RAG 检索历史轨迹，还要提炼成 memory？
- 轨迹是原始数据，长且噪声大；memory 是**蒸馏后的教训**——检索单位从「几千 token 的轨迹」变成「一条 200 token 的经验」，命中率和上下文成本都优一个量级
- 跟 SkillOpt 的 skill extraction 同理：轨迹 → 结构化技能文档，不是轨迹直接进上下文

### Q6: 为什么用 subagent 做总结？
- 后台任务、用户无感知，必须另起执行流；严格说无主从关系，就是后台 agent（星河觉醒实战中主动纠正术语，效果好，保留这个答法）

### Q7: 你的评测集是怎么构建出来的？（✅ 字节二面全场最好的一段，定稿保留）

**核心方法论：别去建评测集，去找「人本来就在做修正」的地方。**

以 **CI/CD 失败分类 agent** 为例，闭环四步：
1. 后台每天抓取一批 CI/CD 错误，自动跑 agent，让它判断失败原因、给 bug 分类、提单给对应的组
2. 对应工程师收到单——**分类对就不动，分类错就把分类改掉**
3. **这个修正动作本身就是人工标注，等于金标准，且零额外成本**
4. 保留 CI 的 **commit id**，可以还原当时的场景重跑，把结果跟标注比对

> ⭐ **两个必须说出来的点**：① **「用 commit id 还原场景」保证了评测可重放**——否则每天的错误都不一样，跑分之间没有可比性 ② **这类「自然标注信号」的边际成本接近零，而且会随业务自动增长**，比任何人工标注集都更值得投入。

**第二个数据集（description-to-test agent）及其取舍**：自然语言描述 → 测试步骤 → 操作真机。两个维度打分：**生成步骤与标准答案的语义相似度** + **是否真的达成测试目标**。
**但它被搁置了，理由要讲成取舍**：要连真机 → 学生权限抢不到设备、有网络波动、耗时长、**不可复现**。**评测集的第一属性是可重放，不是真实**——所以改用离线数据集跑分。
> 💡 **「shadow 数据集」这个词要么当场立定义，要么别用**：把线上真实请求复制一份到不影响用户的旁路环境跑，只记录结果。**输入分布跟线上一致，但没有人工标注，只能做新旧版本的相对比较，不能算绝对准确率。**

**（旧）定稿三段：具体场景 → 诚实划线 → 证伪计划**

> 「**实测数字我现在给不出来，评测流水线刚搭起来，我不想编一个。** 但我可以给一个非常具体的、我们真实会遇到的场景，也是我做这件事的直接动机：
>
> **典型 badcase 是『同一个环境坑反复踩』。** 比如某类设备上某个测试必须先关掉某个后台服务才跑得通——**通用 memory 记不住这件事**，因为它是按用户偏好和通用经验设计的，而这条经验**既不是偏好也不通用，它是「这个测试 × 这类设备」上的一条具体教训**。结果就是每换一个人、换一个会话，agent 都要重新踩一遍，白花一整轮试错。
>
> **这类经验恰恰最该被记住**，因为它有三个特征：**复现率高、代价大、而且有客观对错**——测试通没通过是明确信号，不需要人判断。
>
> **我要验证的假设很明确**：把这类带环境条件的失败教训沉淀下来，**同类任务的首次通过率应该上升、平均交互步数应该下降**，这两个指标在 CI 数据集上都能直接算。
> **我也想好了怎么证伪**：如果加了之后分数不涨甚至掉了，说明沉淀出来的是噪声不是经验——**那要改的不是 memory 的结构，是沉淀的粒度。**」

### 🆕 Q8b: 通用 memory 接进来之后到底有没有用？（2026-08-14 字节三面首次报出实测结论）

> ⭐ **这是二面 Q8 那道题的真答案，而且比「有改善」更值钱，因为结论是反直觉的。** 从此这题不要再答「还在 develop」。

**实测结论（评测场景：CI/CD 报错分类 agent，判断失败原因 → 分类 → 提工单，测的是分类准不准）：**

| 指标 | 结果 |
|---|---|
| **准确率** | **没有提升**——在 baseline 的波动范围内上下波动 |
| **turn 数 / tool call 次数** | **明显下降** |
| **latency / 输入输出 token** | **明显下降** |

**机制解释（这段才是重点）：**

> memory 沉淀出来的东西**退化成了「关键词 → 结论」的硬映射**——见到某个关键词就判某类错误。
> **对的时候**：模型不用读完整个报错就能直接分类，**省下的正是推理那部分开销**。
> **错的时候**：模型**同样不会去读完整的报错**，因为它已经不看原始输入了。
> **所以「省 token」和「判错」是同一个机制的两面。**
> 一句话收口：**它现在更像 hard code——给你一套规则让你跟着走，代价是降低了模型的思考。**

**由此改变的方向**（讲完结论必须接这段，否则听起来像在说自己项目没用）：

> 「所以我现在的判断是：**memory 在这个场景里的价值是降本，不是提效。** 我要做的事情因此也变了——**不是让它记更多，是让它记的东西不要替模型做决定。**
> 具体在试的方案是**把 memory 从『结论型』改成『线索型』**：不写『见到 X 就是 Y 类错误』，而写『见到 X 时优先去看某个日志段』——**保留导航价值，去掉裁决权。**
> 下一步是把『原本能答对、因为 memory 反而答错』的那些条目单独摘出来剔掉，**把 improvement 留下。**」

> 🔑 **为什么这个结论比「提升了 X 个点」更能打**：它证明了**评测这套 infra 本身的价值**——**没有这套跑分，「准确率没涨但 token 降了」这个结论根本浮不出来**，团队只会以为 memory 装上就赚了。**讲这段时一定要把这句话说出来**，它把「我的项目效果一般」翻译成了「我的评测发现了别人看不见的东西」。
