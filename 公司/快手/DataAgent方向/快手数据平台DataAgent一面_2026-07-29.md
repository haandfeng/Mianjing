## 2. 项目深挖（字节 DeerFlow）

### Q：五段实习里你最熟悉哪一段？
**当时的回答：** 字节，刚结束那段。 ✅

### Q：字节里对你来说最有挑战的是哪件事？

**当时的回答：⚠️ 答偏了**
> 「最有挑战的是——这个业务机器人不止我一个人在做，同组同学在做、前端组同学也在做，我们几个要相互对比。你要汇报给我的 leader，告诉他为什么我这个研发是有必要的、相比他们优势在哪。」
> 后半段才转到技术：前端组「**套了一个 OpenClaw 的壳**，后来改成爱马仕，没有对 agent 的行为做出改变」；后端组「只是把 skill 写上去，教 agent 怎么做工作」；而我「真真切切对 agent 的行为做了大量改进」，能跟 Codex / Claude Code 跑分比较且在业务场景下更好。

**⚠️ 三个问题：**
1. **问的是技术挑战，答成了组织竞争。** 开场 30 秒给面试官的印象是「这人觉得最难的是搞定人」。后半段虽然救回来了，但第一印象已经形成。
2. **「套壳」这个词评价同事的工作有风险。** 面试官会想：他以后会不会这样评价我们团队？技术上的差异化可以讲，但要讲**我做了什么**，不要讲**他们没做什么**。
3. **浪费了一个送分题。** 「最有挑战」是让你自选战场展示深度的题，我却选了一个没有技术含量的战场。

**改进后的回答（选一个真正的技术难题，且带取舍）：**
> 「技术上最难的是**怎么让模型把所有业务分支列全**。
> 我们的业务是多个状态叉乘的——达人玩法状态 × 订单付款方式 × 国家维度，逻辑纠缠在一起。模型在几十轮代码探索之后，注意力被稀释，明明代码已经在上下文里，最终总结时还是会漏掉分支，给一个『看起来很有依据但以偏概全』的答案。**而且它很自信，不会说自己不确定。**
> 难点在于：**这不是模型能力问题，换 Opus 也一样偷懒。** 我做过对比实验，强模型反而更容易提前收敛——找到一个看起来 OK 的答案就返回了。
> 所以我的解法是**把『完备性』从模型的主观判断变成系统可检查的客观状态**：要求它在生成答案前，先把每个分叉显式写进一棵决策树，每个节点必须标注来源代码文件。然后加一道门禁——**如果这次会话没有调用生成决策树的工具，直接打回重做。** 准确率从 56% 到 87%，主要就是这一步带来的。」

> **铁律：「最有挑战」= 自选战场展示技术深度，永远选技术题，永远不选人际题。**

### Q：能简单介绍一下 DeerFlow 整体架构？你二次开发的主要内容是什么？

**当时的回答（清楚）：** ✅
- 本质是一个 agent 框架，外面套了 IM（即时通讯）壳，把飞书消息转发进 agent
- 原始 agent 很基础：用户问题进来 → 推理 → 有工具调用就调用、把结果返回给 agent → 没有工具调用说明是纯文本输出，结束循环
- 我做的两件事：①在这个粗浅的 ReAct 逻辑上加了**决策树功能 + 校验门禁** ②从**单 agent 变成多 agent**

### Q：为什么要多 agent？单 agent 满足不了现在的业务场景吗？

**当时的回答（好，两个理由都具体）：** ✅
- **理由一：状态叉乘导致以偏概全。** 业务场景复杂，达人玩法状态 × 订单付款方式 × 不同国家逻辑相互叉乘，逻辑非常多且纠缠在一起。单 agent 难以从用户一个粗浅的问题里把所有情况考虑清楚或排除在外，结果是以偏概全的错误回答。**有一部分原因是用户问题本身没问好**——没把限定条件提出来。所以我们希望模型生成完回答后，能**有理有据地反问用户**到底特指哪些方面，让他限定范围。
- **理由二：长程注意力衰减产生幻觉。** 多轮思考、多轮工具调用之后，因为看的文件比较多，会出现 attention 能力不足。**代码它看到了、也在上下文里，但最终总结的时候会把逻辑总结错。** 所以加 review agent，出现这种情况就打回给生成 agent 重新生成。

### Q：ReAct 循环越多、上下文加载越多，碰到上下文膨胀 / 超限怎么处理？

**当时的回答（好，有真实踩坑）：** ✅
- 我们场景下较少遇到：用 GLM 系列模型，上下文 200K，且一般是单轮对话
- 最简单粗暴是做一轮 **summary**（把历史压缩成摘要）。但我实测踩过坑：**模型没配好、上下文空间调小了 → 自动触发 summary → 代码被大量精简 → 最终生成结果完全错误，有遗漏、逻辑线也错了**
- 所以真正用的是：上下文快爆时把**工具调用的结果 offload（卸载）到本地磁盘**，只告诉 agent「你要的信息在磁盘哪个位置，需要时再读」

⚠️ **口误**：现场说的是「上下文有 200M」，应为 **200K token**。数量级说错在面试里会被记一笔。

### Q：通用做法是 summary，但每个模型压缩完结果不一样、也可能丢失原意。**怎么让压缩过程能提取到关键信息、更符合原意？**

**当时的回答：⚠️ 散，且大量不确定**
- 提到用 skill 的方法（说了一个叫「gremlin store」的东西，**这个名字在转录里存疑**），思路是「给它 structure、给符合业务场景的要求细节，通过框让压缩有一定逻辑」
- 提到 Codex 的做法：只是简单让 agent summary，但它是内部请求、结果加密看不到，可能用了内部特制模型
- 提到 Claude Code 的做法：多级门禁、工具级 context 管理、对特定工具内容裁剪、修改内部 prompt 把工具信息掩盖掉
- 中间说了「**我忘了它具体有什么样的一些逻辑**」

> ⚠️ **问的是方法论（怎么压得好），我答的是别人的实现（Codex/Claude Code 怎么做的）。** 举例子不等于给判断框架，而且举的例子自己还不确定。

**改进后的回答（三层，且都能落地）：**
> 「压缩一定是有损的，所以关键不是『压得多小』，而是**决定什么绝对不能丢**。我会分三层做：
>
> **① 不做自由文本 summary，做结构化压缩。** 自由 summary 的问题是模型自己决定什么重要，每次决定还不一样。改成给一个固定的槽位表让它填——比如：**已确认的事实（含来源文件和行号）/ 已排除的分支及排除理由 / 待验证的假设 / 下一步动作**。这样丢掉的是叙述过程，保住的是事实和状态。**槽位表是我定的，不是模型定的，这就把不确定性收敛了。**
>
> **② 分层保留，不是分层丢弃。** 原始工具输出（比如整份代码文件）offload 到磁盘只在上下文里留一个索引，需要时按路径重新读。**被压缩的只有叙述层，事实层一直是可回溯的。** 这是我在字节实际用的方案。
>
> **③ 压缩要可验证。** 压完之后跑一个反向检查——让另一个 agent 只看压缩结果，回答『这个任务已经确认了哪些事实、排除了哪些分支』，跟压缩前的记录对一遍。**对不上就说明这次压缩丢了东西，回退重压。** 这比事后发现答案错了再排查便宜得多。
>
> 一句话：**压缩不该是让模型『自由复述』，而是让它『按表填空』，再验一遍表填没填对。**」

### Q：准确率 56% → 87% 是怎么测评的？测评过程中怎么保证**不重不漏**？

**当时的回答（打分环节答得有结构）：** ✅
- 数据集：前端组做的 ~50 道常见问题，每题给评分标准，**像阅读理解题**——答出 A 点得 1 分、答出 B 点得 1 分，总分 3~5 分，除以总分归一
- 流程：脚本一道道发给 DeerFlow → 收集回答 → 回答 + 评分标准一起放进内部的类 LangSmith 评分系统 → 用 GPT 系列模型打分（选它是因为语言能力好）
- 保证分数可靠：①**分点评分**（不是整体印象分）②**每题跑三次取平均**（耗时久，所以三次）③**每次回答 review 五遍取平均**（review 快，可以多跑）

**⚠️ 问题：答的是「打分稳不稳」，没答「测试集全不全」。** 面试官问的「不重不漏」指的是**覆盖度**——所以他紧接着追问了下一题。

### Q（追问）：你验证的都是核心、常见问题。**不常见的就不验了吗？**（举例：业务常关注 GMV，那其他指标、其他场景呢）

> 💡 **术语补**（数据领域词，我的背景里没有）：**GMV**（Gross Merchandise Volume，商品交易总额，电商最核心的规模指标）、**ROI**（Return on Investment，投入产出比，投放场景的核心指标）。**面的是数据平台，这类指标词要能张口就来。**

**当时的回答：** 可以验，对问题进行分类、分数据集——关注 GMV 的一类、关注 ROI 的一类，每类分别跑测试，拿到每类的分数和总分，就能看到不同方向的能力。

**⚠️ 两个问题：**
1. **答的是「可以这么做」而不是「我们这么做了」**——面试官听到的是设想，不是经验。
2. **分类只解决了「已知问题的组织」，没解决「未知问题的发现」。** 把 50 道题分成 5 类，测试集还是那 50 道，长尾一道没多。

**改进后的回答（正面回答长尾覆盖）：**
> 「这确实是我们评测体系最大的短板——**50 道人工出的题，本质是『我们以为用户会问什么』，不是『用户真的问了什么』**。
> 要补长尾，我的做法是**不再靠人想题，让测试集从两个真实来源长出来**：
> **① 从线上真实 query 分层采样。** 把线上问题按频次排序，头部高频的必采，长尾按比例随机采——**长尾正是最容易错、也最没被测到的部分**。这样测试集的分布跟线上分布一致，分数才有意义。
> **② 从系统结构反向生成，用代码做覆盖率的分母。** 业务代码里有多少个玩法分支、多少个国家维度，就应该有对应的问题。**这样『漏』就从一个模糊的感觉变成了一个可计算的比例——覆盖了多少个业务分支。**
> **③ bad case 自动回流。** 用户点踩的、人工纠正过的，自动进测试集并标注正确答案，保证同一个错不会犯第二次。
> 核心是：**测试集不该是人想出来的，该是从真实分布和系统结构里长出来的。**」

### Q：DeerFlow 里也用 skill 吧？

**当时的回答：** ✅ 用得比较少。回答问题分两层——**第一层读业务文档**（文档已组装成 LLM wiki 形式，用 skill 教它怎么读、快速根据问题定位到具体代码仓库）；**第二层读代码仓库**（没有特定 skill）。

### Q：怎么提高 skill 里流程的执行命中率？（大模型不一定按你编写的流程走）

**当时的回答：✅ 这题答得最好——三层递进，且落到自己做过的真实机制**
- **第一层：能不能被触发。** 我统计过 skill 被读取的概率，确实有问题。处理两个角度——①**删掉无关的 skill、或整合成工具**，让上下文更精准 ②**在描述里写清适用范围**：什么时候用、什么时候不用、什么关键词会触发
- **第二层：内部流程能不能被执行。** 在 prompt 里用 XML 标签写清 `forbidden` 行为，**明令禁止**，能一定程度提高准确性
- **第三层：实在要保证的流程，写成 middleware（中间件，在模型和框架之间强制拦一道的代码层）。** 真实例子：决策树本来是用 skill 告诉它「生成回答前先更新决策树，把所有可能性写清楚」，但它有时候不听、直接把答案生成出来，漏掉这一步。**后来我在它生成回答前加了一道校验——检查这轮有没有调用生成决策树的工具，没调用就打回重做，并在 prompt 里告诉它漏了哪一步。这样能 100% 避免流程遗忘。**

> ✅ **「从提示到强制」的三层结构 + 落到自己项目 + 给出「100%」的强判断，这是全场最好的一段。记住这个模式。**

### 🔴 Q【本场分水岭】：假设流程是「① 取数据 → ② 用 pandas 分析 → ③ 给结论」。实际执行中会出三种问题——**模型跳过分析那一步**；**给假分析**（它结合上下文以为之前分析过了，拿上一次的结果直接返回）；**每次分析结果都不稳定**（你不知道它 pandas 到底怎么算的）。**有什么工程化的办法解决？**

**当时的回答：⚠️ 三个方案被连否两次，面试官两次追问「还有别的思路吗？有没有一些工程化的思路呢？」**

| 我给的方案 | 面试官的否定 |
|---|---|
| ① 用 **workflow** 把流程固定下来（不用 skill） | 「workflow 有什么问题吗？」→ 我答「太固定了」→ **「灵活性很差。100 个场景要写 100 个，泛化场景里不可行。」** |
| ② 起一个 **subagent 在旁边监督** | **「生产环境很少用。一是费 token，二是用户体感会非常差——要等它监督完再返回。」** |
| ③ **structured output + human in the loop**（谷歌内部 testing 工具的做法：多层 skill 叠加，一个 skill 一个 workflow，中间人工确认再路由到下一个） | （没有正面否，但面试时间到了）**——需要人工介入，本身就不叫「工程化自动解决」** |

> 🔴 **最致命的一点：正确答案我上一题已经说出来过了。**
> 上一题我刚讲完「**skill 不听话 → 就在生成回答前加一道校验，检查有没有调用那个工具，没调用就打回重做，100% 避免流程遗忘**」——这就是「跳过分析步」的标准答案，我却没有把它迁移过来。
> **知识是有的，取不出来。这是三场复盘里反复出现的同一个模式。**

**改进后的回答（三个症状 = 同一个根因，逐个给工程化解法）：**

> 「这三个症状看起来不一样，**根因是同一个：我们把『过程』也交给了模型自述，而模型的自述是不可信的。**
> 工程化的方向就一句话：**把关键步骤从『模型说它做了』变成『系统能观测到它做了』。** 三个症状分别对应三个抓手：
>
> **① 跳过分析步 → 不靠 prompt，靠门禁校验。**
> 分析必须通过一个真实的代码执行工具产生（sandbox 里跑 pandas），这次工具调用在 trace 里是有记录的。**在返回结果之前拦一道：这轮会话里如果没有这个工具的调用记录，直接打回重做，并告诉它漏了哪一步。** 这个我在字节做过——决策树那道门禁就是这么加的，能 100% 杜绝流程遗忘。**成本是零额外模型调用，就是一个 if。**
>
> **② 假分析（复用旧结果）→ 给结果和输入做强绑定。**
> 每次分析产出的时候，带上一个**内容指纹**——就是把「这次的输入数据」和「这次执行的分析代码」各算一个 hash 拼起来。返回结果时校验指纹跟本轮输入对不对得上，对不上就是复用了上一轮的结果，拦截重做。**模型可以撒谎说自己分析了，但它伪造不了一个跟本轮输入匹配的指纹**，因为指纹是系统算的不是它写的。
>
> **③ 结果不稳定 → 把分析代码从『每次现写』沉淀成『固定算子』。**
> 不稳定的根因是分析代码是模型每次临时生成的，同一个需求它能写出五种写法。解法是：**第一次让模型写，写完校验通过之后，把它固化成一个带参数的函数注册进工具库**——比如 `计算同比环比(表名, 指标列, 时间列, 粒度)`。以后同类分析直接调这个工具，**模型只决定『调哪个、传什么参数』，不再决定『怎么算』。**
>
> **而且第三点正好回应您刚才对 workflow 的批评**——workflow 的问题是把整条流程写死了，100 个场景要写 100 条。但**固化『算子』不一样：算子是可组合的，流程还是让模型自由编排。** 我锁的是每一步的确定性，没锁流程的灵活性。这个粒度我认为是对的。」

> **⭐ 思想总结（可迁移到任何「模型不可控」的题）：**
> **能用代码校验的，不要用 prompt 请求；能沉淀成工具的，不要让模型每次现写；能让系统观测的，不要信模型的自述。**
> 三层成本递增、灵活性递减：**prompt 提示（免费、不可靠）< 门禁校验（一个 if、100% 可靠）< 算子固化（要开发、锁死行为）**。按需要的确定性选层级，**不要一上来就跳到 workflow 或 subagent 这种最贵的方案。**

### Q：DeerFlow 是 harness 架构，在 harness 工程里怎么降低大模型幻觉？

> 💡 **术语**：**harness**（承载 agent 运行的外层工程框架——管上下文拼装、工具注册、循环控制、校验门禁的那一层，不是模型本身）。这个词面试官全程在用，**是这个团队的核心词汇**。

**当时的回答（好，有自己的实践）：** ✅
- **来源强制引用**：决策树每个生成的节点都要写「为什么列这个节点、它的来源是哪里、从哪个 source file 的什么代码推导出来的」
- **最终强校验**：每个节点都必须写来源，存在不写的情况就提示它补完再生成答案
- **总结两点**：①让模型**根据代码或文档回答**，而不是凭记忆回答，幻觉率会小很多 ②**控制 context 长度**——上下文太长很容易出幻觉，所以 harness 一个重要工作是「怎么给它尽可能少的上下文，同时还能回答这些问题」

### Q：你主要用什么语言？我看之前项目也有用 Java？
**当时的回答：** 现在主要 Python，最早的项目用 Java。 ✅

### Q：DeerFlow 的记忆系统是怎么做的？

**当时的回答（好，有判断力）：** ✅
- 做得很粗糙：每轮对话结束后台起一个 subagent，把这轮 query 和回答总结成一句话记进 memory；同时把所有原始 query / answer 原封不动存进 markdown 文件
- **「后来我们没怎么用它——因为你没办法保证记忆不腐化，它记错东西怎么办？」**

> ✅ **「我们评估后没用」比「我们用了」更能体现判断力。这个理由（记忆腐化不可控）站得住。**

### Q：Claude Code 的记忆系统了解吗？

**当时的回答（大体对，但反复说「我忘了是哪一个」）：**
- ① 用户明确指令时记录（`CLAUDE.md` 也算一种记忆文档）
- ② 有一个 dreaming 模块，每天定时任务对记忆做管理和统计
- ③ 后台进程：聊天 idle（闲置）约一小时无后续对话后，起一个 subagent 对这段对话做总结，把重要信息写进 memory

### Q：它这个记忆里分短期记忆和长期记忆吗？

**当时的回答：🔴 第五次把判断权交给面试官**
> 「我印象中是没有分吧，你只要写在这个 memory 里面，都是长期的记忆。**是吧？你看是，好厉害。**」

> 🔴 **这是三场复盘里同一个毛病的第五次**（微信支付两次「是吧？你认为？」、星河一次、点点一次）。而且这次多了一句「**好厉害**」——面试里夸面试官，会被读成心虚和讨好。
>
> **改进：不确定就明确划出确定的部分，把不确定的部分交代清楚，然后停住。**
> > 「我了解到的是没有显式分短期和长期——写进 memory 文件的都按长期用，短期的部分靠会话上下文本身承载，会话结束就没了。**不过我只看过公开资料和别人的逆向分析，没读过源码，这块我不打包票。**」
>
> **铁律：不确定 → 说清「我确定什么、不确定什么、依据是什么」，然后闭嘴。永远不要用反问句结尾。**

## 3. 算法题（两道，共 ~20 分钟）

> 按仓库规则，算法只在此如实记录，不建专题——算法在另一个仓库。

### 题 1：最大子数组和（LeetCode 53，Easy/Medium）
给一个含正负数的数组，找出相加和最大的连续子数组，返回它的和。

**过程：⚠️ 从 33:49 到 42:22，约 9 分钟，绝大部分卡在推 DP 定义上**
- 一上来判断出「有正有负、要连续 → 动态规划」✅
- 然后反复自问「**怎么从前一个状态推到下一个？**」，转录里这句话出现了三次，中间有多段长时间沉默
- 39:01 才定下正确定义：**`DP[i]` = 以 `i` 为结尾的子数组的最大和**——**定义一对，递推立刻就出来了**
- 复杂度答：时间 O(N)、空间 O(N) ✅
- 面试官中途提示两次：「你的 DP 可以去掉」「你那个写错了」
- 问「有优化空间吗」→ **答对了**：只依赖前一个状态，不需要 DP 数组，用一个滚动变量，空间降到 **O(1)** ✅

> ⚠️ **这是 DP 最经典的入门题，9 分钟推定义太久。** 卡点不在算法，在**没有条件反射地先写「以 i 结尾」这个定义**。
> **子数组 / 子串类 DP，第一句永远先写「`DP[i]` = 以 `i` 结尾的 ⋯⋯」**——先写下来再想对不对，比在脑子里空推快得多。

### 题 2：子集（LeetCode 78，Medium）
给一个不重复的数字集合，返回所有子集（含空集）。

**过程：⚠️ 从 45:13 到 53:46，约 8 分钟，两个 bug 都是面试官提示后才发现**
- 方向对：回溯 ✅
- **Bug 1（起始位置）**：DFS 递归时起始下标传错，导致重复。面试官提示「**你每次 DFS 遍历的时候，是从哪个位置开始的呀？**」才发现要从 `j` 而不是 `i` 开始
- **Bug 2（引用对象）**：把当前路径 `append` 进结果集时直接放了引用，后续 `pop` 会把已收集的答案一起改掉。自己排查了约 1 分半才反应过来：「**哦，因为它是个对象，它被删了**」——需要放拷贝

> ⚠️ **Bug 2 是 Python 写回溯的头号坑，属于「知道了就永远不会再错」的类型。** 收集答案时无脑写拷贝，不要写引用。

## 5. 总结 / 自评

**✅ 答得好：**
1. **多 agent 的两个理由**（状态叉乘导致以偏概全 + 长程注意力衰减产生幻觉）——具体、有业务背景、不空洞
2. **上下文膨胀的 offload 方案**——带真实踩坑（summary 把代码压没了导致结果全错），可信度高
3. **skill 命中率三层递进**（删无关/写清触发范围 → prompt 里 XML 写 forbidden → middleware 强制校验），落到自己做的门禁并给出「100%」的强判断——**全场最好的一段**
4. **降幻觉**（来源强制引用 + 强校验 + 控制 context 长度）有自己的实践
5. **DeerFlow 记忆系统「评估后没用」的理由**（记忆腐化不可控）体现判断力
6. **反问质量高**，问出了完整的部门架构和 WAU 量级

**⚠️ 待改（按严重程度排）：**
1. 🔴 **「工程化解决模型跳步 / 假执行 / 结果不稳定」被连否三次没答出**——**而正确答案在上一题自己刚说过（门禁校验）**。第 N 次证明「知识有但取不出来」
2. 🔴 **「记忆分不分短期长期」→「是吧？你看是，好厉害」**——第五次把判断权交给面试官，且这次多了讨好

4. ⚠️ **「不重不漏」答成了打分稳定性**，没答测试集覆盖度——被追问一次才补上，且补的是设想不是经验
