## 1. 算法题（禁 AI，投屏手写，Python）

**题目：** 一次交换（从 word1 取一个字符与 word2 的一个字符互换），能否使两个字符串中**不同字符的数目相等**。→ **LeetCode 2531「使字符串总不同字符的数目相等」**，Medium。

**当时的做法（用了 23 分钟）：**
- 先想暴力枚举 O(n×m)
- 04:00 说出关键条件：「**只用小写英文字母组成**……相同的字母可以跳过，用一个 set 存看过的字母」← **核心洞察摸到了**
- 模拟交换 + 回滚，维护「试过的组合」集合
- 14:47 面试官提示「**现在这个实现有点问题**」「逻辑上出问题了」
- 16:27–17:17 自己发现并修正了一个剪枝错误 ✅
- 18:17 被问复杂度 → 答「**N 乘 M**」⚠️
- 18:31 被问优化空间 → 走了分情况讨论（diff>2 / ==2 / ==1 / ==0）的路，diff==0 分支没说完整

**⚠️ 两个问题：**

1. **摸到了洞察却没兑现成复杂度**。既然只有 26 个小写字母，要枚举的就不是 n×m 个字符对，而是 **26×26 = 676 对，是常数**。自己写了去重逻辑，被问复杂度却答 N×M——**没意识到自己的算法早就是 O(n+m) 了**。然后被问优化时走了更复杂、更易错的分情况讨论。
2. **「不确定就先放着」= 埋雷**。原话：「**算了，这个不确定的就不剪了，到时候再讨论吧**」——一分钟后自己发现那个剪枝是错的（两边 distinct 已相等时**仍必须交换一次**，交换两个相同字母可以把机会用掉，不能直接跳过）。自己修好是加分，但根因是当时选择了「先放着」而不是「30 秒验证掉」。

**改进后的回答（标准解，30 秒讲完）：**
> 「因为只有小写字母，两边各统计一个长度 26 的词频数组，O(n+m)。
> 然后**枚举 word1 出现过的字符 i 和 word2 出现过的字符 j**——最多 26×26 = 676 种，是常数。每种组合模拟交换（i 在 word1 减一、j 加一，反之同理），比较两边 distinct 数是否相等，相等返回 true，否则回滚。
> **总复杂度 O(n + m + 26²) = O(n + m)**，空间 O(1)。」

> **铁律：任何标记为「不确定」的剪枝，要么当场举例验证，要么直接不写——绝不留着。**

## 2. 字节 DeerFlow 项目深挖

### Q：从用户输入到最终结果返回的完整链路是什么样？
**当时的回答（答得好）：**
- 用户问业务问题（例：达人 A 提交视频后什么时候能收到打钱 / 审核最多几天）
- **第一步语义查找**：靠同事维护的**知识库文档**做「业务名词 → 代码名词」映射（达人 → influencer），并指明大概在哪个仓库、哪个 domain
- **快速定位仓库**（前后端共 **40 多个仓库**）
- 标准 code agent 那套：grep / glob 关键字匹配 + readfile 读代码
- **决策树**：显式提醒 agent 存在多少可能性，防止阅读过程中遗忘、总结时遗漏
- 生成答案前**强制调用决策树工具至少生成一遍**，列全才允许总结
- 答案 + 决策树发给 **review agent** 检查

### Q：为什么多 agent 编排能提高准确度？
**当时的回答（⭐ 全场最佳，主动纠正了问题的预设）：**
> 「**多 agent 编排提高准确度这方面，我觉得反倒还好**——在我的实测里，真正能提高准确度的是**决策树**，因为它能把所有情况列出来放到 prompt 最后面，让 agent attention 到，而且它像 write todo 一样在探索中不断更新，最终总结时有根据。
> 测试中所有扣分点主要源于它对**逻辑链路和用户状态流转不熟悉**导致的偏差。
> **review agent 更多是兜底机制**——实测大概 **20 个问题触发 1 次**。它有效是因为 **context 不一样**：回答 agent 探索了很多代码、上下文很长会有幻觉；给 review agent 一个干净上下文 + 只给骨架，能过滤掉不重要的上下文。」

> ✅ **没有顺着面试官的预设讲故事，给了真实因果判断 + 数据。这是前两场复盘的直接成果**（前两场在这个位置是「是吧？你认为？」）。

### Q：引入 review agent 有什么缺点 / 新问题？
**当时的回答（主动说缺点，不粉饰）：** 最大缺点是**问答时长翻倍**——没有用更廉价更快的模型做 review，为保证准确性用了同样思考强度的模型，两边都要看代码探索，**用户必须等审核完才能追问**，这是设计上的弊端。

### Q：review agent 和主 agent 用相同 / 不同模型各有什么优势？
**当时的回答：** 完全一致（含思考强度），只有 prompt 和可用工具不同（review 删掉了写文件/生成图片等无关工具和 skill）。
- **不同模型的优势**：回答用弱而快的模型 + review 用强模型 → 响应快、token 消耗少（1:1 → 用弱模型可降），有兜底保证总体准确度
- **相同/强模型的优势**：第一次就答对更 user friendly，用户看到第一次回答总是错体验不好

### Q：日常写代码用 code agent 吗？有没有模型总也改不对的情况？
**当时的回答：** 内部对比过 Claude Code / 自研框架 / Codex，最后用自研——因为**即使 Claude Code + Opus 4.8 仍会偷懒、以偏概全**（找到一个 OK 的答案就返回，不继续探索），而业务要求必须列全，所以要能**延长 agent 探索步数**，现有 code agent 没有这种设计。
- 「模型总改不对」的情况：字节用 Claude Code 还好，**谷歌用 Gemini 确实遇到过怎么说都理解不了的情况**
- 我们这个 agent 不写代码只总结代码，所以少见语义理解问题；出问题一般是**业务知识没匹配上**——例：玩法 A 没写进业务文档，agent 就会随机挑一个 A 开头的变量当成玩法 A，且**用户不管怎么纠正都改不过来**，除非明确指出对应的变量名
- **模型选型实测**：比较过 GPT / Gemini / GLM，**最终选 GLM 5.1**；**表现最差的是 GPT**——容易偷懒、工具调用次数偏少，看到差不多的答案就生成；GLM 5.1 倾向于调用很多工具

### Q：决策树和直接让大模型自由选择有什么区别？
**当时的回答：** 决策树也是大模型自己生成的，但有格式规矩——**每个节点必须是名词不能是动词**（函数名或枚举内容，不能是「A 干了 B」这种动作）；**必须给出理由和来源文档**（为什么 B、C 是 A 的子节点），这样结构更正确、也方便 review 检测。

**⚠️ 问题：答的是「决策树怎么约束」，没有正面回答「vs 自由选择」这个对比。** 面试官最后自己总结：「**你们这个决策树听起来就主要是对生成的依据进行结构化的一种方式，是？**」——**又一次面试官替我完成了回答**（同微信支付「我帮你翻译这个问题」）。

**改进后的回答（对比要正面给）：**
> 「区别在于**约束的时机**。自由选择是在**生成答案那一刻**才决定要不要提某个分支——而那时上下文已被几十轮代码探索稀释，遗漏是必然的。
> 决策树把这件事**提前并外化**：探索过程中就要求把每个分叉显式写进结构并附来源依据。这样**『有没有列全』从模糊的主观判断变成可检查的客观状态**——review agent 才有东西可查，门禁才有条件可判。
> 一句话：**自由选择是让模型自己保证完备性，决策树是把完备性变成可验证的外部状态。**」

### Q：网关适配 Gemini/Anthropic/OpenAI 多协议，为什么不能只替换请求地址？
**当时的回答（⭐ 这题分最高，三个具体理由 + 数据）：**
1. **参数名不同**：内部网关提供不同模型、协议不同（GLM 走 Anthropic 协议、Gemini 走 Gemini、GPT 走 OpenAI）。开启思考的参数名不一样（OpenAI 是 `reasoning effort`），**config 解析不对、参数没传对 → 模型根本没思考**，能力被削弱。**内部有文章验证大概 10%~15% 的性能损耗**
2. **Gemini 的 signature**：想让它持续做 ReAct 式多轮工具调用，**必须显式回传一个 signature 参数**（思考延续的凭据），不传直接报错
3. **prompt cache**：OpenAI 默认开启缓存，**Anthropic 协议必须显式打开相应变量**才生效

### Q：流式输出和普通响应都适配了吗？多做哪些处理？
**当时的回答：** 只做流式——框架本身是异步的，同步没意义。额外处理主要是 **Python 协程那套**：异步生成器逐块读流式数据，**I/O 时让出 CPU**。

### Q：token 在不同协议中有哪些差异？
**当时的回答：⚠️ 答崩** —「我没有对这方面额外处理……**这方面我没有仔细的去研究**，框架已经做得差不多了，具体参数变量我没有仔细去考究。」

> ⚠️ **三场里第四次出现「没细究」**（星河两次、这里一次、微信支付一次变体）。而这题**完全是通用知识**，且我做过网关适配，不该空手。

**改进后的回答（三个层面）：**
> **① 分词器不同**——同一段文本在三家的 token 数不一样，成本估算和上下文预算不能跨模型套同一系数，要各自用 count API 实测。
> **② usage 字段名和结构不同**——OpenAI 是 `prompt_tokens`/`completion_tokens`；Anthropic 是 `input_tokens`/`output_tokens`，另有 `cache_creation_input_tokens`/`cache_read_input_tokens`；Gemini 是 `promptTokenCount`/`candidatesTokenCount`。网关要统一成一套内部字段，否则上层无法核算成本。
> **③ 思考 token 的报告方式不同**——OpenAI 有单独的 `reasoning_tokens`，Gemini 有思考 token 计数，**Anthropic 没有独立字段、思考 token 直接计进 output_tokens**。这直接影响怎么监控「思考模式有没有生效」——**正好接上我自己做的思考模式适配**。

### Q：prompt cache 为什么能生效？一般缓存哪些内容？
**当时的回答（答得好）：**
- 生效原理：**前缀匹配**。基于 transformer 的线性生成——想生成 C 必须先有 A、B 的计算结果；前缀完全一致就能复用已保存的计算结果，不必重算，省计算成本和费用
- **适合缓存**：长期不变的内容——system prompt、对话历史（用户问题 + 模型回答）
- **不适合**：频繁变化的——**时间戳粒度是个坑**：system prompt 里放「某年某月某日」没问题，放「某时某分」就会让前缀完全匹配不上、cache 全失效
- 还提到：取决于 **context 管理**——先进的 harness 为保证上下文空间会删除中间的 tool message，这时要考虑删什么、怎么处理（会影响缓存前缀）

### Q：什么是事件循环？为什么跨事件循环复用连接会出错？本质是什么？
**当时的回答：**
- 事件循环定义：⚠️ **讲错了**——「相当于招待所前台，**每个线程，它会检测每一个线程是否有任务**，有任务就捞起来」。**事件循环不检测线程**，它是**单线程**的，检测的是 **I/O 就绪事件和任务队列**
- 出错原因（✅ 比微信支付那次讲得清楚）：**两套框架打架**——LangGraph 复用连接池，字节内部 SDK（日志框架）**每次日志处理结束就把事件循环关掉**，LangGraph 无感知；下个请求进来从旧连接池捞连接，绑定的事件循环已被删 → 报错
- 解决：不让它关掉事件循环，保证连接一直存活

**改进后的回答（事件循环的正确定义，30 秒）：**
> 「事件循环是**单线程**的调度中心，维护一个任务队列，同时通过 epoll/kqueue 监听一批 fd。循环体三件事：**问内核哪些 I/O 就绪 → 把就绪的回调/协程放进队列 → 逐个执行到下一个 await 点**。
> 价值是**一个线程管上万连接**——大部分时间连接在等 I/O，等的时候不占线程只占一个 fd 注册项。所以它省的是**线程栈内存和上下文切换，不是省 CPU 计算**。」
> 比喻：不是「招待所前台查房间」，而是**餐厅里一个服务员——不在某桌前干等，谁举手（fd 就绪）去谁那儿**。

### Q：一次 agent trace 还有哪些核心内容？
**当时的回答（答得好，有结构）：**
- 输入 / 输出 / 中间思考过程
- **可视化按类型渲染**：工具调用信息渲染成工具调用，文本渲染成文本
- **按时间顺序 + 主次关系**：一次 agent 循环有多次工具调用，要梳理成树（输出的子节点是工具调用及其结果）
- **元数据**：用户问题、最终 output、提问时间（方便 filter）、模型、temperature、思考强度、思考预算
- **token 明细**：每轮输入/输出/cache 各多少
- **工具与 skill 调用次数**：方便 debug 哪些 skill 没被成功调用、哪些工具没被用过

### Q：如何判断准确率提升是真的提升，而不是测试集的偶然波动？
**当时的回答（答得好）：**
- **扩大数据量**：基线推上线后收集所有真实问题 + 反馈按钮，形成数据迭代
- **多次生成**：模型回答生成 **3 次**
- **判官也多次**：LLM as judge 打分测 **5 次左右**（token 量少、耗时也少）
- **高质量精标数据集**：人工维护、**有打分要点**（像语文阅读理解，答出 A 得 1 分、答出 B 得 1 分）——框架评价迭代主要参考它；没有打分点的普通数据集主要用来**发现 bug 和问题**

## 3. Arm 项目

### Q：onCPU 和 offCPU 分别表示什么？
**当时的回答（答得好）：** 工作是量化「优化某段代码对吞吐量有多大提升」——方法是**加延时**测性能衰减，反推优化收益。加延时靠 sleep 对线程加延时，**必须在线程里跑（onCPU）**。但现代程序性能瓶颈常不在 CPU，而是 **memory 读写的 IO bound**，所以做了扩展：**测量给处于 IO 等待状态的程序加延时能带来多大性能提升**——这就是 offCPU。

### Q：同一段 CRC 代码在 ARM 和 x86 上为什么性能不同？
**当时的回答（答得好）：** CRC 是加密/校验计算单元。**ARM 芯片没有专门的加密计算单元设计**，只能用通用计算单元的 kernel 算子函数算；**Intel 有专门的硬件单元和调用它的专用函数**做加速。我们的工作就是发现这类问题反馈给硬件工程师，作为优化方向。

## 4. 概念题

### Q：ReAct 范式的基本执行过程？
**当时的回答（对）：** Reasoning → Action → Observation 循环——先推理，推理出行为并执行动作，观察环境变化，根据变化进一步推理下一步动作。

### Q：ReAct 有哪些常见问题？
**当时的回答：⚠️ 只答了一个** ——「没有终止标准，弱模型会不断重复尝试、重复工具调用形成死循环；靠 harness 框架感知到重复循环时注入 prompt 提醒」。

> ⚠️ 这是 **AI Agent 岗位的核心概念题**，只给一个点偏薄。

**改进后的回答（四类全景，且最后接回自己的项目）：**
> **① 没有全局规划**——每步只看当前观察做局部决策，容易陷进死胡同还继续挖。这正是 **Plan-and-Execute** 要解决的。
> **② 错误累积**——中间一步的错误观察污染后面所有推理，而模型倾向自洽，不会主动怀疑前面的结论。
> **③ 上下文膨胀**——每轮 thought+action+observation 全进上下文，长任务很快撑爆，且大多数信息后面用不上，所以要配 context 编辑或压缩。
> **④ 循环和偷懒两个极端**——弱模型重复调工具死循环；**强模型反而容易提前收敛**，找到看起来 OK 的答案就返回。**我在字节遇到的正是后者，所以才做了决策树强制它列全所有分支再总结。**

## 6. 总结 / 自评

**✅ 明显进步（前两场复盘的成果）：**
1. **主动纠正问题预设**（「多 agent 提高准确度这方面我觉得反倒还好，真正提高的是决策树」）+ 带数据（20 问触发 1 次 review）——**前两场在这个位置是「是吧？你认为？」**
2. **主动说缺点**（review agent 时长翻倍）不粉饰
