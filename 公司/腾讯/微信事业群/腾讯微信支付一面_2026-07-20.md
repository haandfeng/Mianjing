## 2. 题 1：手写环形队列（禁 AI，Python）

**题面：** 实现固定容量队列（C++ 描述、语言不限）：push/pop、初始化传容量。可选进阶：O(1) 复杂度、多线程正确性、close 语义、统计 push 成功/失败次数。

**当时的做法：**
- 环形数组 + `head`（头指针）+ `size`（当前长度）+ `capacity`，尾部位置 = `(head + size) % capacity`
- 中途自己举例（1~7 绕圈）发现 head 忘取模的 bug，**自己修正**（`head % capacity`）✅
- 多线程：粗粒度锁——push/pop 全加锁（Java 就 synchronized），其他函数就没有并发问题了
- close：加 `is_closed` 标志，push 时检查直接 return；pop 剩余数据仍可弹出，判断后无需改动
- 统计：成功/失败分支各加计数器
- **pop 返回值契约被追问**：泛型 template 下返回 False 会和合法值冲突 → 我答封装 Response 对象（是否成功 + 值）或约定返回空值 ✅

**head 指针被连环拆解约 6 分钟（28:18–34:48）：** 「head 设计目的是什么 / 插入时头部要不要变 / 一个头指针能否满足环形队列」——**方案（head+size）完全正确、扛住了追问**，但三个问题：

1. **用举例子论证，被明确纠正**。我讲「一开始是 0，pop 到 7 时 head 等于 6……」→ 面试官打断：「**不要按照你刚才指定的用例来讲，你按照你的代码里的逻辑来讲**」，还把 head 出现的行号（16/29/38/39）都列出来了。**例子只能证明一个点，不变量才能证明所有点**，而且举例要心算、容易讲岔。
2. **三次自我打断**（「等一下等一下」「我得再思考一下」「不对」）——内容对，听感像蒙的。
3. **第三次反问求确认**：「还有什么样的一个 bug 点吗？」（前两次是「不应该重试，是吧？」「你认为？」）

**改进后的回答：**

> **① 先给不变量（不举例子）**：「三条不变量：**head 永远指向队首元素下标**，范围 `[0, cap)`；**size 是当前元素个数**，范围 `[0, cap]`；**队尾下一个可写位置永远是 `(head + size) % cap`**。所以职责清晰：**push 只改 size 不改 head**（往尾部写不影响队首）；**pop 两个都改**（head 前进取模、size 减一）。空满直接看 size——`size==0` 空、`size==cap` 满，**不需要额外标志位**。」
>
> **② 主动对比设计空间（直接回答「一个头指针够不够」）**：「常见两种维护方式，我选 **head+size**。**head+tail** 更接近底层实现（内核 ring buffer），但经典问题是 **`head==tail` 无法区分空和满**——解法有三：牺牲一格让 tail 追不上 head、加 full 标志、或用只增不减的读写计数配合无符号溢出取差。**head+size 没有这个歧义**，代价是多维护一个字段。这题选它因为空满判断直接、不浪费容量；**如果是高并发无锁场景我会倾向 head/tail 计数**，因为两个游标可分别由生产者和消费者独占，更容易做无锁。」

> **铁律：被问「你这个设计对不对」时，答不变量，不要举例子。**

**测试用例设计（🔴 判断为本场首要挂点——面试官亲口说「没有专职测试，TDD 一定要具备」，这题他问了三轮）：**

- **第一轮**（24:37「你打算构建哪些测试用例」）：我答「**每一个 if else 判断条件我都要过一遍**」+ size=0 / close / size=capacity / 绕圈取模（1-7 一组、8-14 再一组）
- **第二轮**（26:04「具体点，比如说**异常的用例**」）：我答的还是正常剧本（pop 空→push 0~5→pop 一个→push 6,7,8 第 8 个满了返 false）→ **面试官直接打断纠正：「push 0~5 属于异常用例吗？」** → ⚠️ **我没有转向**，答「就是都返回 true 嘛」然后继续同一个剧本，还说「这大概就是把所有条件都测了一遍」
- **第三轮**（34:48，中间隔了 8 分钟）面试官把答案形状完整描述出来：「你的测试剧本**仅局限于一个单一场景**，基于你上面注释的参数上下文构建的……你觉得这个剧本就已经满足所有异常场景了？」→ 我才想到 **capacity = 0 / 负数**，并承认「我这里其实没有考虑好」
- 补充时还说了两句防御性的话：「**item 没有什么异常的数据**」「**size 不可能出现小于 0 的情况**」

**⚠️ 五个问题（一层比一层深）：**

1. **覆盖率思维 vs 契约思维（根因）**。开场句「每个 if else 都过一遍」= 以**自己写的代码**为地图。而**覆盖率思维只能找到你写过的分支里的 bug，你漏写的分支它结构上就找不到**——这题漏的恰恰是 capacity 校验，代码里没这条分支，所以永远走不到。面试官三轮追问就是在引导这个认知（第三轮「仅局限于你上面注释的参数上下文」= 你只测了你已经想到的）。
2. **混淆「异常用例」和「正常操作的边界」**。pop 空 / push 满是**边界用例**（代码有明确定义行为）；**异常用例 = 违反契约、代码没定义行为的输入**（capacity ≤ 0、close 后 push、无锁并发）。
3. **面试官纠正后没转向——比原始错误更伤**。「push 0~5 属于异常用例吗」是明确点破，我当成事实确认题答了。答错=知识缺口，接不住纠正=**实时反馈能力问题**，而这个组的质量体系就靠人和人 review 反馈。
4. **在防御代码而不是攻击代码**。「item 没有异常数据」——C++ 泛型下指针传 nullptr？重对象拷贝开销？拷贝构造抛异常时队列状态一致吗（异常安全）？「size 不可能小于 0」——我自己都说了「最好写小于等于」，说明心里知道有隐患，结论却是「应该不会」。**测试存在的意义就是验证「应该不会」是不是真的不会。**
5. **没有分层框架，只有流水意识**——说完只能讲「大概是这样」（说了两次）。**讽刺：我在字节做的就是给 agent 加决策树解决「列不全」，给 AI 装了框架，自己临场却在流水列举**（这个自嘲下次可主动讲，把弱点变觉察）。

**定稿：测试设计五层框架（任何组件通用，先报框架再展开）**

> 开场第一句：「我分五层来设计：**契约、边界、状态序列、并发、资源规模**。」

| 层 | 问自己什么 | 环形队列具体用例 |
|---|---|---|
| **① 契约** | API 承诺了什么？什么输入破坏承诺？ | capacity ≤ 0 / 非整数 / 极大值；pop 空的返回值语义（泛型下怎么区分「失败」和「合法的假值」）；push 满返回什么 |
| **② 边界** | 极值和临界点 | 空、满、capacity=1、恰好绕一圈、head 取模临界、size 0→1 与 max→max-1 |
| **③ 状态序列** | 能否走出非法态 | push 满→pop 空→再 push（验 head 复位）；close 后 push/pop；close 两次；空队列直接 close |
| **④ 并发** | 哪些操作会竞态 | 多线程交叉 push/pop 后 size 一致性；成功/失败计数器竞态；close 与 push 并发；锁粒度是否覆盖计数器 |
| **⑤ 资源/规模** | 规模与资源极限 | capacity 极大分配失败；item 重对象拷贝/移动开销；拷贝构造抛异常时的异常安全；长跑计数器溢出 |

**第一层最容易漏也最值钱**——现场漏的 capacity 校验就在这层，只能靠契约思维找到。

> **两条铁律：**
> 1. **测试设计不是「验证我的代码对」，是「假设我的代码错，去抓它」。**
> 2. **覆盖率思维找不到你漏写的分支——永远从契约出发，不从代码出发。**
>
> **战术**：面试官纠正时先出声承接再重构——「您说得对，我刚才那个理解有偏差，让我重新组织一下」。买三秒钟，且明确展示接住了反馈。

## 3. 题 2：带重试的调用封装（指定用 AI，共享屏幕）

**题面：** 实现一个带重试的下游调用封装：options（最大尝试次数、总超时、单次超时）、仅对可重试错误重试、总时间不足一次尝试时返回超时、两次尝试间休眠。

**当时的做法：**
- 直接把题目原文喂给 AI 让它实现 → **被面试官打断要求共享屏幕看过程**⚠️
- AI 生成期间被要求口述理解：参数校验（<1 返回 invalid argument）、可重试才重试、for loop、前后计时扣减 total time、指数退避休眠并扣减
- 被问「你自己要给 AI 补哪些 point」→ 事后补列了 4 点（参数违法直接返回 / 仅可重试错误重试 / 剩余时间不足一次尝试返回超时 / 休眠扣减剩余时间），并自我吐槽「平时我会用 Gemini/Superpowers 先跟 AI 讨论清楚再写，这次直接扔题不像我平时的做法」
- 测试设计被追问 → 答了 TDD（先测试再开发，「先射箭再画靶不行」）+ 用例：参数违法 / 成功立即返回 / 可重试 vs 不可重试两个假下游 / 达到最大次数返回最后一次失败 / 总时长与单次超时**故意不整除**测剩余时间分支 / 每次尝试打 log 验证指数退避
- 边界追问：`max_times=1` 还重试吗 → 答不重试，但承认「语义没说清楚，这正是要跟 AI 澄清的二义性」（面试官认可：自然语言需求有二义性，要为 AI 澄清边界）
- `kTimeout` vs `kPermissionDeny` → 超时可重试、权限拒绝不重试，按枚举分类处理
- 「AI 生成的代码如果无限重试，你怎么发现？」→ 每轮重试打 log（第几次/累计耗时/剩余预算），异常即可见

**🎯 面试官在反问环节把评分标准原原本本说了出来：**
> 「TDD 是一定要具备的，**方案设计阶段测试设计就要完备**……你要把整个测试思路——异常用例、正常用例、所有测试边界、覆盖点**全部想一下**，然后让他补充细节、你来确认，**最终代码阶段才是让他生成的**。人工在**设计端要参与、要指导 AI**。」

分工：**人（完整测试设计 + 边界澄清）→ AI（补细节 + 生成代码）→ 人（确认验收）**。**我跳过了第一段。**

**⚠️ 四个问题：**
1. **直接喂题 = 把唯一不可替代的环节外包了**（核心失分）。面试官那句「你自己有哪些 point 是需要加的」潜台词是「**你只是复制粘贴的话，我自己也能做，你的价值在哪**」。AI 时代人的瓶颈已从「写代码」转到「**验证代码**」——人剩下的不可替代能力就是**定义什么是正确**。而最可惜的是**我知道正确做法**（自己说了「平时会让他先跟我讨论」），**压力下放弃了自己的最佳实践**。
2. **10 分钟限时下取舍算反了**。AI 生成只要 30 秒，瓶颈从来不是生成，是「知道该要什么」和「知道对不对」。**前 4 分钟不写一行代码才是最优解**。
3. **测试设计第二次被拖出来**——第一题追问三轮，这题卡壳答「测试。」「测试项。」面试官只好解释什么叫基于测试做设计。**同一场同一短板出现两次，对明说「没有测试岗、TDD 是硬门槛」的团队基本是决定性的。**
4. **没主动共享屏幕**——面试官说「不然我**看不见过程**」，他要评估的**不是最终代码，是你跟 AI 交互的方式**。

**定稿：AI 协作题四阶段**

> **开场第一句（这句就能拿下大部分分）**：「我准备用 AI 了，**先共享屏幕方便您看过程**。我的习惯是**先花两分钟澄清需求边界、再列测试清单，最后才让 AI 生成代码**——因为 AI 产出的质量上限取决于我给的 spec 有多清楚，而且我需要测试清单来验收它。」

**阶段 1（2min）二义性清单——不碰 AI**（任何「带重试封装」通用）：

| # | 二义性点 | 我的决策 |
|---|---|---|
| 1 | `max_attempts=1` 是打 1 次还是打 1 次+重试 1 次？ | 总尝试次数=1，**不重试** |
| 2 | `total_timeout` 包不包含 sleep？ | 包含——墙钟预算 |
| 3 | 剩余 3s 但 `per_call_timeout`=5s 用哪个？ | **取 min**，用剩余时间裁剪 |
| 4 | 「剩余不足一次尝试」判定基准？ | 剩余 < per_call → 直接返回超时，不发无意义请求 |
| 5 | 最终失败返回哪个错误？ | 最后一次的，但**保留错误链**便于排障 |
| 6 | 退避固定还是指数？ | **指数 + 随机 jitter**，防重试风暴同步 |
| 7 | 「可重试错误」谁定义？ | **调用方注入判定函数** > 内置枚举 |
| 8 | **timeout 算可重试吗？** | ⚠️ 见下 |

**⚠️ 第 8 条：本场自相矛盾了（重要发现）**
- 本题我答「kTimeout **超时就是要重试**」
- 第三题被教育「超时状态未知，资金操作**不能盲目重试**」
- **两个答案冲突，我当时没意识到。** 统一说法：**「timeout 是否可重试取决于操作是否幂等——幂等读操作可直接重试；非幂等写操作（尤其资金）超时是状态未知，必须先查证。所以可重试判定不能只看错误码，还要看操作语义。」**
- 💡 **如果第三题结束后主动回头说「刚才第二题那个结论要补个前提」，评价会完全不同**——跨题一致性是资深标志。

**阶段 2（2min）口述测试清单**（照搬五层框架）：①契约（max_attempts=0/-1、total_timeout=0/负 → 立即 invalid argument 不发请求）②边界（max_attempts=1、剩余恰好等于一次超时、总时长与单次超时**故意不整除**）③序列（可重试失败×N 后成功、耗尽返回最后错误、首次成功立即返回不 sleep）④时间（sleep 从预算扣、指数退避打 log 验证、总耗时不超 total）⑤分类（两个假下游：一个可重试一个不可重试，验证行为不同）

**阶段 3（1min）喂 AI 的 prompt = 原题 + 8 条决策 + 测试清单**，让它先写测试再写实现。顺带：「**spec 写清楚后这任务用便宜小模型就够了**」（现场说过，是好点）

**阶段 4 验收盯三处**：①**有没有无限重试可能**（退出条件是否同时受次数和时间预算约束）②**时间预算扣减**（sleep 和调用耗时都要扣）③**错误分类**是否真按注入函数走。发现无限重试的手段：**每轮打 log**（第几次/累计耗时/剩余预算）。

**✅ 保留亮点**：`max_attempts=1` 的二义性识别 + 「语义没说清楚」——面试官当场认可并展开讲自然语言需求的二义性。**问题只在于它是被追问出的 1 个点，不是开场成体系交付的 8 条清单。**

> **一句话记忆：AI 能写代码，不能替你定义「什么是正确」。AI 协作题里你的价值 = 澄清二义性 + 设计验收标准；把这两件事交给 AI，等于宣布自己可被替代。**

## 4. 题 3：支付转账代码 review（禁 AI，C++）

**题面：** 一段转账代码（Transfer 结构含 from/to/amount、Debit 下游扣款声明、单号生成、满减逻辑、almost_equal），找逻辑问题为主，风格问题权重低。

**当时找到的点：**
1. **金额用 double 存储和比较** → 应整型存分（×100），比较和计算都不安全 ✅（面试官确认「用 int 单位是分」）
2. **from account 有效性无校验**，下游请求无错误/超时保护（try-catch 缺失）✅
3. **转账单号直接拼 from+to+金额**：不唯一（A 给 B 转两次 1 块就撞）+ 从单号能反推谁给谁转多少钱，信息泄露 ✅
4. **只有扣款没有加钱**：transfer 语义 from 扣 to 加必须同成功同失败——原子性/事务问题 ✅（面试官点头「原子性问题」）
5. 满 100 减 0.1 的 double 直接比较，同问题 1；almost_equal 存在但没被调用 ✅

**🔴 最关键的追问（绕了 4 分钟，本场第二硬伤）：「超时了，你怎么判断扣款有没有真的成功？」**

- **第一反应答错了问题**：「**看返回消息吧，他返回成功就是成功**」→ 面试官反问「**他不是超时了吗？**」⚠️ 超时的定义就是「没收到返回消息」，我却去看一个不存在的东西
- 第二次：「查账单、查数据库、对账」→ 被拒（「说的是**实时业务代码，离线的不参与**」）
- 第三次：「用幂等 ID 再发一次，**我们假设下游会告诉你已经扣过款**」→ ⚠️ **凭空假设了下游幂等**，面试官点破：「**题干里面没有告诉你 Debit 是幂等的**」
- 然后自言自语摸索：「不能查账、不能查数据库……**查什么？能有什么？**」→ 想拿 ID 查余额 → 自己否掉（并发下分不清哪单）
- 面试官只好**整段翻译问题**：「接口幂等性未知 + 又是资金操作，超时未决下他的策略是？」
- 我：「**不应该重试，是吧？……你认为？**」⚠️ **把判断权交给面试官求确认**
- 最终答对：Timeout 与 Busy 走不同逻辑，忙可立即重试，Timeout 要等足够时间后先查询再决定 ✅（方向和结论都对，但**是被引导着到的**）

**💀 最扎心的事实：同一类问题，这是第二次栽。**

[[阿里云/阿里云消息团队一面面经]] 里有完整的「本地消息表 + 幂等重试 + 独立对账 + **宁可多查一次也不能漏一笔**」——**但那是标注为「改进后的回答」的事后补写材料，不是现场输出**。查那场的「当时的回答」：面对「积分对账怎么做」，我现场说的是「**把新旧系统操作包在一个事务里，强一致**」，被面试官纠正「这不一定是纯技术问题」，才引到「同步系统与对账系统分离」。

> **诊断（修正版）：不是「知识有但取不出来」，是「知识只存在于笔记里，从没变成口头能力」。**
> 阿里云现场没答好 → 事后写了很好的书面答案 → 三个月后微信支付同类问题 → 又没答好。**中间那份好答案从来没从纸面变成嘴上的东西。**
>
> ⚠️ **系统性风险**：本仓库所有「改进后的回答」（含本文件的全部定稿话术）现在都处于当年那份阿里云答案的同一状态——**写得很好，没说过一遍**。
>
> **转化动作**：①**出声讲一遍并录音**（写得顺 ≠ 说得顺——现场的「一个……一个……」「等一下我再想想」就是没演练过的直接表现）②**领域问法 + 代码问法各练一次**（阿里云考前者、微信支付考后者，只练一种另一种照样答不出）③每套骨架配一句**口令**：超时→「超时不等于失败，等于状态未知」；测试→「契约、边界、状态序列、并发、资源」；一致性→「宁可多查一次，也不能漏一笔」

**⚠️ 五个问题：**
1. **「超时」的语义没建立**——超时 ≠ 失败，超时 = **我方不知道对方做了什么**（信息缺失态，不是失败态）
2. **凭空假设下游幂等，且假设没出口**——**跟星河觉醒 LC698 默认「每组两个数」是同一个病**。憋在心里的假设只会在论证到一半时爆炸
3. **穷举试错而非分类**——「查账单→查数据库→查余额」是搜索；正确第一步是**建三态模型**（成功/失败/未知）把搜索空间收敛成三个格子
4. **把判断权交出去**（「是吧？」「你认为？」）——**有理由的结论即使方向错也加分；没理由的求确认即使方向对也减分**
5. 公道话：最终答案完整正确，问题只在于**不是第一反应**

**定稿：超时未决（in-doubt）五步答法**

> **① 建三态模型（15s）**：「超时的语义是我方等待失败，不代表对方没执行。请求可能：没到达 / 到达成功但响应丢了 / 到达失败 / 还在执行中。所以下游状态是**三态：成功 / 失败 / 未知**。资金操作里**未知态最危险**——既不能当成功（漏扣）也不能当失败（重扣）。」
>
> **② 表明立场：不赌下游幂等（20s，⭐真正的核心得分点）**：
> 「题干没说明 Debit 是否幂等。我的处理原则是：**幂等性未知，就当它不幂等**。更进一步——**即使有人告诉我它是幂等的，资金链路上我也不会裸重试**，因为幂等实现可能有 bug、幂等键可能有过期窗口。**正确做法不是去赌下游的行为，而是把自己设计成：不管下游幂等与否，我都不会造成资损。**」
>
> ⚠️ **注意**：只问一句「是不是幂等的」**不是答案**——因为答案永远是「不知道」。「幂等性未知」不是这题的障碍，**是这题的前提**，答案必须在这个前提下依然成立。
>
> **③ 按错误类型给策略表（30s）**：
>
> | 下游返回 | 语义 | 策略 |
> |---|---|---|
> | 明确成功 | 已扣款 | 结束 |
> | 明确业务失败（余额不足/冻结） | **确定没扣** | 不重试，返回失败 |
> | 权限拒绝 / 参数错误 | 确定没扣且重试无用 | 不重试 |
> | 忙 / 限流 / 连接被拒 | **确定没执行** | ✅ **可立即重试**（幂等与否都安全） |
> | **超时 / 网络中断** | ⚠️ **状态未知** | ❌ **不能盲目重试** → 走查证流程 |
>
> 关键洞察：「可重试错误」这词有歧义，**真正的分类维度是「下游有没有可能已经执行」**。
>
> **④ 未知态处理（30s）**：①**等足够长时间**（避免查到中间态）②用**业务单号**调下游**查询接口** `query_order(out_trade_no)`（支付系统标配）③已成功→结束，未受理→才可重发 ④**查询也超时** → 标记 **UNKNOWN 落库**，交异步补偿（定时轮询+每日对账）⑤**对上游返回「处理中」，不猜成功或失败**
>
> **⑤ 设计层根治（25s）**：
> ①**调用下游前先在本地落库**（业务单号 + status=PROCESSING）——进程崩了/超时了这笔的存在性也不丢，**未决态可恢复**，不是只活在内存里
> ②**业务单号全链路贯穿**当幂等键：下游若幂等我天然安全；下游若不幂等，我至少能用这个单号去查证、去对账。**单号是我方掌控的，幂等是下游的——把安全建立在前者上**
> ③**对账兜底**：实时链路做到最好也有极小比例遗留，这在支付行业叫**单边账**（我方未知、对方可能已扣）。「**宁可多查一次，也不能漏一笔**」
>
> **⑥ 追问「下游连查询接口都没有呢？」（15s）**：「那这个下游不具备承载资金操作的资格。我只能做两件：**绝不重试** + 未决单全落库靠对账和人工介入；同时**把它作为架构缺陷上报**，推动下游提供幂等或查询能力。**在资金链路上『我不知道对方做了什么、也查不到』是必须被消灭的状态，不是能在代码里绕过去的状态。**」
>
> **⭐ 思想总结：不确定性不可消除，但可以被「隔离」和「记录」。** 好的资金系统不是「保证每次都知道结果」，而是「**每一笔不知道结果的，都被记下来了，都有人管**」。
>
> **⭐ 可迁移原则——业务风险的不对称性**：少扣可以补扣（用户无感、损失可控）；多扣要退款+客诉+监管资损考核。**所以未决时默认动作是「停下来+记录+上报」，不是「猜一个方向继续」。** 说出这条证明你懂业务风险，不只懂技术模型。

**改进后的回答（资金安全 review checklist，直接背）：**
金额整型存分 → 单号全局唯一且不含业务信息 → 幂等 ID 贯穿 → **超时未决三态处理（成功/失败/未知，未知先查证）** → 转账双边同事务 → 下游调用超时保护 + 入参校验 → 敏感操作日志。

> **一句话记忆：超时 ≠ 失败，超时 = 状态未知。重试的前提是幂等；幂等未知时先查证再决定；查证不了就标记未决 + 异步补偿，绝不猜。**

## 5. 反问环节

**Q：你们怎么用 AI 开发同时保证质量？（支付场景严谨性要求高）**

面试官的回答信息量很大，原样记录：
- 组里**没有专职测试岗**，开发必须具备 TDD 能力，方案设计阶段测试设计就要完备
- AI 用法：人负责测试设计和边界澄清（异常用例/正常用例/覆盖点），AI 补充细节 + 生成代码，人验收
- AI 产能是人工 review 上限的成百上千倍，**没有完整测试覆盖，质量无从保证**——单测/集成/UAT 体系 + 核心用例知识库（随代码自动更新，AI 基于它维护 UAT）
- 「质量第一位，提效第二位」

## 6. 总结 / 自评

- **答得好：** 环形队列 bug 自己造例发现并修复；pop 契约答出 Response 封装；review 找全 5 个点（double/校验/单号/原子性），原子性和单号安全是亮点；反问质量高（引出了组织方式情报）
- **答崩 / 待改：**
  1. **异常用例设计被追问三轮才挤出来**——这个组没有测试岗、TDD 是核心考察，测试分层枚举（构造/边界/契约/并发/状态序列）必须变成条件反射
  2. **AI 题直接喂题没先做需求澄清**，被要求共享屏幕+全程引导——先 spec 后 AI
  3. **超时未决绕了三个错误方向**（查账/查余额）才到「超时≠失败、先查证再重试」——微信支付的命门题，就是共性分析里「钱不能多也不能少」的实战形态
- **风格实证（回填共性分析）：** 微信支付基础面 = 实操三连（数据结构手撕 + AI 协作 + 支付 code review），零八股零算法题——印证并扩展了爬取报告里「个别组零八股实操面」的判断；「资金安全/幂等/超时未决」在**一面**就以 code review 形态出现了
