## 0. 本场结论

面试官的题目分成三条线：

1. **项目是不是本人做的。** 字节项目一路追到停止条件、决策树生成、遗漏判断、适用范围、用户量、团队规模、成本和上下文管理。
2. **Agent 机制能否说准。** Memory 横向对比、自进化门禁、评测集泛化和“RSI”命名都在检查术语与证据是否匹配。
3. **能否迁移到车载语音。** 开放题的分水岭不是会不会说工具路由，而是能否发现多人车厢里的“这句话是不是在对车说”，并把声学、对话、安全和端云时延连起来。

**本场高光：**

- 字节决策树门禁的主链讲出来了：模型—工具循环、LangGraph state、结束前硬校验、树不完整就回灌继续执行。
- 能把决策树节点来源落到枚举值、`if / else`、抽象方法多实现和抽象语法树工具，不是只说“让模型分类讨论”。
- 谷歌自进化 Memory 能说到版本、评测、简单题防退化和回滚，研究目标与验证方式基本连得上。
- Coz 的动机讲对了：传统热点不等于优化后真能提高端到端吞吐量。
- 岗位动机和经历高度匹配，面试官也花了约 4 分钟完整介绍团队、三端架构和岗位方向。

**本场最贵的六个问题：**

1. **“怎么保证决策树没漏”答成“再让审核 Agent 看一遍”。** 同一个模型体系再次检查不能构成完整性证明；只能说降低遗漏率，并明确抽象语法树覆盖边界与离线评测证据。
2. **开源 Memory 对比严重串名和串机制。** 从描述推测想说 Claude Code、Codex、OpenClaw，但转录里出现 Coze、Calco、coder、open call；“6 小时”“七天晋升”“六个指标”等数字也没有稳定出处。
3. **把自己的方案称为 RSI。** RSI（recursive self-improvement，递归自我改进）范围远大于“冻结模型、只优化外部 Memory 文档”，会把可验证项目说成过度包装。
4. **Coz 的虚拟加速机制说反。** 不是给目标函数加延迟，而是在采样命中目标代码时让其他线程按比例暂停，从相对时间上模拟目标代码变快。
5. **车载语音系统只答了查询改写和工具路由。** 漏掉声学前端、多人说话人分离、设备定向语音判断、打断、执行安全和端云降级。
6. **两句岗位风险很大：**“现在是 Agent 的时代，所以代码写得少了”和“不足是后端基础”。研发岗会直接理解成编码基本功与工程能力不稳定。

### 下次同岗位面试前只做五件事

1. 背熟“声学前端 → 是否对车说话 → 意图与会话 → 安全执行 → 端云协同”的 90 秒车载语音架构。
2. 能白板写出 Attention 的 `QKᵀ / √d`、掩码、softmax 和乘 `V`。
3. 开源 Memory 只讲三个已核验系统，每个机制只报有源码依据的事实，不报记不准的时间和阈值。
4. 固定两句边界：“审核 Agent 降低遗漏但不保证完整”“这叫评测门禁下的 Memory 优化，不叫 RSI”。
5. 编码能力回答只报当前主语言、可独立完成什么、如何验证，不再说“Agent 时代写得少”。

## 3. 决策树门禁在架构上怎么实现？

### 当时的回答（忠实压缩）

先解释 DeerFlow 的模型—工具循环：模型输出工具调用就执行工具并把结果返回，输出普通文本就结束。决策树是一个工具，生成后保存在 LangGraph state 中。系统在模型结束前检查 state 里有没有树、节点是否有代码来源、枚举值或函数名；不完整就向模型注入提醒，不让循环结束。扩展点覆盖模型、Agent 和工具调用前后。

### 复盘

**技术定义：** 决策树门禁是框架在 Agent 结束前执行的硬校验：只有树存在且所有要求字段通过检查，最终答案才允许返回。

**解决什么问题：** 普通模型—工具循环的停止条件由模型决定。模型过早输出普通文本时，系统会交付一份措辞完整但漏掉业务分支的答案，用户又很难察觉遗漏。

**机制：**

1. 主 Agent 调用决策树工具，把分支节点、验证状态和代码来源写入 LangGraph state。
2. 模型尝试输出最终答案时，框架先检查树是否存在、节点字段是否完整、可验证节点是否全部完成。
3. 未通过时，框架合成一条校验失败消息追加到消息列表末尾，让模型继续调用工具；不是改写原历史。
4. 通过后才进入答案生成和审核 Agent。审核 Agent 是第二道质量检查，不是决策树存在性的裁决者。

**面试怎么说（30 秒）：**

> 「DeerFlow 原本是模型决定何时结束：没有工具调用就返回答案。我把门禁挂在模型输出之后、流程结束之前，检查 LangGraph state 里的决策树是否存在、节点来源是否完整、分支是否都验证过。没通过就合成一条校验消息追加回上下文，强制再跑一轮。核心是把停止条件从模型手里移到框架手里。」

**题型 B（项目机制）｜扣分：① 落点（先铺很长的循环背景，核心判断出现较晚）**

> 📌 项目事实来源：录音 + [[项目追问/字节答疑Bot#Q1f: 门禁在架构上具体怎么实现的？（🆕 银河二面原题，✅ 现场答得好，本页新增素材）]]；置信度高。

> 术语校准：硬校验、停止条件、LangGraph state 里，哪个术语是你之前没学过的？

## 4. 每道题的决策树怎么生成？支持多少类问题？

### 当时的回答（忠实压缩）

- 每个问题由 Agent 动态生成不同的树。
- 提示词要求重点找枚举值、抽象类的不同实现、语义相近的函数以及 `if / else`、`switch / case`。
- 针对条件分支实现了 AST（abstract syntax tree，抽象语法树）解析工具，把代码里的判断条件暴露给模型。
- 系统没有预定义业务问题类别，支持 40 多个代码仓库；离线评测按简单、中等、困难分级。
- 因为运行前不知道题目难度，所有问题默认都走决策树。

### 改进后的回答（45 秒）

> 「这里要分问题类型和分支来源。产品不是只支持固定问题类型，入口是 40 多个仓库上的任意代码问题；简单、中等、困难只是评测标签。
>
> 每道题的树都在运行时生成。节点来源主要有三类：枚举值或条件分支、同一抽象接口的不同实现、语义相同但分散在不同位置的处理函数。单文件内的 `if / else` 和 `switch / case`，我已经用抽象语法树工具提取；跨仓库调用图只做过评估，没有实现。当前默认所有问题都走树，代价是简单题也会增加模型轮次，这正是后续可以用轻量难度分类器优化的地方。」

**题型 B（项目机制）｜扣分：③ 机制（没有主动区分已实现的单文件分支提取和未实现的跨仓库调用图）**

> 术语校准：抽象语法树、跨仓库调用图、运行时生成里，哪个术语是你之前没学过的？

## 5. 决策树也是模型生成的，怎么保证没有遗漏？

### 当时的回答（忠实压缩）

把决策树和代码来源交给审核 Agent；审核 Agent 逐节点读源文件，看有没有遗漏。发现遗漏就告诉用户问题可能没有框定完整，让用户确认是否需要继续追问；没有遗漏则结束。现场结论是“通过审核 Agent 保证尽量全面”。

### 复盘

**技术定义：** 完整性不是“另一个模型觉得完整”，而是存在一个可枚举的分支集合，并能计算已验证分支数与总分支数。

**解决什么问题：** 主 Agent 和审核 Agent 都可能漏掉同一条隐藏路径。把同一份不完整树交给审核 Agent，只能降低遗漏概率，不能证明树外没有分支。

**机制：**

1. 对抽象语法树能提取的 `if / else`、`switch / case`，分支总数是 `N`，树中已验证分支数是 `M`，可以计算 `M/N`。
2. 审核 Agent 重新读取代码，检查每个结论是否有来源、树上分支是否都进答案；它有独立上下文，但仍不是数学保证。
3. 明确静态分析盲区：运行时配置、反射、下游服务返回值和跨仓库动态调用可能不在 `N` 里。
4. 对盲区必须输出“缺少代码依据 / 需要用户补范围”，最后用 50 多题回归集验证系统级遗漏是否下降。

**面试怎么说（30 秒）：**

> 「我不能说绝对保证。对抽象语法树能枚举的代码分支，我能用 `M/N` 衡量覆盖率：真实分支有多少、已经验证多少。审核 Agent 负责重新读代码和核对答案，但它只能降低遗漏率。运行时配置、反射和下游返回值是静态分析盲区，这些必须明确提示用户，并靠离线回归集验证整体改进。」

**题型 B（项目机制）｜扣分：② 诊断 + ③ 机制（把审核 Agent 当成完整性保证，没有说静态分析边界）**

> 术语校准：完整性、静态分析盲区、`M/N` 覆盖率里，哪个术语是你之前没学过的？

## 7. 有没有 token budget？成本和资源瓶颈是什么？

### 当时的回答（忠实压缩）

先说有预算，又说成本不是主要限制。真实瓶颈是内部模型资源排队和单轮抖动，因此接入多个厂商的模型协议。用户约两三百人、几分钟一个问题，整体并发不高；单个模型调用有时几秒，有时排队一分钟。现场还说“模型轮次越多，回答效果越好”。

### 复盘

**技术定义：** token budget 是单次任务允许消耗的输入与输出 token 上限；它和模型资源排队、每分钟调用配额、端到端时延是四个不同约束。

**解决什么问题：** 如果把四个约束混成“预算”，就无法判断该做模型切换、减少上下文、并行工具还是限制循环；“轮次越多越好”也会让系统没有停止上限。

**机制与口径：**

- 当时没有业务侧明确的单次成本目标，不能说“做过降本目标”。
- 实际受限的是内部模型排队、长尾延迟和多轮 Agent 的累计时间。
- 多协议网关解决的是模型可用性和切换，不自动解决质量与成本。
- 应记录每次任务的模型调用次数、输入输出 token、排队时间、工具时间和端到端耗时，再与 56 → 87 的质量指标一起看。
- 轮次需要上限；是否多跑一轮由“还有未验证分支吗”决定，不由“越多越好”决定。

**面试怎么说（30 秒）：**

> 「这个项目没有硬性的单次成本目标，真实瓶颈是内部模型排队和长尾时延。用户只有 200 多，吞吐不是第一矛盾，但单题会跑很多模型轮次。我接三家协议主要是为了可用性；质量和资源要一起量：模型调用数、token、排队时间、工具时间、端到端耗时和离线得分。是否继续循环由未验证分支决定，并设置硬上限。」

**题型 B（项目机制）｜扣分：① 落点 + ② 诊断 + ④ 口径（预算、配额、排队和时延混在一起；“轮次越多越好”没有实验边界）**

> 术语校准：token budget、长尾延迟、硬上限里，哪个术语是你之前没学过的？

## 8. 怎么减少上下文和 token？做过上下文压缩吗？

### 当时的回答（忠实压缩）

说项目倾向保留更多模型轮次，因为观察到轮次多时回答更好；但超过上下文窗口阈值后会压缩用户问题、当前调研进度和关键文件。检索返回过大时，把结果 offload 到磁盘，让 Agent 按路径读取，而不是把全部结果注入 system prompt。

### 复盘

**技术定义：**

- 上下文压缩是把早期消息改写成更短的状态摘要，减少下一轮发给模型的历史。
- 卸载（offload）是把大工具结果写入磁盘，上下文只保留路径、摘要和重新读取方法。

**解决什么问题：** 不做压缩会撞上下文上限；不做卸载会让一次大搜索结果占掉大量 token，挤走用户目标和关键证据。压缩过度又会丢失约束、已验证分支和文件来源。

**机制：**

1. 达到 token、消息数或上下文占比阈值后，只压缩较早消息，保留最近完整轮次和模型—工具配对。
2. 摘要至少保留用户目标、已完成调查、关键决策、关键文件、未验证分支和下一步。
3. 大搜索结果写磁盘，上下文留“文件路径 + 命中摘要 + 如何按需读取”，不是说写进 system prompt。
4. 稳定事实尽量留在源文件，压缩后按需重读；用同一回归集检查压缩前后答案是否退化。

**面试怎么说（30 秒）：**

> 「我分两层做。第一层是上下文压缩：窗口接近阈值时，把早期轨迹压成用户目标、已验证结论、关键文件和待办，最近几轮与工具调用保持完整。第二层是卸载：搜索结果太大就写磁盘，上下文只留路径和摘要，需要时再读。这样不是盲目砍模型轮次，而是减少每一轮里的无效 token。」

> 📌 当前 DeerFlow 会按 token、消息数或窗口占比触发压缩，并保护模型消息与工具结果的配对；来源是 [DeerFlow 上下文压缩文档](https://github.com/bytedance/deer-flow/blob/main/backend/docs/summarization.md)，来源类型为官方仓库文档，置信度高，查证于 2026-09-19。

**题型 B（项目机制）｜扣分：③ 机制 + ④ 口径（把大工具结果说成注入 system prompt；没有说明压缩后的验收方式）**

> 术语校准：上下文压缩、卸载、模型—工具配对里，哪个术语是你之前没学过的？

## 9. 看过哪些开源 Agent Harness？Memory 有什么不同？

### 当时的回答（忠实压缩）

从 Memory 切入，对比了三个系统：一个在会话中把记忆写入 Markdown 并通过索引文件读取；一个在会话空闲后汇总历史轨迹；一个按召回频率、时间和效果多指标晋升长期记忆。现场产品名被转录成 Coze、Calco、coder、open call，且多次自我修正“6 小时”“是不是立即写入”“好像 6 个指标”。最后把差异解释为厂商对自家模型能力的信任程度不同。

> ⚠️ 从机制描述推测，现场想说的是 Claude Code、Codex 和 OpenClaw，但这是根据转录做的推断，不能冒充已还原原话。

### 复盘：先各讲各的，再比较

#### 1. DeerFlow

一轮对话结束后，Memory middleware（中间件，即插在 Agent 运行链路中的处理组件）把消息放入异步队列；接近上下文压缩时还会先把即将被压掉的消息刷新到队列。当前版本包含事实抽取、置信度门槛、过期复审和可插拔后端。

> 来源：[DeerFlow CHANGELOG](https://github.com/bytedance/deer-flow/blob/main/CHANGELOG.md) 与 [Memory Module Roadmap](https://github.com/bytedance/deer-flow/issues/2450)。来源类型：官方仓库源码 / issue；置信度高；2026-09-19 查证。

#### 2. Codex

Codex 把空闲会话先做阶段一抽取，生成 raw memory 和 rollout summary；再由专职 consolidation agent（整合 Agent）把它们合并成 `MEMORY.md`、`memory_summary.md` 和可复用 skill。`memory_summary.md` 是后续会话的入口，细节再按需查 `MEMORY.md`。不要背“固定 6 小时”，因为空闲阈值可配置且版本会变。

> 来源：[Codex Memory README](https://github.com/openai/codex/blob/main/codex-rs/memories/README.md) 与 [consolidation prompt](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/consolidation.md)。来源类型：官方源码；置信度高；2026-09-19 查证。社区拆解只用于交叉检查，不单独作为证据。

#### 3. OpenClaw

OpenClaw 的 Dreaming 是定时后台整理：前置阶段先去重、暂存候选和提取主题，Deep 阶段先过确定性门禁，再做合并。当前官方架构明确使用召回相关性、召回次数、不同查询数、时间和多日重复等信号，并先按来源可信度排除不可信内容。

> 来源：[OpenClaw Memory Architecture](https://github.com/openclaw/openclaw/blob/main/docs/concepts/memory-architecture.md)。来源类型：官方仓库文档；置信度高；2026-09-19 查证。

#### 横向结论

| 系统 | 什么时候判断 | 谁决定值得长期保留 | 主要约束 |
|---|---|---|---|
| DeerFlow | 每轮后 / 压缩前 | 抽取模型 + 阈值与过期规则 | 在线增量、低额外时延 |
| Codex | 会话空闲后的两阶段任务 | 抽取模型 + 专职整合 Agent | 个人跨任务知识的离线整理 |
| OpenClaw | 定时 Dreaming | 多信号确定性门禁 + 合并步骤 | 长期个人 Agent 的污染与晋升 |

**为什么不同：** 不是“谁更相信自己的模型”，而是产品作用域、允许的后台算力、写入延迟和错误代价不同。这是根据三套公开架构做的工程推断，来源类型为我的推断，置信度中高。

**面试怎么说（45 秒）：**

> 「我重点看了三个开源实现。DeerFlow 是每轮后异步抽取，靠阈值、容量和过期复审控制；Codex 是两阶段，先从空闲会话抽取，再由专职 Agent 合并成正式记忆；OpenClaw 是定时 Dreaming，候选要经过召回次数、不同查询数、时间和来源可信度等门禁才晋升。它们的差异不是模型自信程度，而是作用域和错误代价：在线系统重时延，编程 Agent 重跨任务整理，长期个人 Agent 更重污染控制。」

**题型 C（通用知识）｜扣分：④ 口径（产品名、时间、指标数和机制均不稳定；把架构差异归因为模型自信）**

> 术语校准：middleware、rollout summary、consolidation agent、Dreaming、确定性门禁里，哪个术语是你之前没学过的？

## 10. 谷歌的“自进化 Memory”是什么？

### 当时的回答（忠实压缩）

说现有通用 Memory 面向所有用户和任务，不够适合测试 Agent；自己的目标是做领域专用 Memory。Memory 写入后可能腐化、矛盾或降低 Agent 效果，因此建立 golden data set 作为门禁：每天 Memory 更新后跑评测，性能下降就回滚到前一天版本，希望让 Memory 与性能曲线持续向上。

### 复盘

**技术定义：** 自进化 Memory 是在模型权重不变时，把外部 Memory 文档视为可更新状态；每次候选改写都必须经过独立评测，变差就拒绝或回滚。

**解决什么问题：** 普通 Memory 只解决“写进去和找出来”，不能证明写入后任务更好。坏记忆会稳定地把 Agent 引向错误路径，而且影响可能跨很多会话。

**机制：**

1. 从成功 / 失败轨迹提出候选经验，并保留适用条件和来源。
2. 每次改写生成新版本，不直接覆盖已验证版本。
3. 用独立回归集比较旧版本与候选版本：简单题不能退化，中高难题和成本指标达到阈值才接受。
4. 不通过就回滚；通过后仍做线上旁路观察，避免固定评测集之外退化。
5. 当前已确认的实测结论是：通用 Memory 接入后，准确率没有显著提升，但模型轮次和 token 下降。它证明 Memory 目前更像降本线索，不应直接替模型下结论。

**面试怎么说（60 秒，按当前保守口径）：**

> 「普通 Memory 只有写入和召回；我想加的是版本、评测和回滚。测试 Agent 每次从轨迹提出候选经验，先生成新版本，再在独立回归集上和旧版本对照：基础题一旦退化就拒绝，中高难题与成本指标整体更好才接受，否则回滚。
>
> 我们已经观察到一个反直觉结果：接入通用 Memory 后，分类准确率没有明显提高，但模型轮次和 token 下降。原因是结论型 Memory 会让模型更早停止读取原始报错。所以后续方向不是记更多，而是把 Memory 改成线索型：告诉 Agent 优先看哪段日志，不替它直接下结论。自动回滚门禁是否已经完整上线，我会按真实进度回答，不把设计说成完成项。」

**题型 B（项目机制）｜扣分：① 落点（自己的工作与平台现状混在一起）+ ④ 口径（门禁是否落地与 ground truth 冲突）**

> 📌 内部项目事实仅来自录音、[[谷歌实习]] 与 [[项目追问/谷歌Memory]]；完成状态待本人确认，置信度中。通用设计结论有项目评测作为线索，但不能外推到所有 Memory 系统。

> 术语校准：候选改写、独立回归集、线索型 Memory、线上旁路观察里，哪个术语是你之前没学过的？

## 11. 自进化的关键路径是什么？怎么防止只拟合评测集？

### 当时的回答（忠实压缩）

Memory 有会话内写入和每天定时 Dreaming 两条路径，以 Markdown 存储并保留版本。每天 Dreaming 完成后增加 evaluation：基础题只要有一道从对变错就回滚，中等和困难题看分数；变差回滚到前一天版本。面试官指出这会向 evaluation 数据集收敛，现场回答是“定期重构、升级或更换题目”。

### 复盘

**技术定义：** 数据泄漏是同一条样本或高度相似样本既参与 Memory 生成，又参与最终验收，导致分数上涨但新问题不一定变好。

**解决什么问题：** 反复看同一套题修改 Memory，最终会把答案写进 Memory；此时回归分数看起来持续上升，真实泛化能力却下降。

**机制：**

1. **轨迹池：** 只用于生成候选 Memory。
2. **验证集：** 用于比较方案和调阈值，可以多次看。
3. **冻结留出集：** 只做阶段验收，不参与 Memory 生成和日常调参。
4. **滚动线上集：** 从新时间窗口抽样，检查输入分布变化；加入前先去重，不能把错误样本直接塞进冻结留出集继续调。
5. 同时监控任务正确率、模型轮次、token 和时延，避免只优化一个分数。

**面试怎么说（30 秒）：**

> 「不能靠不断换题来解决过拟合，关键是数据职责隔离。历史轨迹只生成 Memory，验证集用于调方案，冻结留出集只做阶段验收；再从最新线上流量维护一套滚动集看输入分布变化。同一根因的近似样本先去重，绝不能一边看留出集答案一边改 Memory。」

**题型 B（项目机制）｜扣分：③ 机制（“定期改评测集”没有先说明轨迹、验证和最终留出的隔离）**

> 术语校准：数据泄漏、冻结留出集、滚动线上集、输入分布变化里，哪个术语是你之前没学过的？

## 13. Arm 的 Coz / Causal Profiling 做什么？

### 当时的回答（忠实压缩）

说 Coz 来自 2015 年系统方向 best paper，用于量化优化一段代码对整体吞吐量或延迟的影响。举了两个串行阶段的例子：一个累计占 16 秒 CPU（central processing unit，中央处理器）时间但可并行，另一个占 4 秒且不可并行，传统热点会把注意力放在前者。随后说给候选函数“注入延迟”，比较整体循环耗时变化。

### 复盘

**技术定义：** Causal Profiling（因果性能剖析）通过受控实验估计“如果某段代码变快，程序整体吞吐量或延迟会改善多少”。

**解决什么问题：** 传统采样只能告诉你 CPU 时间花在哪里。并发程序里的热点可能不在关键路径上，优化后只会让线程更早等待锁或 I/O（input/output，输入输出），端到端指标不变。

**机制：** Coz 不能真的提前优化代码，所以做 virtual speedup（虚拟加速）：随机选一行和加速比例；采样命中目标行时，按比例暂停其他线程，使目标行相对其他代码看起来变快；再观察 progress point（进度点，即吞吐计数或延迟边界）的变化。

**面试怎么说（45 秒）：**

> 「Coz 解决的是‘热点不等于值得优化’。传统 profiler（性能剖析器）只能看某行占多少 CPU 时间，Coz 直接估算优化这行后端到端吞吐会涨多少。它随机选一行和虚拟加速比例；采样命中这行时，不是给这行加延迟，而是让其他线程按比例暂停，从相对时间上模拟这行变快，再看吞吐进度点或延迟进度点怎么变。我在 Arm 做的是把这套工具迁移并扩展到 Arm 和 Linux 6.8，同时补预热、调用栈和 off-CPU（线程没有占用 CPU、正在等待锁或 I/O 的时间）能力。」

> 📌 来源：[Coz 官方仓库](https://github.com/plasma-umass/coz) 与 [SOSP 2015 论文](https://arxiv.org/abs/1608.03676)。来源类型：源码 / 原始论文；置信度高。

**题型 B（项目机制）｜扣分：③ 机制（把“暂停其他线程”说成“给目标函数加延迟”）**

> 术语校准：关键路径、虚拟加速、进度点、off-CPU 里，哪个术语是你之前没学过的？

## 15. Attention 的计算过程是什么？

### 当时的回答（原话）

> 「Attention 计算过程不行，不太熟悉。」

### 复盘

**技术定义：** Attention（注意力）让每个 token 根据匹配分数，对上下文中其他 token 的信息做加权汇总。

**解决什么问题：** 如果每个 token 只看自己，模型无法根据上下文消解指代或组合远距离信息；如果所有位置权重相同，关键 token 的信息会被稀释。

**机制：**

1. 输入矩阵 `X` 分别乘三组参数，得到 `Q`（query，查询向量）、`K`（key，键向量）和 `V`（value，值向量）。
2. 用 `QKᵀ / √dₖ` 计算每个查询位置对每个键位置的匹配分数；除以 `√dₖ` 是为了避免向量维度大时分数过大。
3. 自回归模型加 causal mask（因果掩码，即把未来位置设为不可见）。
4. softmax（把一组分数转成总和为 1 的正权重）后乘 `V`，得到加权汇总结果。
5. Multi-head attention（多头注意力）把通道分成多组独立计算，再拼接，让不同组学习不同关系。

公式：`Attention(Q, K, V) = softmax(QKᵀ / √dₖ) V`

**面试怎么说（30 秒）：**

> 「输入先线性映射成 Q、K、V。Q 和所有 K 做点积并除以根号下键向量维度，得到相关性分数；自回归模型再用因果掩码遮住未来 token；经过 softmax 变成权重，最后对 V 加权求和。多头注意力就是把这个过程并行做多组再拼接，让不同头关注不同关系。」

**题型 C（通用知识）｜扣分：① 落点 + ③ 机制（完全未作答）**

关联：[[Agent延迟优化#1.1 一次 agent 回答的时间由什么组成]]

## 18. 设计一个车载语音 Agent，有哪些关键点和挑战？

### 当时的回答（忠实压缩）

提出两个难点：

1. 语音转文字后不如打字规范，需要查询改写和意图识别，同时控制延迟。
2. 车内工具很多，不应把全部工具暴露给同一个 Agent；先路由到负责不同模块的 Agent 或 skill，再让固定 workflow 约束执行顺序。

面试官追问“还有吗”，现场没有继续想到，反问面试官提示。

### 复盘：系统架构先行

车载语音 Agent 不是“文本 Agent 前面加一个语音转文字”，完整链路至少有六层：

1. **声学前端：** 麦克风阵列先做 AEC（acoustic echo cancellation，声学回声消除）、降噪、波束形成（利用多麦克风的相位差增强特定方向声音）、VAD（voice activity detection，语音活动检测）和多人语音分离。
2. **流式 ASR：** ASR（automatic speech recognition，自动语音识别）边听边输出文字和时间戳；车内中文重点看 CER（character error rate，字错误率）与长尾噪声场景。
3. **设备定向语音与会话控制：** 判断“谁在什么时候说话”以及“这句话是不是对车说”；管理唤醒后的会话拥有者、打断和多人抢话。
4. **意图与路由：** 结合文本、座位、当前车况和会话历史判断意图，只加载当前域需要的工具。
5. **安全执行：** 大语言模型只产出结构化意图；确定性执行器检查权限、车辆状态、前置条件、幂等性和风险等级。高风险动作要求确认，不能让模型直接操作执行器。
6. **端云协同：** 端侧处理唤醒、声学前端、基础命令和失网降级；云端处理复杂理解与长任务。全链路流式化，分别测首个识别结果、首个语音响应和动作完成耗时。

### 具体取舍

| 位置 | 适合做什么 | 主要原因 | 主要代价 |
|---|---|---|---|
| 弱算端 | 唤醒、VAD、基础降噪、极简本地命令 | 最低时延、断网可用 | 模型容量小 |
| 强算端 | 多通道声学、设备定向语音判断、本地意图与常用工具 | 隐私和时延平衡 | 功耗与车型差异 |
| 云端 | 复杂对话、长任务规划、开放域知识 | 模型能力强、更新快 | 网络抖动、隐私和成本 |

### 为什么这样设计

- 声学错误会向后级联：说话人分错、文字再准确也会执行错人的命令。
- 语义正确不等于允许执行：开窗、空调与自动驾驶相关动作的风险等级不同，必须由执行层裁决。
- 单纯把全部工具给一个模型，会同时增加选择错误、上下文 token 和权限暴露。
- 端云不是按功能永久二分；要按时延、隐私、算力、网络和安全等级动态选择。

### 常见失败与指标

- 误唤醒 / 漏唤醒。
- 把乘客对话误判成对车指令，或拒绝真正指令。
- 多人重叠讲话导致说话人和文本错配。
- 用户在 TTS（text-to-speech，语音合成）播报中打断时，旧动作仍继续执行。
- 网络切换后会话状态重复提交，导致动作执行两次。
- 指标至少覆盖：唤醒错误、设备定向语音判断、CER、端到端 p50 / p95、工具成功率、重复执行率和高风险误执行数。p50 / p95 表示 50% / 95% 请求不超过的耗时。

### 面试怎么说（90 秒）

> 「我会把车载语音 Agent 分成六层。第一层是多麦克风声学前端，做回声消除、降噪、波束形成、语音活动检测和多人分离；第二层是流式语音识别；第三层不是意图，而是先判断谁在说、这句话是不是对车说，并管理唤醒后的会话和打断；第四层才做意图识别和工具路由，只加载当前域的工具；第五层由确定性执行器检查车辆状态、权限、前置条件和风险，高风险动作必须确认；第六层是端云协同，端侧保低时延和断网能力，云端处理复杂理解。
>
> 我会分别看误唤醒、设备定向语音误判、字错误率、端到端 p95、工具成功率和高风险误执行，不能只看大模型回答质量。」

> 📌 多人车内语音的客观难点由 [AISHELL-5 论文](https://arxiv.org/abs/2505.23036) 和 [开源基线](https://github.com/DaiYvhang/AISHELL-5)支持：数据包含四路车内远场麦克风、多人语音与真实驾驶噪声。来源类型：原始论文 + 官方代码，置信度高。
>
> 📌 “声学 + 文本 + 对话上下文共同判断是否对设备说话”由 [M³V](https://arxiv.org/abs/2409.09284) 和 [多模态设备定向语音研究](https://arxiv.org/abs/2403.14438)支持。来源类型：原始论文，置信度中高。上面的具体六层落地方案是基于岗位信息和论文做的系统设计推断，置信度中高，不是小鹏内部实现口径。

## 19. 多人车厢里，怎么知道用户是在和车说话？

### 当时的回答（忠实压缩）

先说唤醒词；面试官指出唤醒后多人地位平等。随后提出按唤醒者声纹过滤其他声音。面试官指出声纹和音频特征效果不够好后，又提出把几秒对话全部转成文字，让 Agent 根据上下文判断谁在下指令，但承认不知道准确率。

### 复盘

**技术定义：** 这题叫 addressee detection（受话对象判断），目标是判断一句话是否指向车机。它和两个相邻任务不同：speaker diarization（说话人分离）回答“谁在什么时候说话”；speaker localization（说话人定位）回答“声音来自哪个座位或方向”。

**解决什么问题：** 声纹只能说明“像谁”，不能说明这个人正在对谁说话；纯文本只能看语义，无法区分同一句“打开一下”是在对乘客说还是对车说。单一信号都会产生误执行。

**机制：**

1. 唤醒词只建立初始会话，不永久授予控制权。
2. 麦克风阵列估计 DOA（direction of arrival，声源到达方向）和座位区域；说话人分离给每段语音附说话人标签。
3. 说话人嵌入（把声音编码成向量）只作为一个特征，再结合文本意图、称呼词、上一轮车机问题、会话拥有者和时间间隔做设备定向语音分类。
4. 如果车辆有合规的舱内视觉输入，可把视线或头部朝向作为可选信号；没有就不依赖。
5. 低置信度不执行，先问“你是在让我打开副驾车窗吗”；高风险动作即使高置信也要二次确认。

**面试怎么说（45 秒）：**

> 「这不是单纯声纹识别，而是受话对象判断。我会融合四类信号：麦克风阵列给座位方向，说话人分离给谁在说，声纹给身份相似度，文本和会话历史判断这句话是否承接车机。唤醒词只建立初始会话，不能一直锁定一个人。最终分类器输出置信度；低置信度先澄清，高风险动作再确认。声纹和大模型文本判断都只是特征，不能单独做裁决。」

> 📌 [AISHELL-5](https://github.com/DaiYvhang/AISHELL-5)证明车内多通道、多人、重叠语音和噪声需要联合处理；多模态设备定向语音论文显示音频、文本与上下文融合优于单一模态。来源类型：论文 / 官方代码，置信度中高。具体阈值和小鹏产品指标未查到，不做推断。

**题型 C（系统设计）｜扣分：② 诊断 + ③ 机制（把声纹当裁决；文本模型没有说输入、分类目标、阈值和失败处理）**

> 术语校准：受话对象判断、说话人分离、说话人定位、DOA、说话人嵌入里，哪个术语是你之前没学过的？

## 总体评价

**匹配度：中高。** 三段 Agent 经历与团队 Harness、工具接入、上下文、Memory 和评测方向高度重合；字节项目机制真实、ownership 强。主要差距集中在岗位特有的车载语音链路和模型基础，而不是 Agent 项目数量。

**本场可能给面试官的正向信号：**

- 项目能追到框架停止条件和状态字段，不是只会讲业务背景。
- 一个人 owner 过完整 Agent 项目，且有评测数字。
- 系统、Agent 和底层性能经历能覆盖团队多条工作线。
- 遇到不熟的 Attention 直接承认，没有编答案。

**本场可能给面试官的风险信号：**

- 角色核心题需要面试官提示“多人车厢里是不是对车说话”。
- Attention 完全不会，模型基础短板被确认。
- Memory 产品名与机制混乱，容易让“看过源码”失去可信度。
- “审核 Agent 保证完整”“自己称 RSI”“轮次越多越好”三处结论大于证据。
- “Agent 时代写得少”“后端基础不足”让研发基本功显得不稳定。
- 美国政策问题主动报未核实数字，口径控制不足。

### 已知复发毛病对照

1. **用“没有 / 比较少 / 不行”开局：** 模型训练、Attention 两题命中。Attention 不会可以承认，但下一句要给补课边界；模型训练要讲成岗位取舍。
2. **给愿望不给机制：** “让 Agent 根据上下文判断是不是在对车说”没有分类输入、阈值和失败处理。
3. **内部名称与保密：** 谷歌框架和团队迁移细节再次说得过深。
4. **数字口径漂移：** 字节定稿是 56 → 87，本场又退回“50 多 → 80 多”。
5. **术语扩大：** 把外部 Memory 优化称为 RSI。
