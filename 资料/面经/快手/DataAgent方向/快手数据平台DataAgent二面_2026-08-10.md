## 2. 字节答疑 Bot 项目深挖

面试官明确表示"你实习公司蛮多，谷歌只待了一个月简历写得也少，我们主要聊字节这块"。

### Q1【B 项目机制】：当时为什么选择做决策编排（决策树）的模式？

**当时的回答：**
> "主要是为了保证回答的一个准确率。因为我们代码仓库比较多，业务逻辑比较复杂，如果想把问题答案找到，它要走很多 step，然后这个 context 是比较长的，所以它很容易出现它的 summary 出现一个张冠李戴的幻觉问题，就比如说原本是 A 流程能转到 B 流程、A 状态转到 B 状态，但它说成了 A 状态转到 C 状态，然后你必须要做这样的校验来保证它回答是一定准确，不能说误导别人，所以说当时是需要说有一个专门做 review 的 review agent 来做这样的一个兜底机制。"

**评分：**
- ①落点 ✅ 开口直给结论"保证准确率"
- ②诊断 ✅ 给了具体坏结果（A→B 说成 A→C 的张冠李戴幻觉），不是空泛的"提高性能"
- ③机制 ⚠️ **只说"有一个专门做 review 的 review agent"，没说这个 agent 拿什么判据判断对错、判错了怎么处理**——给了愿望没给裁决者
- ④口径 ✅ 无问题

**改进后的回答（补上机制的裁决者和判据）：**
> "保证准确率的根本问题是：单 agent 一次性生成的长链路回答，中间任何一步的 summary 出错都会被无声地带到最终答案里，用户看不出来。所以拆成两个 agent 的关键不是『多一个人看一遍』，而是**给这条链路加一个可以独立复核的裁决点**：review agent 不重新回答问题，只做一件事——**逐条核对生成 agent 输出的每一个状态转移，是否能在决策树的原始节点里找到依据**。找不到依据的转移，直接打回重做，并标出是哪一条对不上。这样『对不对』不再是生成 agent 自己说了算，而是有一个独立的、只做核对不做生成的裁决者。"

### Q3【B 项目机制/诊断】：13% 的错误是因为什么原因？

**当时的回答：**
> "因为错误的话主要两点：一点是用户问题问得不太好……用户会问得非常泛，把很多不同状态给包括起来，但其实用户他只关心某几个特定范围里面的回答。因为我们本质上是一颗决策树……但其实你可能只需要看 A、B、D，你不需要回答 A、C、F、G，但是因为用户问题问得非常泛，没把这个范围给限住，没把这个枝剪掉，导致他回答的会比较不够全面……包括说可能他评分指标没有做得很好，比如说 A 能不能做某事，那他只需要回答说 A 能做某事或不能做某事就好，但是他还会期望说答出比如说 A 还能做到另外一件事，这是另外一个他指标没有做好的原因。"

**评分：**
- ①落点 ✅ 直给"两点原因"
- ②诊断 ✅ 两点都具体（问题没剪枝导致漏答范围外分支；打分标准和问题预期不匹配）
- ③机制 —（这题只问原因不问解法，不强制要求）
- ④口径 ✅ 无问题

这题答得扎实，无需大改。

### Q4【C 通用知识】：什么场景下用"多 agent + 决策树"这种策略比较好？（面试官明确说是业界视角，不限于自己项目）

**当时的回答：**
> "我们其实这样做主要是为了隔离上下文，因为回答生成那个 agent 的上下文会很长，所以用了一个多 agent 架构。另外是一些工具的不同……你不同 agent 负责不同的业务，或者给他不同的 system prompt，这时候就需要另外 agent 来负责不同的工作，因为 attention 的原因，一个 agent 比较难以负责不同的工作。另外如果希望快速处理某些任务，需要并行处理来提高回答的效率，这时候你可能会需要多 agent 架构来并行处理一些事情。"

**评分：**
- ①落点 ⚠️ 没有先给一句总判断（比如"看两个信号：上下文会不会爆、任务能不能并行"），直接进入三点列举，读者要自己归纳
- ②诊断 ⚠️ 三点理由都合理但都停留在"是什么"，没给反例（什么场景**不**适合，比如任务强耦合、总数据量小的场景硬拆反而增加串行开销）——问的是"业界视角"，缺对照面
- ③机制 ⚠️ "隔离上下文"没展开怎么隔离（各 agent 独立上下文窗口，互不共享历史）
- ④口径 ✅ 无问题

**改进后的回答（先给判断框架，再落三点，加反例）：**
> "我会看两个信号：**上下文会不会爆、任务能不能拆成互不依赖的子问题**。满足任一个，多 agent 就值得做；两个都不满足，单 agent 反而更省事——因为拆多了会引入额外的串行调用开销和一致性维护成本。
> 具体到我们的场景：**上下文侧**，业务逻辑复杂到需要几十轮工具调用才能把决策树填完，单 agent 把生成和自我核对挤在同一个上下文里，核对时反而会被自己刚才的推理带偏，所以拆出一个不共享生成过程、只看最终输出的 review agent。**任务侧**，不同业务方向（比如不同玩法/不同国家维度）用的知识库和 system prompt 不一样，硬塞进一个 prompt 会互相干扰，拆开反而降低单 agent 的认知负担。
> 反过来，如果任务量小、链路短、一次工具调用就能出结果，拆多 agent 只会多两次网络往返和一次上下文重建，没有收益。"

### Q5【B 项目机制】：Agent 之间的通信（A2A）怎么设计的？

**当时的回答：**
> "我们在 A to A 的通信里面，其实是我们没有做特别具体是特别设计，我们其实是相当于暴露成了一个工具。DeerFlow 它这个 loop 是看你的输出，如果你的输出是工具信息，它就会持续下去，如果是纯文本、非工具的响应信息，它就会直接停止这个 loop。所以当时是把这个 agent 跟 agent 之间调用变成了一个工具的调用……好像是 ACP，就是把 subagent 当成工具这样调，我们调用某个工具就相当于发了某一段 prompt 给这个 agent，然后我们会用这个工具新起一个 agent，把这个 prompt 组装起来，把这个 agent call 起来。"

**评分：**
- ①落点 ✅ 直给"暴露成一个工具"
- ②诊断 ⚠️ **段②空缺**——完全没提这个设计的代价：把 agent 当工具调用意味着子 agent 拿不到父 agent 的完整历史、也无法反向追问，只能一问一答，复杂协作场景下会信息缺失
- ③机制 ✅ 交代清楚：DeerFlow 的 loop 判定规则（工具输出继续/纯文本停止）→ 工具调用即组装 prompt → 起新 agent 执行，机制完整
- ④口径 ⚠️ **"我们没有做特别具体设计"是『没有』开局，且后面自己也说"好像是 ACP""我忘了是不是纯工具的调用"——不确定用词密集**

**改进后的回答（把"没有做设计"翻译成"做了一个选择"，并补代价）：**
> "我们的选择是**把 agent-to-agent 调用收敛成 agent-to-tool 调用**——不是没设计，是刻意不做双向对话协议：调用方发一段组装好的 prompt，被调用方跑完一轮 loop（工具调用就继续、纯文本就停止），把结果当工具返回值传回来。
> 这个选择的代价很明确：**子 agent 拿不到父 agent 的完整推理历史，也没法反问澄清**，只能靠调用方在 prompt 里把上下文喂全。我们能接受这个代价，是因为职责边界本来就切得很清楚——生成 agent 和 review agent 是纯粹的生产者/消费者关系，不需要来回商量。**如果换成两个 agent 需要多轮协商才能收敛的场景（比如两边各持部分信息、要对齐认知），这套单向工具调用就不够用了，得换成真正的双向消息协议。**"

### Q6【B 项目机制】：这种调用方式里遇到什么复杂问题？

**当时的回答：**
> "最大的问题就是时间上，因为我们本质上是把一个 agent 变成两个 agent，然后他们串行。如果出现错误的话，我们这个 agent 还要重新调用工具升级这个错误，让生成回答 agent 重新再回答。所以我觉得最大的问题是执行时间的问题，特别是我们是面向用户的一些 agent，回答时间比较久。解决方案是先把生成的回答先生成出来，然后我们再进行审核，出了问题我们再拼用户，弹出用户说这个回答出错了，通过这样的方式来给到一个后续的更新推送给用户消息。既保证准确率，也保证一个实时度，不然的话把整套生成加审核走完，时间是要翻倍的。"

**评分：**
- ①落点 ✅ 直给"时间问题"
- ②诊断 ✅ 具体（串行导致延迟翻倍，出错还要额外一轮重试）
- ③机制 ✅ 给出明确方案：**先返回生成结果 → 异步审核 → 有问题再推送更新**，有裁决点（审核判定）和后续动作（推送更新），机制完整
- ④口径 ✅ 无问题

这题答得好，全场机制最扎实的题之一，不需要大改。

### Q7【B 项目机制】：subagent 机制的问题

**当时的回答：**
> "DeerFlow 原本有一个 subagent 机制，能通过 subagent 模式阅读不同的代码，最终生成一个比较 summary 的回答，但是我们当时后来是把这个 subagent 给禁用掉了。主要是考虑到它这个任务分得不是很清楚，大语言模型或者我们给的 prompt 没有能力把所有任务拆分成每一个有边界的、比较简单的任务，所以会把相互交叉并且比较困难的任务给派发给 subagent，这时候 subagent 因为它的 loop 次数、prompt、模型调用限制都有一定的限制，导致最终会出现超过调研次数的报错。而且它不固定，你不知道它什么时候起、什么时候不起，是模型自己决定的，不好复现。包括说它涉及到一些多线程的问题，包括 loop 次数调用问题，报错返回给 main agent 的 prompt 位置的问题，从前端切面到后端都会有一定的 bug。并且我们也没想到一个很好的拆分环节——一开始想过按仓库分，但按仓库分没办法很好理清整个调用链的环节，我们更希望它能把所有仓库整个调用链给捋清楚，所以最后把这个小 agent 的方案给取消掉了。"

**评分：**
- ①落点 ⚠️ 先讲"原本有这个机制"再讲"后来禁用了"再讲原因，结论藏在中间，铺垫略多
- ②诊断 ✅ 具体到位：任务拆分不清→交叉任务派给 subagent→超限报错；不确定性导致不可复现；多线程/报错定位有 bug
- ③机制 —（这题问的是"出了什么问题"不是"怎么修"，面试官没追问改进方案，暂不强制扣分，但候选人自己提到"没想到一个很好的拆分方案"说明这块本身就是空的）
- ④口径 ✅ 无问题

**改进后的回答（把结论提到最前面）：**
> "我们最后把 subagent 机制禁用了——**根因是任务边界这件事我们没能可靠地自动化**，只能靠模型自己判断该不该拆、拆给谁，而模型在这件事上不稳定：交叉度高、边界模糊的任务经常被错误地派给 subagent，subagent 自己的调用次数/token 有硬限制，一旦任务超出边界就会跑到限制耗尽然后报错，而且**这个报错本身不可复现**——是否触发 subagent 是模型当场决定的，同样的输入下一次可能就不触发了。我们也试过按代码仓库做静态拆分来替代模型自主判断，但业务要求的是把**跨仓库的完整调用链**捋清楚，按仓库切反而把一条链切断了，所以最后选择了不用 subagent、由主 agent 自己顺序遍历调用链，牺牲一些并行度换稳定性。"

### Q8【C 通用知识 / 对比分析】：面试官分享另一位候选人（字节 oncall agent）的方案——把决策树**预编译**成 workflow，问你听完这个思路后，跟你们现在的方案比怎么样？

**当时的回答：**
> "我觉得他的一个 oncall 机器人更多的是回答用户，我们是回答内部看代码的一个 agent，他更像是一个回答用户的客服机器人。他这个预编译的决策树更像一个 LLM wiki 的形式，把所有解决方案放到了一棵树里面/一个 map 里面，根据这个 map 一步步导航，去把所有的可能性都找到。可能在我们这里，我们在前置用户问题、自然语言到代码的时候，也会存在这个 LLM wiki 来做匹配——一个用户的关键词具体到是代码的 code，比如说网红达人对应 influencer，会有这样 code 的名词对应参照，以及具体业务语义的解释和关键代码仓库的位置，所以我们也有类似的预编译逻辑。
> 另外我觉得在我们的决策树场景比较难做：首先我们没有一个很 general 的 root 节点，我们这个决策树的 root 节点是根据用户问题来定义的……不是一个很 general 的 root，更像是一个扩散的过程。另外我们的状态特别多，一个订单状态可能就有 20 多种可能性，Mesh mode 有 8 种，玩法有五六种，相互插进来整个数是非常大、非常昂贵的一件事，我觉得在我们场景下面这个数运转起来本身就是一件很复杂的事，我们难以做到。我觉得最重要的还是没有一个很 general 的节点，你怎么从一个 general 的节点到最终的 leaf 节点。"

**面试官追问：** 这样听下来你们不像典型的树，更像网状？
**当时的回答：** 是的，更像 graph，但希望能从某一点（用户 query 有一定范围限制）进行延伸，所以种成了树的一个状态。

**评分（🔴 2026-08-14 重评，原评分把「组合爆炸」记成 ✅，那是判高了）：**
- ①落点 ⚠️ 逐点对比展开，但没有先给一句总论断，读者要看完全部才拼出结论
- ②诊断 🔴 **「状态组合爆炸所以编不完」这个论证有洞**——workflow 的节点数是**流程长度**，不是**状态的笛卡尔积**。面试官只要问一句「我的 workflow 就五个节点，跟你有多少种订单状态有什么关系」就拆了。**量化本身很好，但用错了地方。**
- ③机制 🔴 **两处空缺**：(a) 没拆开「预编译的是什么」就开始反驳，听起来像"workflow 我们做不了"；(b) **没说自己已经在用 workflow**——门禁 + review agent 那段节点固定、流转确定，本身就是
- ④口径 🔴 **「我们难以做到」是「没有」开局的变体**（本场待改第一条同款）

**改进后的回答（先拆词 → 质的论证 → 亮自己的混合方案 → 给下一步）：**
> 「**我们俩其实是同一个思路的两种落法——都在用预编译换运行时的搜索成本，区别是预编译的对象不同。**
>
> **他预编译的是答案空间。** oncall 的故障类型有限且重复，所以能把「什么现象 → 查什么」整棵树离线固化，运行时只是导航。**这在他的场景里是对的选择。**
>
> **我们预编译不了答案空间，但原因不是分支多，是分支是什么运行前不知道。** 这棵树的 root 由用户这次问的问题决定，分叉要等 AST 从相关代码里把条件表达式抽出来才成型——**我连节点是什么都不知道，画不成静态图。这跟分支数量无关，就算只有三个分支，只要不知道是哪三个就编不了。**
>
> **但我们确实也预编译了，只是编的是求解流程。** 三条建树约束（节点必须是名词、同层必须同类、一个节点只能一个值）、四个必填字段、门禁校验、review agent 打回——**这些节点固定、流转确定，本身就是一个 workflow。**
>
> **所以准确说是混合的：探索阶段是 agent，交付阶段是 workflow。要的是 workflow 的确定性，但只把确定性加在退出条件上，不加在路径上。**
>
> 要往他那个方向靠一步的话，我会做**局部预编译**——把占 80% query 的那几种玩法组合的子图固化，长尾仍然现场展开。**吃到高频路径的稳定性，又不用维护一棵编不完的全量树。**」

> 📌 完整拆解（含「量的论证 vs 质的论证」对照表）见 [[项目追问/字节答疑Bot]] Q1g。**同题在银河二面以「这方案比较 SOP，为什么不用 workflow」的形式问过一次，字节三面可能第三次出现。**

## 3. 评测数据飞轮方法论

### Q10【C 通用知识】：你在字节做了评测数据飞轮，在谷歌做自演化 memory，这两者有关系。两边实习下来，你觉得现在跑这种自演化方案/飞轮，最关键的点是什么？

**当时的回答：**
> "我思考一下……我觉得最关键的点，一个是数据的数量，第二个是评测的速度。现在是一个 agent 时代，agent 解决一个问题可能一道题就得好几分钟，比如说 50 道题乘 5 分钟就是 250 分钟，评测一次要花很长时间，哪怕并行，LLM 的 request 有托管限制，并发多了会报错。我觉得最重要是怎么能够快速把这个评测数据集给跑完跑全，这是我现在做自动化 memory 比较大的难点——如果评测集特别大特别长，会很耗用户 token，时间也会特别久，可能得用到好几个小时，对用户不可接受，对我这种不断迭代的过程来说，跑一次几个小时，一天只能跑两三次，也很难接受。所以最重要的是有没有一个高效的办法能把评测数据集全部跑完，或者能不能选到一些比较 golden 的数据集，它的方差比较小，不会有时候会有时候不会，构建一个比较稳定、不需要重复多次评测的数据集。"

**评分：**
- ①落点 ✅ 停顿后给出"两个点：数据数量+评测速度"，判断明确
- ②诊断 ✅ 量化到位：50 题×5 分钟=250 分钟评测一次、几小时对用户不可接受、一天只能跑两三次——都是具体坏结果，不是"提高效率"这种空话
- ③机制 —（这题问的是"关键点是什么"，机制解法在下一题追问里展开，此处不强制要求）
- ④口径 ✅ 无问题

这题落点和诊断都到位，基本合格。

### Q11【B 项目机制】（面试官追问）：评测速度可以靠加机器/建环境解决，但怎么选到优质 case、case 怎么持续迭代——你们现在有很好的方法解决吗？

**当时的回答：**
> "我现在也在做这个评测，遇到一个大的难点就是方差太大了，你无法确定它到底是变好还是变坏了。我现在的思考是希望能用一个比较综合的数据，不单单是回答的准确率，可能分析它的 latency、call 的次数，包括 input output token 次数，通过综合评分来降低单纯正确答案导致的波动性。另外因为大数据集其实没有那么多资源，只能用小数据集，一个是把这些东西都限制好，另外加更多的 evaluation 方案，另外多天合并会不会是一个更好的选择，因为单轮是有波动的，跑多轮也是一个解决方案。"

**评分：**
- ①落点 ⚠️ 先讲现状（方差太大）再给方案，属于按思考顺序展开，非硬性扣分但不够干脆
- ②诊断 ✅ 具体（单纯准确率导致的波动性大，无法判断变好变坏）
- ③机制 ⚠️ **给了方向（综合评分、多天合并）但没给可执行的判据**——综合评分具体怎么加权 latency/call 次数/token 数，没有说；"多天合并"合并规则（取平均？取最差？）也没说，全程"可能""我思考一下"，机制停在"想法"层面没有落到"规则"
- ④口径 ⚠️ 多次"我觉得""我思考一下""对"这类试探性语气，没有一句"我们现在就是这么做的"的确定表述

**改进后的回答（把想法落成规则）：**
> "我会把这个方差拆成两个来源分别处理，而不是笼统地『降低波动』：
> **来源一：打分维度单一。** 只看『答没答对』，一次幸运/不幸运的生成就能翻转结果。改成**加权综合分**——正确率占大头（比如 60%），latency 和 token 消耗占小头（各 20%），**权重按业务实际在意的顺序定，不是拍脑袋**：如果这次迭代的目标是降本，token 权重就调高；目标是提准确率，就把正确率权重进一步拉大到 80%。分数固定公式后，波动会从『答对答错的二元跳变』变成『连续分数的小幅漂移』，更容易看出趋势。
> **来源二：单次采样的随机性。** 大模型生成本身有随机性，一次跑不出真实水平。**规则是：同一版本连续跑 3 天，取中位数而不是均值**（中位数对单次异常更鲁棒），只有中位数连续两个版本之间的差超过某个阈值，才判定为『真的变了』，否则算噪声。这样即使小数据集，也能用『多天』把统计力补回来。"

### Q13【B 项目机制】：60 条 case 怎么持续迭代跟得上 agent 发展速度？怎么判断一条 case 是优质 case？

**当时的回答：**
> "我得看能不能稳定复现，能不能稳定复现是我希望的一个很优质的 case，就是它不会一会会一会不会，这样导致方差太大，我无法看出有效数据。我希望的 case 要不就是会或不会（比较确定），要不就是它对 latency、input output token 影响特别大的一些数据，我可能会从这方面来进行判断。"

**评分：**
- ①落点 ✅ 直给"能不能稳定复现"
- ②诊断 ⚠️ 和 Q11 内容重叠（方差大导致无法看出有效数据），属于重复表述，没有新增信息
- ③机制 ⚠️ **只定义了"优质 case 长什么样"，没说怎么操作性地筛出这类 case**——比如同一 case 连续跑几次算"稳定复现"、跑几次不一致就淘汰，这个操作规则没给
- ④口径 ✅ 无问题

**改进后的回答（补操作规则）：**
> "标准是能不能稳定复现，但光有标准不够，得有个能落地的检验流程：**新 case 候选先跑 5 次，5 次结果的正确性方差如果超过阈值（比如 5 次里对错不一致），直接淘汰，不进入正式评测集**——这样保证进集合的 case 本身就是低噪声的，不需要靠事后统计去猜是 case 不稳定还是模型真的变了。同时按你说的第二类，专门留一部分对 token/latency 影响大的 case（比如触发长链路工具调用的问题），这类 case 哪怕正确率一直是对的，也留着用来监控效率退化。"

### Q14+15【B 项目机制】（面试官连续追问，两问一起答）：假设最开始 60 条 case（编号 1-60），一开始只能答对 45 条，迭代后能答对 55 条，剩下 5 条 badcase 可能是天花板一直答不上，但用户问题会越来越刁钻、不断有新问题。case 集要么变大要么替换旧 case。**第一个问题：你是靠人肉去选新 case 进来吗？第二个问题：如果不想让 case 集越来越大，替换时怎么筛掉谁？**

**当时的回答：**
> "首先替换这方面我觉得挺好回答，就是那些一定能做对的、比较 basic knowledge 的东西我就把它替换掉——我越做到后面，理论上模型能力应该越来越强，那些 basic 的东西、不需要 memory 也能回答正确的 case，在后期就能把它替换掉。我们能做一个后台统计，每条 case 回答准确的次数是多少，把回答准确次数比较多的再做一轮测试，看它不需要 memory 时候回答的可能性，把能回答比较准确率比较高的剔除掉。
> 维护确实是一个很难的问题，我们当时是考虑到用户可能一周问几十条到一两百条问题，但我们每周就捞 10 条出来给专家做评价，每周花半小时其实并不多，特别是针对我们数据集量不特别大的话，每周能存个 5、6、10 个已经是很 enough，累积一两个月在我们场景里已经是非常可观的数据集数量。这个时候再从里面挑选大家会认为比较重要的题目，挑选的时候会挑那些专门用户打过差评的——我们有差评好评按钮或者表情，会专门把这些数据挑出来，然后专家来做评测。"

**评分：**
- ①落点 ✅ 直接说"替换这方面我觉得挺好回答"然后给标准，落点干脆
- ②诊断 ✅ 具体（basic case 不需要 memory 也能对→可以退休；用户反馈里差评优先级最高）
- ③机制 ✅ **全场机制最完整的一题**：有明确判据（后台统计准确次数→高准确率 case 做去 memory 测试→能对就剔除）和明确操作流程（每周捞 10 条→专家评价→按差评优先→累积一两个月形成可观数据集），闭环清楚
- ④口径 ✅ 无问题

这题答得最扎实，不需要大改，可以直接背这版。
