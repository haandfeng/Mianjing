## 2. 介绍你最熟悉的一个 agent 项目：目标、你的职责、怎么做的

**当时：** 选了字节答疑 Bot。
- 背景：业务文档、产品 PRD 都过时，**所有代码逻辑真相都集中在代码仓库里**，但仓库有很多个、不同工程师开发、彼此不理解对方的业务逻辑。运营、产品、研发要开新 feature 或用户提问时，都得深入代码里查
- 目标：做一个 oncall 机器人回答业务卡点问题，**减少研发回答问题的时间**
- 难点：直接用 Claude Code、Codex、OpenClaw 这类框架读代码，它们**看到一些相关文档就停止回答，生成一个以偏概全的答案**。举例：一个状态到另一个状态的转移有 A/B/C/D/E 五种，它只答出三种、漏了两种，而且 D 在某些情况下不能转移——它没看到就说能转
- 解法三块：**① 决策树**——给 agent 决策树工具，让它自己构建所有可能性，并在输出答案时**校验整个决策树的状态**，保证树被完整构建 ②**AST 代码解析工具**——把代码里所有 if-else 骨架提取出来，让 agent **不需要阅读完整代码**就知道存在哪些枚举、哪些可能性 ③**re-review**——因为仓库多、上下文长，最终回答会出现幻觉（A 能转到 B 说成 A 能转到 G），必须再加一层复查，**保证「可以漏，但不能错」**

✅ **「可以漏，但不能错」这个收口很好**——它把两类错误的优先级讲清楚了，而且直接解释了为什么要多加一个 agent。**这句话之前几场没说过，保留。**

🔴 **整段零数字，第三场复发。** [[项目追问/字节答疑Bot]] 的数字口径表就在那里：**56% → 87%、200+ 用户、50+ 题评测集**。而且这场后面（§14）专门问了评测飞轮——**送到嘴边都没接住。**

⚠️ 另一处：**「减少研发回答问题的时间、提高效率」是定性的**。这里正是报「200+ 用户在用」的位置。

**改进稿（只改开头和结尾两句，中间原封不动）：**

> **开头补一句量级**：「这个 Bot 现在服务 **200 多个**产品、运营和研发。它要解决的问题是……」
> **结尾补一句消融**：「效果我是用一个 **50 多道题的专家评测集**量的，每题是分点式 rubric、AI 按得分点判卷。**裸框架纯看代码是 56%，加了决策树门禁到 70% 出头，再加审核 agent 到 87%。** 我特意把这两块分开测过——**门禁治的是『列不全』，审核 agent 治的是『总结时说错』，两种病不重叠，这就是两个都保留的原因。**」

**题型 A｜扣分：② 诊断（零数字，第三场复发）**

## 3. 多 agent 编排这块是怎么做的？

**当时：⚠️ 自我缩小开局，但机制讲清楚了**

> 「多 agent 编排其实主要就是**我们其实只有两个 agent，没有一些……**」

然后讲清楚了流程：生成回答的 agent 看代码、生成决策树、生成回答 → 把**生成的回答 + 用户的问题 + 决策树**给到 review agent → review agent 检查回答是否正确、是否有遗漏 →
- 发现**不正确** → 调用一个**升级工具**，重新调用回原来那个 agent，相当于用户又注入了一个问题，告诉它哪里做错了，让它重新生成一轮
- 只有**遗漏**没有事实错误 → 把遗漏输出出来告知用户，**问他是否需要让生成 agent 再去探索这些遗漏方向，还是原版答案已经够了**

✅ **「事实错误直接打回 / 遗漏交给用户裁决」这个双层响应机制答对了**，跟 [[项目追问/字节答疑Bot]] Q2c 的定稿一致。**这一层是把「review agent 误判」的代价限制住的关键设计，能主动说出来是加分。**

🔴 **但开局那句「其实只有两个 agent，没有一些……」是典型的自我缩小。** 面试官问的是**编排**，不是**数量**。两个 agent 的编排不比五个 agent 差——**差的是你自己先把它说小了。**

**改进稿（换开局，内容一个字不改）：**

> 「是一条**两站的流水线，外加一条回退通道**：生成 → 审核，审核可以把流程打回上一站。
> **只做两个 agent 是有意的**——每多一个 agent 就多一次完整的上下文重建和一遍代码探索，延迟和 token 都是线性涨的。**我们只在收益能说清楚的地方拆**：审核这一站的收益是明确的——主 agent 跑了几十轮工具调用之后注意力已经稀释了，**换一个干净上下文重新对着决策树核对,是它自己再想一轮做不到的**。再往下拆（比如单独拆一个反问 agent）收益就说不清了，所以没拆。
> 下面讲这两站之间怎么流转……」

**题型 B（项目机制）｜扣分：① 落点（自我缩小开局）**

## 4. 🔴 agent 与 agent 之间的通信是怎么做的？

**当时：🔴「没有」开局，但后面自己找补出了两条真实的通信机制**

> 「哦，我们**没有做一个具体通信**，因为它们其实更多的是一个串行的逻辑，它们并没有并行运行，不需要一个通信。」

然后补了两条：
1. 这些信息都**记录在日志、记录在数据库里**，所以能很轻易地把它们全部拿到、传递给另一个 agent。「我们可能只是**简单地用代码读取日志**，把关键信息发送给 agent，当成一个 prompt 启动 agent 就好了」
2. 「另外我觉得算它一点通信的就是这个**升级**——review agent 发现存在问题时会调用升级工具，**在升级工具里面填这个 prompt 当成一个参数**，告诉它有什么错误。这个 prompt 会**再组装成用户的 input** 给生成回答的 agent，这算是个通信」

🔴 **三个问题：**
1. **「没有做具体通信」是错的，而且是你自己在同一段话里推翻的。** 你有共享状态、有回灌通道，这就是通信。**说「没有」不是谦虚，是把一个有设计的东西讲成了一个没做的东西。**
2. **「简单地用代码读取日志」这个说法很危险**——听起来像是拿运行日志当数据源。真实情况是框架的 state（结构化状态）落在数据库里，**日志和状态是两个东西，混着说会让人怀疑你的系统是拿日志当持久化。**
3. **这是「没有 / 没做到」开局的第 N 次复发**，[[资料/面经/字节/中国商业化/字节商业化AgentInfra二面_2026-08-06]] 那场一场里说了 6 次。**这场也说了 3 次（§3、§4、§10）。**

**改进稿（先给形态，再给两条通路，最后说为什么这个场景该这么选）：**

> 「**是通信的，但载体是共享状态不是消息，我说一下为什么。**
> 两个 agent 是**串行**的，有明确的先后依赖，所以不需要运行时的点对点消息。它们之间有两条通路：
>
> **① 结构化状态（正向）**：决策树、答案草稿、用户原始问题都在框架的 state 里，跟着 checkpoint 一起落库。审核 agent 启动时，是**用代码把这几样组装成一条新的用户输入**喂给它——**它拿到的是压缩后的结构化输入，而不是主 agent 那几十轮探索的原始上下文，这正是它有效的原因。**
>
> **② 升级工具（反向）**：审核 agent 发现事实性错误时调一个升级工具，工具的入参就是它写的那段说明；这段说明被**组装成一条新的用户消息回灌给生成 agent**。
> **这里有个我认为很关键的设计选择：从生成 agent 的视角看，审核意见跟用户追问长得一模一样。** 这是有意的——**它不需要为『审核』这个来源单独设计一套处理逻辑，复用已有的『收到新输入就重新回答』路径就行。**」

**再补一句把它抬到通用层（这题面试官多半在测这个）：**

> 「多 agent 之间的通信一般就三种形态，我们选的是第一种：

| 形态 | 载体 | 什么时候选 |
|---|---|---|
| **共享状态**（黑板模式） | 一份所有 agent 都能读写的公共状态 / 数据库 | **串行、有明确先后依赖**——省一层协议，且天然可回放 |
| **消息传递** | 消息队列或直接调用，点对点 | **并行**、需要谁跟谁单独说话 |
| **把 agent 当工具** | 父 agent 用工具调用子 agent，**返回值就是通信内容** | **主从（subagent）**，子 agent 的上下文对父不可见 |

> **我们是第一种，因为流程是串行的；如果哪天要做并行探索，才需要考虑第二种，那时候真正麻烦的不是通信本身，是并行分支的结果怎么合并。**」

> 💡 **术语（C 档，仓库里搜不到，先立定义）**：**黑板模式（blackboard）**——多个组件不互相直接调用，而是**都读写同一份公共状态**，谁需要什么就自己去这块「黑板」上取，谁产出了什么就写回去。它的好处是组件之间零耦合、状态天然可回放；代价是并发写要自己管冲突。**LangGraph 的 state 就是这个模式。**

**题型 B｜扣分：🔴 ① 落点（「没有」开局，且被自己后半段推翻）+ ④ 口径（把 state 说成日志）**

## 5. ✅ agentic 里面 skill、workflow、tool、agent 各自的职责和边界？

**当时：✅ 本场答得最完整的一题**

- **tool（工具）**：「更多的是一个 agent 真正的**手脚**」——给 agent 加入更多功能，比如读邮箱、写日历，这些它自己做不了。或者它单靠推理做不好的（比如算数），给一个计算工具能保证结果更准确
- **skill**：「我理解它更像是一个 **prompt**，更多的是一个**流程的编排**，它就像一个**说明书**，告诉 agent 你要怎么把多个工具组合起来怎么使用、每个工具怎么串联在一起」——像 prompt 一样的 workflow
- **workflow**：「更多的是一个比较**硬编码**的东西。skill 是 prompt 还是比较偏软的，**agent 不一定会按照你定义好的流程来做**；workflow 像 Claude Code 推出的那个 workflow 功能，**能够通过 JS 编码定义好整个 agent 的每一个流程、每个节点要走到什么状态**，是一个更硬的选择，能保证更好的编排」

✅✅ **三个都答对了，而且「软 / 硬」这条轴是对的**——skill 是建议，workflow 是执行。
✅ **点名了 Claude Code 的 dynamic workflow 是 JS 脚本编排——这是 2026-06 才出的功能，说明在跟最新的东西。** 这个动作在 agent 岗上很值钱。

> 📌 **事实核对（可以放心讲）**：Claude Code 的 **dynamic workflows** 于 **2026-06-02** 发布——Claude 为你的任务**写一个 JavaScript 脚本**，脚本本身就是编排器，由独立 runtime 在后台执行；单次运行最多 16 个 subagent 并发、上限 1000 个。**关键点是：编排逻辑（循环、过滤、路由）跑的是普通代码，不花模型 token。**
> <!-- 来源: Claude Code 官方文档 code.claude.com/docs/en/workflows + 社区解析 ・ 查证于 2026-08-10 -->

**唯一可以补的一句（把四个词收进一句判据）：**

> 「如果要一句话收口，我会按**『谁掌握流程的控制权』**排：
> **tool 是能力**——它不掌握任何流程，只是被调用。
> **agent 是控制权本身**——流程由模型在运行时自己决定。
> **skill 是喂给模型的建议**——控制权还在模型手里，**所以它做不到强制**。
> **workflow 是把控制权从模型手里拿回代码里**——节点和边写死，模型只在节点内部做局部推理。
> **所以 skill 和 workflow 不是同一个坐标轴上的两档，是控制权归属完全相反的两个东西**：skill 能给模型知识，给不了它约束。」

**题型 C（通用知识）｜无扣分 ✅**

## 6. ✅ 什么时候会用 skill？什么时候用 workflow？

**当时：✅ 有具体例子、有反例**

- **skill**：更加自由开放的形式。如果你**不希望 agent 走一些非常固定的流程**、希望它足够抽象、能泛化到所有流程里，就用 skill
- **例子（很好）**：简单的数据分析——读数据 → 分析数据 → 生成报告。「如果你用 skill，它比较 general 比较泛化，**有可能你一开始的历史记录里面就已经有数据了，那它就不会走读数据这一步**，能让 agent 有个比较自由的路径选择」
- **workflow**：强行的 workflow 必须经过读数据、分析数据、生成报告每一个节点，「这样会**让 agent 缺乏探索性**；不仅如此，原本已经有历史记录你还让它再做一遍，就是**浪费时间、浪费 token，循环变多**」
- 收口：「主要还是看你希不希望让 agent 的整体流程固定下来，以及**这个 workflow 能否适用于绝大多数场景**。如果不同场景就要建不同 workflow，那太麻烦了。**不适用于绝大多数场景的话，我建议先用 skill 做初步尝试，实在不行再转成 workflow。**」

✅✅ **「历史记录里已经有数据，skill 会跳过读数据这一步」是这题最好的一句**——它用一个具体的执行差异说明了「自由」到底自由在哪，而不是停在形容词上。
✅ **「先 skill 后 workflow」的演进建议也对**，跟 [[Agent设计模式与MCP]] 的选型判据一致。

**可以补的一句（把「适用于多数场景」换成可判断的条件）：**

> 「我判断的时候其实就问一个问题：**这个流程的分支，在运行前是不是就已经知道了？**
> 知道 → 能画成图 → **workflow**。
> 不知道，要跑起来才知道有几条分支 → **画不出图，只能给目标和工具箱** → **agent + skill**。
> **我在字节那个项目就卡在这条线上**：决策树上有几个分支、长什么样，完全取决于用户问的问题牵扯到哪几段代码，**是运行时 AST 提取出来才知道的，没法提前画成静态图**。所以我们选的是『**动态循环 + 静态门禁**』——路径让模型自己走，但**退出条件写死在框架里**。要的是 workflow 的确定性，但只把确定性加在退出条件上，不加在路径上。」

**题型 C｜无扣分 ✅**

## 7. ✅ 实际场景中，workflow 在哪些场景下是必须的？

**当时：⚠️ 两次「稍等，我想好了」卡顿，但三条内容都对**

1. **流程已经沉淀成规范**：「你对这个流程有一个比较清晰的认知，已经沉淀成整个公司或整个流程的**系统性规范**，每一步怎么走已经比较确定」
2. **每步都要可验证**：「你希望它每一步都生成 structure 一样的 output，**每一步的信息都能够被验证**；你不希望某一步做错了但你不能 trace 是哪一步做错的，**你希望有一个 debug 的过程**」
3. **成本**：「现在是 2026 年，agent 是比较新起的年代，因为 model 能力足够强、能足够遵循指令、能做很多聪明的自我探索。**但如果退回到 2025 年的模型，它可能还做不到这样的事。** 如果考虑成本，用 workflow 也是很不错的选择——你不需要让大语言模型自主探索，把整体流程固定好，它做一些比较死板的工作就好」

✅ **第 2 条最好**——「不能 trace 是哪一步错的」是 workflow 唯一不可替代的价值，而且他把它讲成了一个**具体坏结果**（debug 不了），不是抽象的「可控性」。
✅ **第 3 条那个时间维度很少有人说**——把「用不用 workflow」跟「模型能力代际」挂钩，这是有观察的人才会讲的角度。

**可以补的第 4 条（三条里缺的那一类，也是最刚性的一类）：**

> 「还有一类我觉得是**真正必须**、前三条只是『更好』：**流程本身有合规或审计要求的时候。**
> 比如涉及资金、权限变更、对外发布的动作——**必须能证明『这一步之前一定执行了那一步』**。agent loop 给不了这个保证，因为它的路径是概率的，你只能证明这次跑了什么，不能证明每次都会跑。
> **workflow 能给的是『结构性保证』而不是『大概率』**——节点和边是代码，**审计的时候看的是代码，不是一堆 trace 样本**。
> 所以我会这样分：**前三条是 workflow 更划算的场景，这一条是 agent 根本不能用的场景。**」

**题型 C｜扣分：① 落点（两次「稍等，我想好了」）**

## 8. ✅ 什么是 agent 的上下文工程？

**当时：✅ 定义准确，机制也对**

- 定义：「**在合适的时间给它合适的 prompt**，这是我觉得最重要的一件事」
- 为什么需要：agent 的 **attention 注意力机制是不足的**。① 给太多上下文，**context 窗口会爆掉**，没办法做输出和推理 ② 即使不爆，**它也没办法很好地注意到整个 context 里的细节内容，因为注意力不够**
- 机制：「更重要的是**在他需要某些信息的时间，给到他对应的信息**。具体来讲就像 skill 一样——**skill 是渐进式暴露的**，你可以把 description 跟标题给到 agent，**当他真正需要某个 skill 的时候，才让他读出来**」

✅ **「渐进式暴露」这个机制答对了，而且举的例子正好是 skill**，跟 [[Agent设计模式与MCP]] 里的三级成本表一致（L1 元数据约 100 token 常驻 → L2 正文触发才读 → L3 附带资源用到才加载）。
⚠️ **一处口误**：「dress in time」——正确说法是 **just-in-time（JIT，即时的、用到才给）**。这个词是上下文工程的标准术语，说错了会被听出来。

**可以补的两条（他项目里都有，一条都没说）：**

> 「我一般把上下文工程拆成**进和出**两半：
>
> **进——什么时候放什么进来**：就是刚说的 just-in-time，skill 的渐进式披露是最典型的实现。**我在项目里做的是另一种：工具返回值太大就落盘，只给模型一个路径，它要看再自己读。**
>
> **出——什么时候把东西拿走**：这一半更容易被忽略，但长任务里它才是瓶颈。这里有个我认为很重要的区分——**压缩的第一问不是『压多少』，是『压完还能不能还原』**：
> - **可逆压缩**：去掉能从外部状态重建的字段（文件已经落盘了，就只留路径丢掉内容，要看重新读）——**这个可以一直做**
> - **不可逆摘要**：让模型把旧的几轮压成一段话——**只在可逆压缩收益递减之后才做**
>
> 还有两条我自己踩出来的细节：**最近几轮的工具调用要保留原始格式**（压成摘要，模型连输出格式都会飘）；**错误堆栈绝对不能压**——直觉上报错是垃圾该删，**但它是模型唯一的负反馈来源，删了它会一遍遍犯同一个错。**」

**题型 C｜扣分：④ 口径（just-in-time 说成 dress in time；只讲了「进」没讲「出」）**

## 9. 企业级的 agent 应该具备哪些能力？

**当时：⚠️ 框架其实对，但三条全是形容词，没有判据**

1. **可解释性**（说了两次「稍等啊」）：「你能解释这个 agent 它每一个轨迹、它为什么走到这个 step，**能够 debug，或者分析它为什么走错**」
2. **可用**：「尽可能多人能顺利用到你这个 agent，可能需要**适配不同模型**来保证稳定性，**agent 的实例要足够多**，能面向不同用户、在任何时间都能使用到」
3. **稳定 / 职责边界**：「一定要把它的**职责范围圈住**，不能让它做超出职责范围的东西、输出一些不应该输出的东西」
4. 收口：「可能还得具体场景具体分析，这是我暂时想到的一些东西」

🔴 **问题不在选的维度错，而在每一条都停在了「希望它是这样」，没有给出「怎么判断它做到了」。** 三条分别对应的其实是可观测、可伸缩、可控——**方向全对**，但面试官听到的是三个形容词。

> 💡 **这正是四项评分里「③ 机制」那一项的典型扣分形态**：「会检查」「要稳定」「要能 debug」是愿望；**「谁拿什么判、不过怎么办」才是机制。**

**改进稿（同样五条，但每条挂一个可判断的问题）：**

> 「我按『**出了事谁能证明什么**』来排，五条，前两条是本质，后三条是工程：
>
> **① 可观测**——每一步的输入、输出、工具调用、耗时、token 全量落库，能按会话 ID 完整回放。
> **判据：线上出现一个错答，你能不能在五分钟内定位到是哪一步坏的。** 做不到，后面所有优化都是猜。
>
> **② 可评测**——有带标准答案的离线回归集，加上线上的代理指标（proxy metric，没有标准答案时用来间接反映效果的可观测行为，比如用户追问率、转人工率）。
> **判据：你改了一版 prompt，能不能说出它是变好还是变坏。** 说不出，那所有迭代都是口味之争。
> **⭐ 这条是 demo 和产品真正的分界线**，而且它是我在字节和谷歌两段实习里都在做的事。
>
> **③ 可控**——身份透传到工具层做鉴权、工具集做减法、危险动作要人确认。
> **判据：agent 是拿谁的权限在干活？** 如果是服务账号，那**任何能给它发消息的人，都间接拥有了服务账号的全部权限**——这个问题有正式名字叫 **confused deputy（混淆代理人）**：一个高权限程序被低权限的人诱导着做了它有权、而请求者无权的事。
>
> **④ 可恢复**——状态在进程外，实例挂了能从上一个节点接着跑，不是整次任务作废。
> **判据：一个跑了三分钟、二十轮工具调用的任务，进程重启之后是接着跑还是重来？**
>
> **⑤ 可交付**——多租户隔离、限流、灰度、成本能按团队核算。
>
> **一句收口：企业级和 demo 的差别不在能力，在『能不能对它的输出负责』——前四条全是在回答『出了问题你怎么证明和怎么修』。**」

**题型 C｜扣分：③ 机制（三条全是形容词，无判据）**

## 10. 你在做飞书那个答疑工具的时候，有没有想过构建一个知识库？

**当时：⚠️「不是我负责的」第五次划边界，但机制讲清楚了**

- 「知识库这方面我们是有的。agent 生成回答时会**先看知识库**，根据用户的自然语言跟知识库做一个 **mapping**——**自然语言跟具体代码仓库的 mapping**」
- 🔴 「**这个是我们另外一个组的同学在做的**……我主要没负责这一块，**所以我没有说我做这个**……**所以我没有写在简历上**」
- 机制（讲得挺清楚）：「基于 **LLM wiki** 的形式——把 PRD、设计稿、设计文档全部爬下来，代码也爬下来，让大语言模型生成一个 LLM wiki，**把术语的具体解释以及对应的代码位置都放在那里**」

⚠️ **诚实是对的，但「不是我做的」这个开局已经是第五次了**（[[资料/面经/字节/中国商业化/字节商业化AgentInfra二面_2026-08-06]] §7.3、§24.2 都出现过）。而且**你在那场已经示范过正确姿势**：「我不控制存取，**我控制怎么改写**」——在别人负责的系统里把自己的职责边界说清楚，比说「不是我做的」强一个量级。

**改进稿（同样的事实，换成消费方视角）：**

> 「有，而且它是我这套东西能跑通的前提之一。
> 形态是 **LLM wiki**：把 PRD、设计文档、代码全爬下来，让模型生成一份带**术语解释 + 对应代码位置**的 wiki。**agent 拿用户的自然语言去这份 wiki 里做映射，映射到具体的代码仓库和符号，然后才开始读代码。**
>
> **这块的建设是隔壁组在做，我是它的消费方**——但正因为是消费方，我对它的失败模式反而更敏感，说两个我自己遇到的：
>
> **① 这份 wiki 决定的是召回，不是精度。** 答案完全来自代码，这点没变；**但 wiki 决定了 agent 去读哪段代码**。所以准确说法是：**代码是唯一事实来源，wiki 是检索入口**。**入口错了，agent 依然会给出一个『有代码依据』的答案，只是依据了错的那段代码——而这种错是静默的，用户看不出来。**
>
> **② 我在自己这边加了一层兜底**：一个业务术语表，把中文业务词映射到代码里的英文符号。**这是因为 wiki 覆盖不到的词，agent 会自己挑一个长得像的变量当成它**——玩法 A 没进文档，它就找一个 A 开头的变量，然后基于错的代码自信地答。」

**题型 B｜扣分：④ 口径（「不是我负责的」第五次划边界）**

## 11. 知识库的上下文命中怎么做？怎么保证它是能命中的？

**当时：✅ 分两路是对的，但弹药只用了一小半**

**先分两套**（这个分法很好）：「看你走哪一套，一个是 **RAG** 这一套，另外是 **LLM wiki** 这一套」

**RAG 路：**
- 「把这个 chunk 切成一个合适的 chunk」
- 「**拿出一个 chunk，不仅仅看单一 chunk，还会把上下文的 chunk 也拉给 agent**」
- 「可以用**关键词检索**、**语义相似度检索**，多种方式来检索，提高命中率」

**LLM wiki 路：**
- 「把这个 **map 写清楚**，可以采用**多级分层的结构**——先来一个总库，总库下面还有一个次总库，一层一层递进」
- 「把 map 写清楚，能让 agent 做更自由的探索、阅读到相关文档」
- 收口：「提高命中率就两块，**一是文档写清楚、把整个导航逻辑和链路提供清楚；二是 agent 的推理能力要足够强，能识别出语义的相似**」

✅ **「分两套」这个开局很好**——它证明你知道这两条路的判定条件不一样。
✅ **「拉相邻 chunk 一起给」这条对**，是提升召回质量最省的一招。

⚠️ **两个问题：**
1. 🔴 **西门子 RAG 的弹药一个都没用。** 你自己做过的东西：**query 改写**（口语/多语言 → 领域术语）、**多路召回**（dense 向量 + BM25 稀疏）、**reranker**（BGE-M3，30 个文档 2 秒）、**按小节切分平均 500 token**、**XML 表格合并的特殊处理**、**按文档 ID 做增量 embedding**。**这题问的正好是这套东西，一条都没报。**
2. ⚠️ **收口第二条「agent 推理能力要足够强」不是方案**——命中率是你能控的，模型能力不是。**用「模型不够强」收口，等于把这题的责任推出去了。**
3. ⚠️ **需要自查**：转录里 chunk 反复被记成 **trunk**。如果现场真的说了 trunk，这是个会被听出来的术语错——**分块叫 chunk（词根是「大块」），trunk 是树干/后备箱，完全不同的词。**

**改进稿（两路各给三层，最后补一条「怎么证明命中了」）：**

> 「**RAG 这一路，我按链路顺序说三层，每一层解决的问题不一样：**
> **① 切分**——按语义边界切不按长度切。我们的手册是**按小节切、平均 500 token**，另外**表格必须特殊处理**：原始 XML 里能做单元格合并，转 markdown 之后合并信息会丢，所以我专门把合并的行**填成一样的内容**再切。**切错了，后面所有检索优化都白做。**
> **② 召回**——单路一定不够，我们走**双路**：dense 向量管语义，BM25 管关键词。**为什么必须要 BM25**：一个 500 token 的文档里可能只有两三个词是关键的——型号、错误码、参数名——**这几个词的信号会被压进同一个向量里稀释掉，语义检索反而找不出来**，而这恰恰是手册类文档里最该命中的东西。另外 **query 改写**在这一层，把用户的口语和多语言表达改写成领域术语再检索。
> **③ 重排**——双路召回回来大约 30 个文档，用 **cross-encoder 重排序器**（把 query 和文档拼在一起过一遍模型打分，比双路各自独立编码准）取前几个。选型上我们用的是 BGE-M3，**因为它 30 个文档大概 2 秒，而千问 3 是 10 个文档 2 秒**——检索阶段延迟直接进用户等待时间，这个差距选不了后者。
>
> **LLM wiki 这一路完全不同：它不检索，它靠 agent 自己导航。** 所以做的是**分层的目录 + 每个条目写清楚『什么问题该来这里』**，让 agent 顺着层级往下走。
>
> **但这两路我都会补同一件事，而且我觉得这才是这题的关键——命中率必须能被度量，否则『写清楚』永远是个形容词。**
> 做法是：拿评测集里的题，**记录 agent 最终实际读了哪些文件，跟人工标注的『本来应该读哪些文件』比对，算一个检索层的召回率**。
> **这个数字一旦有了，两件事就变了**：① 一次错答能拆成『是没找对文件』还是『找对了但答错了』——**这两种病的药完全不同** ② 『该补哪个词、该拆哪个目录』从拍脑袋变成看排序。」

**题型 C｜扣分：② 诊断（自己做过的 RAG 弹药一条没用）+ ④ 口径（chunk / trunk 待自查）**

## 12. ✅ 做多 agent 编排时遇到过哪些难点？怎么解决的？

**当时：✅ 机制讲得很准，⚠️ 但结尾把功劳交给了 AI**

- 难点：「**DeerFlow 本质是一个单 agent 架构**，它就是个 ReAct loop。你要做的所有更新操作，其实本质上都是在这个 loop 上下做一个 **middleware**——在 agent 调用前和调用后，通过 **hook** 的方式做相关操作」
- 「所以虽然我们把它喊成多 agent 架构，但**在代码底层它还是一个单 agent 架构**。怎么把单 agent 改成多 agent，就是我遇到的比较大的难点」
- 解法：「在这个主 loop 之外还必须加入一些新的工具，**在这个 loop 里面再套一个次 loop**，以及**用状态来维护什么时候要把这个 loop 中断**」
- ⚠️ 结尾：「当时确实卡了一段时间……**但当时是用 AI coding，也是顺利把它解决了**」

✅✅ **「它其实还是单 agent，我是在 loop 外面套 loop」这个自我诊断很诚实也很准确**，而且跟 [[项目追问/字节答疑Bot]] Q1f 的定稿口径一致。**主动说破「我们喊它多 agent，但底层是单 agent」比包装成多 agent 强得多——面试官只要问一句『那你们两个 agent 是两个进程吗』就露馅了。**

⚠️ **但「我们当时用 AI coding 顺利把它解决了」这句话把整段的分数削掉了一半。** 前面刚讲完这是个架构难题，**结尾却把解决它的主体换成了工具。**

**改进稿（结尾换一句，其余不动）：**

> 「……难在**怎么设计好主 loop 套次 loop，以及在什么条件下把外层 loop 中断**。
> 卡了一段时间，最后想清楚的是一句话：**问题不在『怎么起第二个 agent』，在『怎么把停止条件从模型手里拿回来』。**
> 原生 ReAct 的退出条件是『模型输出纯文本就算答完了』——**这个条件握在模型手里**。我们做的是在这个位置挂一道门禁：**拦下来检查 state 里的决策树完不完整，不完整就合成一条消息塞回消息列表，让它继续补**；完整了才允许进入下一站。
> **想清楚这一点之后，第二个 agent 反而是顺带的**——它只是门禁通过之后的下一个节点。**难的从来不是多起一个 agent，是重新定义『什么时候算答完了』。**」

**题型 B｜扣分：④ 口径（结尾把设计功劳归给 AI coding）**

## 13. ✅✅ 你的退出逻辑是怎么做的？（全场机制讲得最完整的一段）

**当时：✅✅ 一次讲完，无卡顿，无追问**

- **原生退出**：「单 agent 的退出逻辑就是——**agent 不输出工具信息、只输出纯文本，那就当成退出了**」
- **加的门禁**：「我们加入了专门的一个门禁：**出现纯文本的时候，还需要再校验决策树是否更新好、更新完善**。不完善的话，**必须重新配一条工具信息，把它的文本也当成工具信息，重新进入循环**」
- **完善之后**：「在 middleware 后面再加一层，**单独调用一次 review agent**。这个 agent 如果 OK，他就不会调用工具信息，就直接退出整个大的循环；如果不 OK，他会通过**升级工具**重新升级生成回答的 agent——**本质上也是一条工具信息**，query agent 收到这条工具信息消息，就再次生成」

✅✅ **这一段是全场最好的：它把「退出」这一件事的三种情况全讲了**（原生退出 / 门禁不通过回灌 / 审核不通过升级），而且**统一在同一个机制上——都是「合成一条工具消息塞回消息列表」**。
✅ **「把文本也当成工具信息重新进入循环」这句是这段的核心**——它说明你理解了 ReAct 循环的续跑条件到底是什么。

**可以补的一句（把机制抬到设计层，20 秒）：**

> 「这套的本质是一句话：**把 agent 的停止条件从『模型觉得答完了』改成『决策树上所有分支都验证完了』。**
> 普通 ReAct 循环的退出条件握在模型手里，**我们把它挪到了框架手里**。
> 而且我特意让所有的『继续跑』信号都长成同一个形状——**都是一条合成的工具消息**。这样生成 agent 那边不需要区分『是门禁让我继续』还是『是审核让我重来』，**它只知道『来了新输入，继续干』，一套逻辑覆盖三种情况。**
> **兜底也要说一句：外面还有最大步数上限**，否则决策树如果因为某种原因永远填不满，这个循环是不会自己停的。」

**题型 B｜无扣分 ✅✅**

## 14. 你的评测飞轮是怎么做的？

**当时：✅ 闭环完整、有节奏、有分工，🔴 但又是零数字**

- 每一轮用户问完问题，**把问题记录到数据库**
- **在飞书卡片里搭一个点赞 / 点踩按钮**，用户点了就更新到数据库

- 「研发同学**每周五花个半小时**做一下评测，**每周就能积累一定的数据集**，后续基于此再进行迭代」

✅ **这个飞轮设计有三个值钱的点，而且他都说到了**：① **反馈入口就在用户已经在用的界面里**（飞书卡片按钮，不是额外的表单）② **不写理由也没关系，有兜底**（定时任务人工补）③ **优先捞差评**，因为好评没有信息量。
✅ **「每周五半小时」这个节奏很实**——它说明这套东西是真的在跑，不是设计稿。

🔴 **但整段又是零数字，而且这题是全场最该报数字的地方**：这套飞轮的产出物就是那个 **50+ 题的评测集**，而评测集的结论就是 **56% → 87%**。**问的是飞轮，答的是飞轮的机器，唯独没说它转出来了什么。**

⚠️ 还有一个能主动加分的点没说：**每周捞差评做人工评审，这套东西在评测方法论里有个专门的位置**——它是「线上没有标准答案」这个根本困境的唯一解法。

**改进稿（原来的三段保留，前面加一句结论，后面加两段）：**

> 「**先给结论：这个飞轮到目前为止产出了一个 50 多题的回归评测集，它是我们所有效果数字的来源。** 下面说它怎么转的。
>
> （原来的三段：飞书卡片点赞点踩 → 机器人引导写理由 → 每周五定时任务捞 10 条、优先差评、研发半小时评审）
>
> **补两点我认为是这套东西的关键：**
>
> **① 为什么必须有人工这一环，而不是全自动。** 线上跟离线的根本差别是——**线上没有标准答案**。评测集能算准确率是因为有专家标注，**线上一条问答，没有人告诉你它对不对**。所以点赞点踩只是一个**代理指标**（proxy metric，间接反映效果的可观测行为），它测的是「用户满不满意」不是「答案对不对」——**用户完全可能对一个错答很满意**。人工每周捞差评补标注，就是在把代理指标慢慢转成真标注。
>
> **② 题从哪来，决定了这个数能推广到哪。** 我们这 50 题是**从线上真实 query 里捞出来、人工归纳成常见问题**的。所以有一句我必须主动说清楚：**题源真实 ≠ 分布真实。** 人工归纳这个动作本身就在丢长尾——把相似的合并成一类，而「相似」和「常见」的标准是人定的。**所以 87% 的准确说法是『在这 50 题上』，不能直接说成『线上准确率 87%』。**
>
> **如果继续做，下一步我会补的是转人工率**——用户问完之后**还是去群里 @ 了研发**的比例。**这是唯一一个系统自己刷不高的指标**：追问轮次可以被「答案又长又全但没解决问题」刷低，转人工率不行。」

**题型 B｜扣分：② 诊断（零数字，第三场复发）**

## 15. ✅✅ 你怎么做一个安全且闭环的 vibe coding？人工 review 看哪些内容？

**当时：✅✅ 本场第二好的一段，六个动作全是具体的**

1. **先 brainstorming**：「有个需求过来，我跟他 brainstorming，讨论具体实现、我斟酌的地方，让我知道这个逻辑怎么实现、有什么难点跟异常点」
2. **先写测试样例，并且一定人工 review**：「因为**他测试样例写得非常不靠谱**——虽然我已经让他先写测试样例，但**写得比较直白，基本肯定能测对**，你把代码写出来就是能测的，**他没有测到我需要的一些比较关键的信息**」
3. **强制打日志**：「我会让他把每一步 step 的逻辑——**每个函数、每个 step 的输入输出是什么**——必须把日志写清楚，方便我后续做 review」
4. **跑测试 + 看日志**：「实现完了之后让他跑，把测试结果跑出来，**我会再看他这个日志，看是否符合我预期的输入输出结果**」
5. **⭐ 拷打**：「我会追问他，**相当于我作为人，我会拷打他**——具体这个东西为什么要这样做、这样实现，**直到问到他答不出来，或者我觉得 OK 为止**」
6. **看架构不看行**：「我会看代码的一些抽象、那些类、层次架构有没有写好，不要写得特别乱。**特别细节的代码可能不会一行行过，但整个逻辑我是会有把握**——它的 input 跟 output 长什么样我会有全部的把握，**包括它的 test case，我也会自己完全看明白，明白它在测什么、是否符合我预期**」

✅✅ **第 2 条是全场最有说服力的一句**：「AI 写的测试样例基本肯定能测对，因为它是照着自己要写的代码写的」——**这是真的用过并且被坑过的人才会说的观察**，而且它直接命中了学术界叫 **misguidance effect** 的现象（让写代码的模型自己写测试，测试会向实现的行为对齐，而不是向需求对齐）。
✅✅ **第 5 条「拷打到他答不出来」是一个可执行的验收动作**，比「我会 review」具体一个量级。
✅ **第 6 条那个边界划得很准**：不逐行读，但 **input/output 和 test case 必须完全看懂**——这是在有限时间里能守住的最强防线。

**可以补的一句（把六个动作收进一条判据，30 秒）：**

> 「如果要一句话概括我的原则：**我不 review 代码，我 review 约束。**
> 因为逐行读 AI 生成的代码，收益随代码量迅速衰减；**但约束的数量是有限的、可以穷举的**。我守的是这三样：**需求边界**（brainstorming 阶段定死异常和边界情况）、**验收条件**（测试样例，而且必须我写或我改过）、**接口契约**（每个 step 的 input / output）。
> **这三样任何一样是 AI 定的，整个闭环就断了**——因为它会同时定义『做什么』和『怎么算做对了』。**测试样例那条尤其重要：让写实现的模型自己写测试，它写的是『我这段代码能过的测试』，不是『需求要求的测试』。**」

**题型 C｜无扣分 ✅✅**

## 18. 🔴 编码题：LC11 盛最多水的容器（19 分钟）

> ⚠️ **算法内容不进本仓库**（见 [`CLAUDE.md`](CLAUDE.md) 第 8 条），题目和过程如实记录，**练习去算法那个仓库**。这里只记面试表现。

**题目：** 给一排柱子高度，选两根柱子和 x 轴围成容器，求最大储水量。示例数组是经典的 `[1,8,6,2,5,4,8,3,7]`，答案 **49**。

**过程（31:53 → 50:52，约 19 分钟）：**

| 时间 | 发生了什么 |
|---|---|
| 33:11 | ✅ **面积公式立刻推对**：`min(左, 右) × (右下标 − 左下标)`，并当场算出 `min(8,7) × 7 = 49` |
| 33:46 | 开始想「越往右越大」，**直接跳进了单调栈** |
| 35:14–36:34 | 手工模拟 8→6、8→6→3、8→6→2→5 几组，判断该弹谁 |
| 37:15 | 「捋一下逻辑，我得先写一下」→ 开始写码 |
| 41:01 | 🔴 **「还是错的，我的逻辑没捋清楚」**——回头重新推单调栈该升还是该降 |
| 41:36 | ✅ 想通方向：**要单调递增栈**，因为「left 取决于最左边的 left，高度取 min，所以越大越好、越偏左越好」 |
| 42:44–44:39 | 反复确认弹出条件（栈顶小于当前就弹、等于不弹）和压入条件 |
| 47:23 | 🔴 **「死循环了吗？」** |
| 47:55–49:11 | 加打印、重跑、逐步 trace |
| 50:43 | ✅ 跑出 49 |
| 50:52 | 面试官让他讲思路，✅ **口头复述清晰**：维护单调递增栈记录 index，右指针往左看能遇到的最大值，算面积 |

🔴 **三个问题，都不是「不会做」：**

1. **公式在 1 分钟内就推对了，但接下来 18 分钟花在了一个不必要的数据结构上。** 这题的标准解是**双指针 O(n)**：左右两端往里收，**每次移动矮的那一边**。单调栈能做但绕得多，而且**你自己的调试记录（两次「逻辑没捋清楚」+ 一次死循环）就是它更绕的证据**。
2. **🔴 全程没有跟面试官对过一次解法方向。** 从 33:46 跳进单调栈到 50:43 跑出结果，中间十七分钟是自己跟自己较劲。**面试官只有在你讲出方向时才有机会说「你要不要想想双指针」——你没给他这个机会。**
3. **这是连续第三场编码环节失分，但三次病因不同**：字节一面是 API 记不熟；[[资料/面经/字节/中国商业化/字节商业化AgentInfra二面_2026-08-06]] 是**需求没听清就动手**（26 分钟，被纠正五次）；**这场是需求听清了、公式也对，但没有先比较解法就一头扎进去。**

**下一场编码题的固定开场（这次的版本，跟上一场那条合并成一套）：**

> **第一步——复述需求**（上一场的教训）：「我确认一下输入输出和约束……」
> **第二步——报候选解法和复杂度，然后停下来**（这一场的教训）：
> 「这题面积是 `min(h[l], h[r]) × (r − l)`。我想到两条路：**暴力两重循环 O(n²)**；**双指针 O(n)**——左右两端往里收，每次移动矮的那边，因为移动高的那边宽度必然变小、高度也不会变大，所以不可能更优。**我打算写双指针，你看方向可以吗？**」
> ⏱️ **这两句话加起来 30 秒，但它买到的是：方向被确认过，写错了面试官会在第 3 分钟提醒你，而不是让你在第 17 分钟自己发现死循环。**

**题型 C（通用知识 · 编码）｜扣分：🔴 ① 落点（没报方向直接动手）+ ③ 机制（选了绕路解法，两次逻辑没捋清 + 一次死循环）**

| 面试官说的 | 跟我做过的东西的关系 |
|---|---|
| **创作类 AIGC**（生成内容） | 🔴 **我全部三段 agent 经验都是「查证 / 答对」，不是「生成得好」**——这两者的评测方式根本不同 |
| **图文视频**（多模态） | 🔴 我的经验全是纯文本 |
| **面向 C 端创作者** | 🔴 我的用户全是内部研发和产品，200 人量级 vs C 端百万量级 |
| **通用创作能力**（平台） | ✅ **唯一对得上的**：我在两场面试里被追问过「单实例怎么变成平台」，有准备 |

> 🔑 **面试官把这四点主动说给你听，就是在问「你觉得你能干这个吗」。** 沉默等于默认答案是「不知道」。

**该问的三个（按价值排）：**

> ① **把最大的差异主动摆出来，转成问题**：「我想确认一个我心里的疑问——**我之前做的 agent，好坏是有客观标准的：答案对不对，能拿代码验证。但创作类的输出没有唯一正确答案。所以我很好奇你们怎么衡量一个创作 agent 好不好？** 是靠人工评审、用户行为数据，还是有模型判分的方案？**因为我在字节和谷歌两段都在做评测这件事，我最想知道的是它在创作场景里会变成什么样。**」
> ② **问「通用」这个词的含金量**：「你说的是『通用的创作能力』——**这个通用是指同一套 agent 服务多种内容形态（图 / 文 / 视频），还是指同一套底座给不同的业务方去搭各自的创作 agent？** 这两种做法的难点完全不一样，前者难在多模态的一致性，后者难在接口怎么抽。」
> ③ **把 C 端这个差异挑明**：「面向 C 端创作者的话，**我猜延迟和成本的约束会比我做过的内部工具严一个量级**——内部工具我可以让用户等几分钟，C 端不行。**你们现在是怎么在『多探索几轮质量更好』和『用户等不了』之间取舍的？**」

> 💡 **第 ① 问是最该问的**：它把「我没做过创作」这个明显的短板，转成了「我带着一套评测方法论来看这个新场景」。**面试官已经看到这个差异了，你主动说出来是加分，装作没看见是减分。**

**题型 A｜扣分：🔴 ① 落点（只问一个）+ ② 诊断（四个钩子一个没接，第三次复发）**

### 对应动作（三条，按性价比排）

1. **🔴 编码题开场加第二句：报解法和复杂度，然后停下来等确认。** 上一场的教训是「先复述需求」，这一场的教训是「**再报方向**」。两句加起来 30 秒，**这场能省下 15 分钟**。

2. **🔴 反问必须准备一个「差异题」模板，专门用在岗位跟自己经验不一致的场合。** 这场、字节二面、阿里星三场都栽在同一个动作上。

   > **只要一句话里出现「效果」「准确」「评测」「提升」「用户」这五个词中的任何一个，下一句必须带数字和分母。**

## 21. 🔴 事后归因：为什么挂了（结果出来后补）

> ⚠️ 下面是从转录里能推出来的结构性归因，**不是面评原文**。挂也可能有 HC、也可能他们只要有内容生成 / 多模态经验的人——这些我无从证实。但下面这条结构是转录本身就能支撑的。

### 核心结论：**答得最好的题区分度最低，区分度最高的题答得最差**

把 19 题按「这题对**这个岗位**有多大区分度」重排一遍，形状立刻变了：

| 区分度 | 题 | 表现 |
|---|---|---|
| **高**（平台岗核心） | §9 企业级 agent 该具备哪些能力 | 🔴 三个形容词（可解释 / 可用 / 稳定），零判据 |
| **高**（创作类的头号难题） | §14 评测飞轮 | 🔴 讲了机器怎么转，**没说它转出来了什么**（零数字） |
| **高**（内容平台一定有素材库） | §11 知识库怎么保证命中 | 🔴 只报了切块 / 拉相邻块 / 多路检索，**自己做过的 query 改写、双路召回、reranker 一条没用** |
| **高**（岗位匹配度） | §19 反问 | 🔴 面试官摊开「C 端创作 AIGC」，零回应 |
| **高**（硬信号） | §18 编码题 | 🔴 19 分钟 + 死循环 + 没对方向 |
| — | — | — |
| **低**（谁读过官方博客都能答） | §5 §6 §7 skill/workflow/tool 边界 | ✅✅ 答得最好 |
| **低**（项目内部机制，只对懂 DeerFlow 的人有意义） | §13 退出逻辑 | ✅✅ 全场最完整 |
| **低**（个人习惯，无法证伪） | §15 §16 §17 AI coding | ✅✅ 很扎实 |

**面试官在 54 分钟里实际拿到的信息是：**
1. 概念清楚 —— **但这不构成录用理由**，所有背过 Anthropic 那篇《Building Effective Agents》的人都能答
2. 做过一个多 agent 系统 —— **但没有任何证据证明它做成了**（零数字，第三场）
3. 代码能力 —— **有明确负面证据**（LC11 走弯路 19 分钟）
4. 对这个岗位的兴趣 —— **有明确负面证据**（反问零钩子）

**2 和 3 和 4 都是「硬信号」，1 是「软信号」。硬信号里有两个负、一个空缺，软信号再满也翻不过来。**

### 三条具体的、可能单独就足够挂的

| # | 位置 | 为什么这条足够致命 |
|---|---|---|
| 1 | §18 编码题 | **LC11 是双指针的入门题**，标准解五行。选单调栈 + 两次推翻 + 一次死循环 + 19 分钟（占全场 35%），**面评上会写成「算法基础一般」，这是最难辩解的一栏**——概念可以再准备，代码能力是当场量出来的 |
| 2 | §9 企业级 agent 能力 | **岗位是「通用创作能力平台」，这题问的就是「你知不知道做平台要什么」**。回答是三个形容词。**这是全场跟岗位最贴的一道题，而它是按「机制」那一项扣分最重的一题** |
| 3 | §19 反问 + §1 自我介绍 | **一头一尾各有一次表态机会，两次都空了。** 开头没把五段实习串成跟创作/评测相关的一条线，结尾面试官把岗位讲得明明白白也没接。**面试官只能自己下结论：这人是海投的** |

### 最该记住的一句

> **概念题答满分，在一面里基本不加分——面试官默认你会背。真正决定结果的是：你的项目有没有可验证的结果、你的代码当场写得怎么样、以及你有没有表现出想来。这三样这场分别是「没报」「不好」「没有」。**

## 如果只能改三件事

1. **编码题：报完方向再动手。** 上一场学会了「先复述需求」，这一场证明还差一句「**我打算走 X 解法，方向可以吗**」。**这两句是同一套开场的两半，缺一半就还是会在第 17 分钟自己发现死循环。**
2. **反问：岗位跟经验不一致时，主动把差异说出来。** 这场面试官把「C 端创作 AIGC」讲得清清楚楚，**而你全部经验是 B 端文本查证——这个差异他一定注意到了。** 你不说，他只能自己下结论；你说了，就变成「他带着评测方法论来看这个新场景」。**同一个动作已经连续三场没做。**
3. **数字：给自己一个触发词表。** 「效果 / 准确 / 评测 / 提升 / 用户」出现任意一个，下一句必须带数字**和分母**。这场两个触发点（§2 说了「提高效率」、§14 整段讲评测）**一次都没触发，而这是第三场了**。
