## 3. 谷歌项目深挖（Memory 方向，连环追问）

### Q：谷歌这边介绍一下？
**当时的回答：** 组里在全面接入谷歌内部类 Claude Code 的 agent 框架，我们组做 testing 方向的插件适配。我负责 memory 方向：现有 memory 是通用的 markdown 文档（记用户偏好、成功经验），不适配测试开发场景，目标是让它能沉淀 testing 业务背景的记忆。

### Q：memory 现在是怎么生成的？
**当时的回答：** 两条生成路径：①对话主题结束时 AI 自动 spawn 一个 subagent 总结对话生成 memory，与已有记录做相似度匹配，决定删除/合并/新增；②「dream」功能：每天凌晨 4 点定时任务把全天对话 summary 成记忆片段，同样匹配后决定合并/增删。记的内容：用户偏好 + 成功/失败经验。

### Q：主题结束是怎么判断的？
**当时的回答：** 内部 agent 自己判断的，不是我们做的，具体没研究过。⚠️ **答崩点**

**改进后的回答：** 即使模块不是自己写的也要能给通用机制：常见三类信号——显式结束（用户关会话/明确说完了）、空闲超时、上下文切换检测（新 query 与当前主题 embedding 距离过大）。再补一句「内部实现我入职两周还没读到那段源码，读完可以细聊」——诚实但不空手。

### Q：为什么要用 subagent？
**当时的回答：** 它是后台功能，用户无感知，必须另起一个 agent 做；严格说不算主从关系的 subagent，就是一个后台 agent 跑异步任务。✅ 答得可以，还主动纠正了术语。

### Q：新 summary 跟原有 memory 怎么匹配？
**当时的回答：** memory 是 skill 形式（title + description 的固定格式）。匹配 = description 之间做语义相似度检索取 top 5，相当于一次 RAG；取出候选后给模型细读，由模型决定合并/更新/矛盾冲突则删除。

### Q：memory 大概多少条？
**当时的回答：** 条数不限制；单条限制 2000 token 防膨胀。检索时按历史记录 + 用户 query 做语义相似度提取。

### Q：语义相似度用什么存储、怎么实现的？
**当时的回答：** 走内部的一个模型，具体实现没细究，不是我做的模块。⚠️ **答崩点**

**改进后的回答：** 通用答案必须能出口：embedding 模型把 description 向量化 → 向量库（或内存索引）存储 → 余弦相似度 top-k 检索。哪怕内部实现没读，也先给这个骨架再声明「内部封装细节待确认」。**在职项目的周边模块要提前补课，连环追问一定会问到边界外。**

### Q：怎么针对 testing 场景做适配？优化方向是什么？为什么？
**当时的回答：** testing 场景的特殊性：不是纯 code agent，要通过 API 真实操作手机、读真实结果。方向是 self-evolve memory（类似微软 SkillUp 思路）：基于成功/失败轨迹数据让 AI 总结成败原因、沉淀教训进文档；提取时不只按相似度，还按「这条经验历史上帮助解决问题的成功率」打分。目前轨迹数据还没就绪，卡在这一步。✅ 思路完整，诚实交代了进度。

## 4. 实习节奏质疑

**当时的回答：** Arm 是 project 制（外企常见，3 个月交付一个项目）。字节本打算干到 9 月，但谷歌流程长：2-3 月面完进 pool，5 月底才匹配到组；4 月先去了字节，谷歌 offer 到了后权衡去了谷歌（**原话「希望能到谷歌这个比较大的公司去见识一下」**），刚好字节的 agent 项目也收尾了。✅ 事实链完整、不心虚——骨架保留。

**⚠️ 三个问题：**
1. **只答了字面问题，没答隐含问题**。面试官问「是规划好的吗」，真正想问的是「**你在我们这会待多久**」（秋招正式岗必评估的留存风险）。整段都在解释过去为什么短，没一句讲未来为什么会长——他的担心一点没消。

3. **最大的浪费：有主线却讲成了碎片**。三段不是随机跳动，是 **西门子 RAG（检索）→ 字节多 Agent（编排+评测）→ 谷歌 Memory（经验积累）** 的递进。这条线一说出来，「三个月一段」从「待不住」变成「在一条主线上高效攒了三层」。

**改进后的回答（背这个版本）：**

> **正因为这样，我现在找的是能长期做下去的岗位**——实习是在探索方向，方向现在清楚了，接下来想要一个能把这条线做深、做到生产级的地方，而不是再攒一段经历。」

## 5. 字节 DeerFlow 项目深挖（面试官在字节待过，问得很内行）

### Q：DeerFlow 项目再介绍一下？
**当时的回答：** 业务背景：新旧玩法/状态叉乘极复杂，运营/产品/研发都理不清用户状态流转，老板要一个 oncall 机器人。难点：内部文档旧、更新不及时，**只有代码是真相**——agent 必须读懂代码并把上下游所有可能性提取全。核心问题是「以偏概全」：状态 A 明明能到 B 也能到 C，agent 只答 B。解法：决策树显式罗列所有可能性 + 每轮把决策树放 system prompt 尾部强化 + review agent 复查有没有列错列漏。

### Q：字节一个仓库上下游依赖几十上百个仓库，怎么保证不以偏概全？
**当时的回答：** 分叉抽象下来就三类：①枚举值导致的 if-else；②抽象方法多实现导致的形态分岔；③业务语义相同的函数聚在一起的不同选项。针对性做了：**AST 工具**——不用读整个文件，直接把 if-else 判断条件从语法树提取出来给 agent；所有判断条件通过工具调用写进决策树（类似 todo）；每轮 LLM 调用把决策树放 system prompt 最后，告诉模型「你做到哪一步、哪些情况没列全」；总结时按决策树输出。**第二重保险**：review agent 拿着决策树、清空 context（让 attention 集中）重查一遍所有可能性，有错就打回重新生成。解决 90%+ 的问题。✅ 这段答得最好。

### Q：很多配置在平台/DC/实验里，是用户实时标签，怎么保证走到正确逻辑？
**当时的回答：** 那是另一套 agent 的职责——国际商业化的用户标签/config 有权限限制，中国这边拿不全；美国组同事的 agent 有权限，先查库/查 config 拿到用户具体状态，再把拼好的 query 转发调用我们的 agent（我们相当于一个 tool/子 agent），我们只负责从代码找原因。

### Q：他们调你的时候传什么样的 query？上下文怎么保证一直拿得到？
**当时的回答：** 单 query 逻辑：一般是用户 ID + 查到的用户状态/数据 + 问题描述（这个用户为什么被 block 在某状态/出了什么错），我们 agent 看代码回答为什么。具体拼接格式没仔细研究过他们那边的实现。

### Q：决策树的节点、边、分支打分具体怎么做？为什么引入决策树？
**当时的回答：** 打分没有。为什么用树：考虑过表格，但二维表格列不了层级递进关系（A→B→D、A→C→E）。节点由 agent 自己生成：root 是玩法，往下是打钱逻辑，再往下币种/税务等，层层递进。边没有严格定义，参照函数调用关系和状态机流转。✅ 被拆解到三要素也没慌，如实说了没有打分。

### Q：环节里有算法决策的点吗（比如模型决定发哪张券）？
**当时的回答：** 没有。本质是「看代码回答问题」的 agent，我解决的是怎么把代码看全、把可能性答全，不涉及推荐/营销类算法决策。✅ 不硬凑，直接说没有。

### Q：具体举一个回答的问题的例子？
**当时的回答：** 产品问：玩法 A 下，达人提交了视频给商家，商家还能否取消订单？实际有很多分支：视频审核状态（我方审核/商家审核）、该达人与商家的历史交易（成功/失败、谁取消的）……传统 agent 只答到一两种情况。我们试过 Claude、Opus 4.8、GLM 5.1，都会以偏概全 + 偷懒（不读全文件、读片段就下结论，可能是训练偏好）。我们的 agent 必须分类讨论列全所有情况。

### Q：这个 idea 是怎么来的？
**当时的回答：** 两条线：①实验发现 agent 运行步数越长、token 用得越多，准确率越高 → 想办法让它跑得更久更全 → 试过 todo 不行 → 试过 table 不行 → 演化到决策树；②leader 的思路：情况列不全时把问题反抛给用户——「你没把限制条件说全，你到底指哪种情况」——这也要求先把所有情况列全才能反问，殊途同归。✅ 有迭代过程，不是拍脑袋。

### Q：为什么不把数据库也作为信息源？
**当时的回答：** ①权限连不到数据库；②数据库只有最新玩法的数据，代码里有历史玩法的残留逻辑（玩法 C 整合了已淘汰的 AB），开发/产品恰恰常问历史逻辑——只看数据库会漏。状态机流转代码里有，AI 自己会看。**「所有东西理论上都是假的，只有代码是真的」**。✅ 这句表达值得保留。

## 6. 算法题（只记题面+思路复盘，解法去算法仓库）

**题目：** 给数组和 k，问能否划分成 k 个非空子集使各子集和相等（LC698 划分为 k 个相等的子集）。

**我当时的思路轨迹：** 先判 sum % k != 0 剪枝 → 想用背包，发现 k=2 对半分可以、k>2 卡住 → 转贪心双指针（排序后首尾拼 target），自己举反例验证 → **自己发现反例**（子集可以 3 个数一组，双指针只能俩俩拼）→ 「有点尴尬」→ 落到回溯（每个数选/不选进当前桶）+ 与 target 比较，提了剪枝方向。

**复盘：** 方向自纠能力是加分项（面试官全程没提示，反例是我自己找的），但绕了 10 分钟弯路。标准解法应该一步到位：**回溯填桶 + 剪枝**（降序排序先放大数、同值失败跳过、桶和相等剪枝），进阶是**状压 DP** O(n·2ⁿ)。LC698 进算法仓库重点题。
