## RAG 相关

### 1. 多阶段 RAG 用了 BM25 + 向量混合检索，两种检索结果的融合逻辑怎么设计的？这种混合策略具体在哪个环节提升了效果？

**答题骨架**

- **两路互补的机理**：向量检索（dense）匹配语义，但长文档里少数关键词的信号会被其余句子的语义**稀释**；BM25 匹配字面，型号 / 错误码 / 专有名词这类 OOV（out-of-vocabulary，不在 embedding 模型词表里的词）它反而最准，但只能硬匹配、扛不住换一种说法。
- **不能直接合并分数**：两路分数量纲完全不同（BM25 是无上界的 tf-idf 累加，cosine 是 [-1,1]），直接相加等于让 BM25 说了算。
- **融合用 RRF（Reciprocal Rank Fusion，倒数排名融合）**：只看**排名**不看分数，`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60。天然免疫量纲问题，毫秒级。
- **再接 Reranker 精排**：RRF 出 Top 30 → cross-encoder（BGE-M3 / 千问 reranker）重排到 Top 10。RRF 负责"别漏"，reranker 负责"排得准"。
- **提升发生在召回环节，不是生成环节**：加 BM25 主要救的是"用户抄了一个型号来查"这类 query，纯向量召回率能从八十几提到九十五以上；生成质量的提升是召回率提升的下游结果。

### 2. PDF 扫描件、OCR、表格结构化，处理过程中踩过什么坑？

**答题骨架**

- **先判断是不是文本层 PDF**：`pdfplumber` 抽不到字符才走 OCR。直接全量 OCR 会把本来精确的文本层降级成识别结果。
- **OCR 层的坑**：`0/O`、`1/l` 字形混淆（错在正文无所谓，错在型号 / 参数 / 错误码里就是致命的，而这些恰恰是 BM25 那一路最依赖的关键词）；扫描时页面横放 → 要开方向检测（PaddleOCR 的 `use_angle_cls=True`）。
- **表格层的坑**：跨页断裂、合并单元格、**无线框表**（靠空格对齐、没画线，`pdfplumber` 默认的 lines 策略检测不到，只能退化成按 x 坐标聚类分列，极易切错列）。
- **最重要的一条 —— 表格绝不能喂纯文本**：按文字流硬抽会变成 `型号 电压 电流 A 220 5 B 380 8`，行列对应关系彻底消失，模型会自己瞎配对产出「型号 A 电压 380」这种幻觉。**数字全是真的、配对是错的，比胡编还难发现。** 必须转成 Markdown 表或 HTML `<table>` 保结构。
- **图片走 VLM 兜底**：纯图表页面 OCR 出来是一堆坐标数字，要用视觉语言模型生成描述文本再入库。

### 3. 识别准确率大概能到多少？（怎么检测成功没成功）

**答题骨架**

- **不能只报一个总数**，要分层报：文本层直抽 ≈ 100%；印刷体中文 OCR 字准 95-98%；表格结构还原率明显更低（70-85%），扫描件比原生 PDF 再降一档。
- **无标注也能自动检测的三个信号**：OCR 置信度（PaddleOCR 每个 text box 返回 `score`，统计 `score < 0.8` 的框占比）；分词 OOV 率（jieba 分完不在词典里的词占比异常高 = 大概率识别出乱码）；表格行列一致性（每行 cell 数是否等于表头列数）。
- **有标注的评法**：抽样 100 页人工标注做 ground truth，字准 / 字段准 / 表格 cell 准分开算；关键字段（型号、参数、错误码）单独算准确率，因为它们权重远高于正文。
- **端到端才是真指标**：OCR 准确率高不等于 RAG 答得对，最终看检索命中率和答案正确率。
- **兜底**：低置信度页面打标记进人工复核队列，别让脏数据静默入库。

## 多智能体系统

### 4. State 管理和 Checkpoint 机制怎么实现的？多个 agent 同时跑的时候，状态竞争怎么避免？

**答题骨架**

- **State 是一个带 reducer 的 TypedDict**：`Annotated[list, operator.add]` 声明「多个节点都往这个字段写时怎么合并」，不声明 reducer 就是后写覆盖先写。
- **满分点：LangGraph 里根本不存在传统 race condition**。底层是 Pregel / BSP（Bulk Synchronous Parallel，批量同步并行）超步模型：① 执行切成一个个 superstep；② 同一超步内并行的 node 读的都是**超步开始时的不可变快照**；③ 它们的返回值不立即写入，先 buffer 住；④ 本超步全部跑完后框架统一按 reducer 归并，原子产出下一超步的 state。并发 node 之间不共享可变内存，没有「读-改-写」交错，所以**不需要加锁**。
- **Checkpoint 存什么**：当前 state、`next`（下一步该跑哪些 node）、`pending_writes`（已跑完但还没合并的写）。最后这个是「续跑不重复执行」的关键 —— 同一超步里 A 跑完了 B 崩了，恢复时不会重跑 A。
- **thread_id 隔离**：checkpointer 按 `thread_id` 分线程存，多轮对话的状态自动续上，不同会话互不干扰。
- **真正要防的不是内存竞态，而是副作用**：节点里写库 / 发消息不是幂等的话，重试会做两遍。要用业务唯一键 upsert，或者把副作用单独拆成一个节点。

### 5. State 的全局管理是怎么做的？

**答题骨架**

- **单一 state schema 贯穿全图**，节点只返回自己改动的那部分（partial update），框架负责合并 —— 不是每个节点都拿到并原样透传整个字典。
- **子图有自己的 state schema**，父子之间通过重叠的字段名自动映射；不重叠的字段要显式转换。
- **Checkpointer vs Store 的分工**（面试官很可能追这个）：Checkpointer 是**线程内短期**记忆，按 `thread_id` 存执行快照，管的是"这次会话跑到哪了 / 崩了怎么续"；Store 是**跨线程长期**记忆，按 namespace + key 存用户偏好之类，管的是"下次换个会话还记得你"。
- **和「数据库存轨迹」的区别**：自己写表存轨迹是只读的日志，用于排障和审计；Checkpointer 是**可执行的状态**，能从任一 checkpoint 恢复继续跑（time travel），还能改掉某个 checkpoint 的 state 再从那儿分叉。
- **控制 state 体积**：检索到的原文别整篇塞进 state（每个超步都会被序列化存一次），放引用 / doc_id，正文另存。

## MCP 工具封装

### 6. 把 Choice 接口封装成 MCP 工具时，标准化接口怎么设计？有没有遇到过兼容性问题？

**答题骨架**

- **原始接口的问题**：Choice（东方财富金融数据终端）的 `CSD(codes, indicators, start, end, options)` 是位置参数，`options` 还是 `"Period=1,AdjustFlag=1"` 这种逗号分隔配置字符串 —— 模型基本不可能拼对。
- **标准化的动作**：位置参数拆成命名字段；固定选项写成 `enum`（很多模型的 constrained decoding 会保证输出只能落在枚举内）；原接口 60 多个字段用 `fields` 枚举挑子集并给默认值；`outputSchema` 声明返回结构。
- **兼容性问题一 —— JSON Schema 方言**：MCP 用标准 JSON Schema，但各家模型 API 的 function calling 只支持不同子集（`anyOf` / `oneOf` / `$ref` / 递归引用 / 嵌套深度 / `additionalProperties` 处理都不一样）。server 端写了个合法定义，翻译到某个模型格式时被降级或直接报错。
- **兼容性问题二 —— 传输层换代**：早期 HTTP+SSE 是双端点（`GET /sse` 收 + `POST /messages` 发）→ 现在 Streamable HTTP 单端点（`/mcp`，按需升级 SSE）。老 client 只会旧 SSE、新 server 只开 Streamable HTTP 会直接连不上，要么双协议并存要么加兼容层。
- **兼容性问题三 —— 版本协商**：`initialize` 时协商 protocol version，HTTP 下之后每个请求要带 `MCP-Protocol-Version` 头，缺了 server 会假定 `2025-03-26`。

### 7. 现场举一个项目里的例子，说出参入参是怎么定义的。

**答题骨架**

- **入参**：`codes`（array，带交易所后缀，`maxItems` 限流）、`start_date` / `end_date`（写死 `YYYY-MM-DD` 并额外支持 `-7d` 相对表达 —— 模型不知道今天几号，让它自己算日期一定错）、`fields`（enum + 默认值，默认只返收盘价和涨跌幅，全返 60 字段纯烧 token）、`adjust`（enum：none / forward / backward）。
- **出参**：`rows` + `total` + `truncated` + `as_of`。**`total` 和 `truncated` 是必须的** —— 只返前 100 行不告诉模型总共 3800 行，它会拿残缺数据直接下结论。
- **单位必须写进 description**：金额是元还是万元、涨跌幅是 `1.5` 还是 `0.015`。这类错在最终答案里看不出来，只会让数字差一万倍。
- **description 要写「什么时候不用」**：工具多了以后模型的主要错误不是参数填错，而是选错工具（拿行情接口去查财报），负向边界要明确写。
- **错误分两类**：参数非法 / 上游挂了 → `isError: true`，错误信息写成模型能照着改的样子（「600519 缺少交易所后缀，请用 600519.SH」）；「代码合法但当天停牌」是**正常返回**空数组 + 说明，标成 error 会让模型以为工具坏了反复重试。

### 8. 大模型在没有 MCP 之前，调用工具的处理流程是怎样的？（原理对比）

**答题骨架**

- **第 0 代 纯 prompt + 文本解析（ReAct）**：system prompt 里用自然语言描述工具，规定 `Thought / Action / Action Input / Observation` 格式，应用端**正则抓取**再查表调函数，结果作为 Observation 拼回 prompt 再问一轮。极脆：JSON 写成单引号、多个换行就解析失败。
- **必须设 `stop=["Observation:"]`**，否则模型会**自己把工具结果编出来**然后基于幻觉继续推理 —— 当年最典型的翻车方式。
- **第 1 代 Function Calling（2023-06 OpenAI 首发）**：工具定义从 prompt 文本变成 API 的独立参数（JSON Schema 描述），调用意图从正文变成独立的 `tool_calls` 字段，不用解析了，而且服务端能做 constrained decoding 保证参数合法。但工具定义和实现**仍然硬编码在应用进程里**。
- **MCP 改了什么 —— 模型侧一个字节都没改**：拿到的工具定义还是要翻译成 function calling 格式塞给模型、模型还是返回 tool_call、还是由 host 执行。它改的是**工具从哪来（硬编码 → 运行时 `tools/list` 发现）、在哪跑（进程内函数 → 独立进程 / 远程服务）**。本质是把 N 个应用 × M 个工具的重复集成变成 N+M。
- **加分点**：MCP 还有 Resources（应用/用户控制的只读上下文）和 Prompts（用户显式触发的模板）这两类 function calling 里**根本没有对应物**的原语，控制权不归模型。

### 9. MCP 有什么缺点或者挑战？

**答题骨架**

- **上下文膨胀（最实际）**：`tools/list` 要全量塞进 prompt，几个 server 就是几十个工具定义、几万 token 且每轮重发；工具超过二三十个后模型选错率明显上升。缓解：prompt caching 解决重复计费但不解决准确率；按场景分组挂载；业界更激进的是 **code execution** 模式（工具暴露成代码 API 让模型按需读定义）。
- **安全（结构性问题）**：① 工具返回内容直接进 context，模型分不清数据和指令 → 一个被污染的 issue 正文就是 prompt injection 入口；② **tool description 本身就是一段 server 完全控制的 prompt，而且不签名**，server 可以在你信任之后偷偷改（rug pull）；③ **组合风险** —— 权限按 server 授予，但一个读文件的 server + 一个发请求的 server 就是完整外泄链路，单看每个都无害；④ 本地 server 等于在你机器上跑陌生人代码。
- **协议迭代快**：`2024-11-05` → `2025-03-26` → `2025-06-18` → `2025-11-25`，中间换过一次传输层，新老 client/server 直接连不上。
- **长任务和分页无标准**：结果是一次性的 `CallToolResult`；分页各 server 自己发明 cursor / offset / limit，模型得现学每个 server 的分页方式。
- **调试难**：**stdio 下 server 往 stdout 打一行日志就把协议弄坏了**（只能写 stderr）；跨进程链路长，出错难定位是模型选错、参数翻译错、server 内部错还是上游挂了。

**拓展双链**：[[Agent问题答案/MCP与协议#Q46]]、[[Agent设计模式与MCP]]

### 10. MCP 返回的结果支不支持流式？

**答题骨架**

- **陷阱题。分两层答：传输层支持流式，但 `tools/call` 的返回值不支持增量返回。** 只答「支持，协议就是支持的」会掉坑。
- **传输层**：Streamable HTTP 下 server 可以把这次 POST 的响应体开成 SSE 流，中途推 `notifications/progress` 和日志通知。
- **但 `CallToolResult` 是一条完整的 JSON-RPC response**，schema 里没有任何「部分结果 / chunk」字段，不能像 LLM 逐 token 那样把工具结果一段段吐出来。流里推的 progress 是**独立的通知消息**，跟 result 不是一个东西，`message` 字段规范里定义的就是 human readable 进度描述，是给 UI 看的，默认不进模型 context。
- **这是刻意的取舍**：工具结果要回灌给模型推理，模型需要完整自洽的一块数据，半截结果反而诱发幻觉；LLM 流式输出是因为消费者是人，人能边读边理解。
- **长任务**：`2025-11-25` 加了 `tasks` 原语，工具上用 `execution.taskSupport`（forbidden / optional / required）声明，server 先返句柄、进度继续用原 `progressToken` 推到终态为止 —— 但最终结果依然一次性。真要流式内容就绕：返回 `resource_link` 让客户端自己订阅，或返回 job id 让客户端轮询。

## 项目工程细节

### 11. 多 agent 项目是主子 agent 那种架构吗？

**答题骨架**

- 这题不考对错，考**能不能准确描述自己系统的拓扑并说出为什么选它**。答「不是」而说不出是什么，比答「是」还差。
- **形态分类**：Supervisor（主子，中心节点用 LLM 决策下一个调谁，星形拓扑）/ Sequential（固定顺序链）/ 条件图 workflow（代码里的条件边判断）/ Network（去中心化 handoff）/ Hierarchical（多层 supervisor）。在 LangGraph 里这些都只是图的不同拓扑。
- **面试官真正在鉴别的分界线**：**下一步由 LLM 决定还是由代码决定** —— 前者才是 Agent，后者是 Workflow。绝大多数人嘴里的「多 agent」其实是 workflow，**这不丢人反而是对的**（Anthropic《Building Effective Agents》的共识：能用 workflow 就别上 agent）。
- **说清主子结构的代价**：LLM 调用次数翻倍（每个 worker 干完都要回 supervisor 再推理一次）；supervisor 的 context 单调增长；延迟叠加；单点误判整条链跑歪；同输入跑出不同路径，测试和排障都难。
- **好收尾**：「编排层是确定的图，但节点内部是 agentic 的 —— 某个节点里模型会自己选调哪个工具、要不要再检索一轮」。既说清架构又证明不是只会搭 pipeline。

### 12. 其中一个功能的一次会话，token 大概有多少？有没有超限？

**答题骨架**

- **必须给具体数字**，答不出量级等于没做过。拆开报：system prompt + 工具定义、单轮检索上下文、历史消息、输出预算，各占多少。
- 超限的处理：历史消息滑窗 / 摘要压缩、检索结果控制条数和单条长度、工具定义按场景分组挂载。
- prompt caching 把 system prompt 和工具定义缓存住，降重复计费。
- 留 ≥10% 给输出，避免 `stop_reason=length` 截断。

### 14. 子任务如果失败了，比如数据抓回来是空的，工作流怎么重试或降级？

**答题骨架**

- **满分点：「抓回来是空的」不是异常，`RetryPolicy` 根本不会触发。** 接口 200 返回空数组是一次**成功的调用**。上来就答「配个 RetryPolicy」就掉坑。
- **硬失败（抛异常）**：LangGraph 节点级 `RetryPolicy(max_attempts, initial_interval, backoff_factor, jitter, retry_on)`。`retry_on` 一定要收窄到超时和 5xx，默认全量重试会把 4xx 参数错误也白重试三次。而且**重试是重跑整个节点函数不是断点续跑**，节点里有写操作必须幂等。
- **软失败（空结果）**：节点里自己判断，把 `fetch_status` 和 `attempt` 写进 state，靠条件边路由到「放宽查询重试」或「降级」。**`attempt` 计数器必须在 state 里**，否则回环会一直转（`recursion_limit` 只是保险丝）。
- **降级是个阶梯**：① 放宽查询（扩时间窗 / 去次要过滤 / 精确改模糊）→ ② 换数据源（备用源 / 缓存 / 历史快照）→ ③ 降精度（日频拿不到拿周频、个股拿不到拿行业均值）→ ④ 部分成功（`Send` 分发的并行子任务用 reducer 分别收集 results 和 failures，按成功率决定继续还是降级）→ ⑤ **显式告知模型**。
- **第 ⑤ 条最容易漏也最重要**：给模型空数组它会当没这回事然后编；给它「该标的自某日起停牌」这种明确缺失说明，它才会在回答里如实标注。**空数组诱发幻觉，明确的缺失说明抑制幻觉。**

### 15. 流式输出：后端是 FastAPI + SSE，但在 LangGraph 这种基于图的状态机里，怎么捕获每个节点的执行结果并实时推前端？

**答题骨架**

- **矛盾在哪**：`graph.invoke()` 是阻塞黑盒 —— 内部跑了 5 个节点花了 30 秒，对外只有「进去」和「30 秒后一次性拿到结果」两个时刻，中间态完全不可见。
- **比普通 LLM 流式难的地方**：图里节点性质不同 —— 检索节点要花 3 秒但**一个 token 都没有**；前端需要的信息横跨三层（走到哪个节点 / 节点内部干到哪 / 模型逐字输出），三者在完全不同的位置产生。
- **解法：`invoke` 换 `astream`，同时订阅多个 `stream_mode`** —— `updates`（节点级增量）+ `messages`（LLM token 二元组）+ `custom`（节点内 `get_stream_writer()` 主动写的业务进度）。另外必须开 **`subgraphs=True`**，否则子 agent 内部执行对外全黑，前端只看到父图卡住；靠 `ns` 字段区分事件来自哪一层。
- **五个工程坑**：① 断连检测（`await request.is_disconnected()`，否则用户关页面后还在烧 token）；② LangChain message 对象不能直接 `json.dumps`，且 `updates` 里可能带几万字检索结果不能原样转发；③ 异常不能让 generator 抛出去（HTTP 头已发、状态码改不了），要 catch 住发 `event: error`；④ 心跳（nginx / ALB 默认 60s idle 断连）；⑤ nginx `proxy_buffering off` + `X-Accel-Buffering: no`，否则事件被攒着不发。
- **最隐蔽的一个**：Python < 3.11 的 async 下 `get_stream_writer()` 拿不到（contextvar 传不下去），要改成 `writer: StreamWriter` 参数注入；且调 LLM 时必须手动透传 `config`，否则 `messages` 模式一个 token 都收不到 —— 这是「流式不生效」最常见的原因。

### 16. 选型问题：为什么用 LangGraph 而不是简单的 LangChain？

**答题骨架**

- **先纠正问题前提**：这不是二选一。**LangGraph 本身就是 LangChain 生态的一部分**，`create_agent` 就是构建在 LangGraph 上的，middleware 的钩子也跑在它返回的编译图里。真正的对比是 **LCEL 链式编排 vs LangGraph 图编排**。
- **LCEL 的形状决定能力边界**：`prompt | model | parser` 是有向无环管道，每步只能拿到上一步的输出。做不了：循环（agent 的本质是 while 循环）、分支后再汇合、跨步骤共享状态（只能一路手动透传字典）、中断恢复、自定义并行归并（`RunnableParallel` 只有固定的字典合并）。
- **LangGraph 补上的**：State + reducer、条件边 / `Command` / `Send`、Checkpointer（断点续跑 + 多轮记忆 + time travel）、`interrupt()` 人在环、多粒度流式、BSP 无竞态并发。
- **判据一句话**：需要环、需要跨步骤共享状态、需要中途暂停 → LangGraph；单向数据变换管道 → LCEL 够了。
- **最好的收尾**：**「LCEL 管一步怎么算，LangGraph 管步与步之间怎么走」** —— 节点内部照样用 LCEL，两者不冲突。再补一句反向诚实：流程本来就是固定单向变换的话上图纯属过度设计，调试成本还更高。
