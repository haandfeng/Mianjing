## 0. 本场结论

面试官主要在判断三件事：

1. **技术选型能不能追到约束。** 为什么从 Elasticsearch 换到 Milvus，为什么已有多语言向量模型还需要查询改写，为什么融合检索后还要重排。

**本场答得好的地方：**

- 两段核心项目都能讲出业务问题、改造动作和量化结果，项目相关性高。
- 西门子检索链路讲到了密集检索、稀疏检索、BM25、融合与重排，不停留在「做了一个 RAG」。

**本场最贵的四个问题：**

## 3. 为什么升级向量模型？为什么从 Elasticsearch 换到 Milvus？

### 当时的回答

把 BGE-M3 升级成 Qwen3 Embedding。因为新模型的向量维度更高，Elasticsearch 当时不方便支持，所以迁移到 Milvus；Milvus 也更适合向量搜索。

### 复盘

**技术定义：** 向量数据库是为高维向量的存储、近邻检索和索引管理设计的数据系统。Milvus 是向量数据库；Elasticsearch 是搜索引擎，也支持向量字段和向量检索。

**解决什么问题：** 选型不能只说「维度更高」。需要说明当时使用的 Elasticsearch 版本、索引限制、吞吐量、延迟或混合检索能力，否则面试官无法判断迁移是否必要。

**机制：**

- 当前 Elasticsearch 的 dense_vector 最大维度是 4096，也支持 sparse_vector；因此「Elasticsearch 不支持高维向量」不能脱离当时版本说成通用结论。
- Milvus 原生支持密集向量、稀疏向量、BM25 和混合检索，更容易把几路召回放在同一套向量检索基础设施中。
- 本项目最稳的口径是：**当时使用的 Elasticsearch 版本和现有索引配置不满足新模型维度与混合检索方案，迁移 Milvus 是结合版本限制、检索能力和团队维护成本后的选择。**

**面试怎么说（30 秒）：**

> 「升级 Qwen3 Embedding 后，我们需要重新评估向量维度、混合检索和线上性能。当时项目使用的 Elasticsearch 版本及索引配置不适合直接承接新方案，而 Milvus 能在同一套系统里管理密集向量、稀疏向量和 BM25 检索，所以迁移。这里我会把版本条件说清，不会泛化成 Elasticsearch 永远不支持高维向量。」

**来源：**

- [Elasticsearch dense_vector 官方文档](https://www.elastic.co/guide/en/elasticsearch/reference/current/dense-vector.html)
- [Elasticsearch sparse_vector 官方文档](https://www.elastic.co/guide/en/elasticsearch/reference/current/sparse-vector.html)
- [Milvus 官方概览](https://milvus.io/docs/overview.md)

**置信度：** 官方文档部分高；项目当时的具体 Elasticsearch 版本，录音未给出，待确认。

> 术语校准：向量维度、密集向量、稀疏向量、近邻检索里，哪个术语是你之前没学过的？

## 4. 已经用了多语言向量模型，为什么还要做查询改写或翻译？

### 当时的回答

用户可能用不同语言提问，文档语言也不同。虽然向量模型支持多语言，但查询改写仍能减少语言和表达差异，提高召回效果。

### 复盘

**技术定义：** 查询改写是把用户原始问题转换成更适合检索的查询，同时保持原意不变。

**解决什么问题：** 多语言向量模型能把多种语言映射到同一向量空间，但不保证产品别名、缩写、设备编号和专业术语都能稳定对齐。直接检索可能漏掉正确文档。

**机制：**

- 识别并保留型号、错误码等不可翻译实体。
- 对自然语言部分做术语归一化或生成多个等价查询。
- 原查询和改写查询都参与召回，再由融合与重排决定最终顺序。
- 是否保留该步骤应由消融实验决定：只关闭查询改写，比较召回率和最终正确性。

**面试怎么说（30 秒）：**

> 「多语言能力解决的是跨语言语义对齐，不等于专业术语和设备实体一定对齐。我们的查询里有设备型号、缩写和内部术语，所以改写的目标不是机械翻译，而是保留实体、统一术语并补充等价表达。原查询和改写查询一起召回，最后用评测判断这一步是否真的增益。」

> 术语校准：查询改写、术语归一化、消融实验里，哪个术语是你之前没学过的？

## 5. 为什么已经做了多路检索，还需要 RRF 和 reranker？

### 当时的回答

密集检索、稀疏检索和 BM25 各自召回结果，通过 RRF 融合，再交给 Rank 模型排序。回答中把 RRF 描述成倒排索引，并把公式简化成 1/rank。

### 复盘

**技术定义：**

- RRF（reciprocal rank fusion，倒数排名融合）把多路有序结果合成一个候选列表。
- reranker（重排模型）读取查询与候选文档的配对内容，重新判断语义相关性。

**解决什么问题：** 多路检索的分数尺度不同，不能直接相加；只按名次融合又看不到查询与文档的细粒度匹配。因此先融合扩大候选覆盖，再重排提高前几名的精度。

**机制：**

- 标准 RRF 对文档 d 的分数为：score(d) = Σ 1 / (k + rank_i(d))。
- k 是平滑常数，避免第一名与后续名次差距过大。
- RRF 只使用各路排名，不是倒排索引，也不读取文档正文。
- reranker 对融合后的候选逐条打分，再截取 top N 交给大语言模型。

**面试怎么说（30 秒）：**

> 「三路检索负责扩大候选覆盖，但它们的原始分数不可直接比较，所以先用 RRF 按各路名次做融合。RRF 不看正文，只解决多路结果怎么合并；之后 reranker 同时读取查询和候选文档，做更细的相关性判断，再选 top N 进入生成模型。两者分别解决融合和精排，不是重复步骤。」

> 术语校准：RRF、平滑常数、reranker、top N 里，哪个术语是你之前没学过的？

## 6. 系统指标怎么测？标注来自人工还是模型？

### 当时的回答

系统有 200 多条问答数据，指标包括 Correctness、Relevance 和 Groundedness。用大语言模型做 judge，并与人工标注对齐；回答时把对齐结果说成大约 80% 的准确率或 A/B 测试。

### 复盘

**技术定义：**

- Correctness 是答案与参考答案是否一致。
- Relevance 是答案是否直接回应问题。
- Groundedness 是答案中的事实是否能被检索证据支持。
- LLM judge 是让大语言模型按固定规则给答案评分。
- F1 是 precision（精确率）与 recall（召回率）的调和平均，用来衡量模型评分与人工标签的一致性。

**解决什么问题：** 只用大语言模型评分可能产生稳定偏差；只用人工评分又成本高。需要先用人工样本校准 judge，再让 judge 扩展评测规模。

**机制：**

- 200 多条高质量问答作为基准数据。
- 人工对一部分答案按同一规则标注。
- 大语言模型按固定评分标准判断。
- 用 F1 约 0.8 衡量 judge 与人工标签的一致性。

**面试怎么说（30 秒）：**

> 「我们有 200 多条高质量问答。最终看 Correctness、Relevance 和 Groundedness；为了扩大评测规模，用大语言模型按固定规则做 judge，但先拿人工标注样本校准。judge 与人工标签的 F1 大约 0.8，所以它适合做快速回归，不等于人工验收被完全替代。」

> 术语校准：LLM judge、precision、recall、F1、Groundedness 里，哪个术语是你之前没学过的？

## 7. 如果现在再做一次西门子项目，会怎么改？

### 当时的回答

会把固定 RAG 链路改成 Agent 循环，并引入 LLM Wiki，让模型先看知识目录，再决定读取哪些页面或调用哪些工具。

### 复盘

**技术定义：** Agent 循环是模型重复执行「判断下一步、调用工具、读取结果、继续判断」的运行流程。LLM Wiki 是由大语言模型辅助生成和维护的分层知识页面，作用是让 Agent 先定位知识范围，再读取具体证据。

**解决什么问题：** 固定的一次检索对简单问答成本低，但面对需要跨页面、多轮核验或工具查询的问题，单次召回可能拿不全证据。

**机制：**

- 简单问题仍走固定 RAG，避免额外延迟和调用成本。
- 复杂问题先读 LLM Wiki 目录，形成知识导航。
- 需要事实时再读取原始文档或调用检索工具。
- 每一步记录证据来源，最后仍由原始文档而不是 Wiki 摘要承担事实依据。

**面试怎么说（30 秒）：**

> 「我不会把 RAG 全部替换成 Agent。简单问题继续走固定检索链路；只有跨文档、多步骤问题才进入 Agent 循环。LLM Wiki 负责导航，原始文档负责事实，最终用相同数据集比较正确性、延迟和调用成本，确认复杂度是否值得。」

**当前机制核验：**

- Claude Code 官方将运行过程描述为 gather context、take action、verify work 的循环。
- OpenAI 对 Codex 的公开说明也把循环拆成输入、模型输出、工具调用与下一轮输入。

**来源类型与置信度：**

- [Claude Code Agent Loop 官方文档](https://code.claude.com/docs/en/agent-sdk/agent-loop)：官方文档，高置信度。
- [OpenAI：Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)：官方说明，高置信度。
- 「复杂问题才进入 Agent 循环」是本项目的改进建议，不是录音里已经实现的事实。

> 术语校准：Agent 循环、知识导航、事实依据里，哪个术语是你之前没学过的？

## 9. 「代码是真相」具体是什么意思？为什么不能只读代码？

### 当时的回答

业务文档可能过期，代码反映线上真实行为，所以把代码作为事实来源。但只读代码又不能理解业务概念和设计意图，还需要 PRD、设计文档和 LLM Wiki。

### 复盘

**技术定义：**

- PRD（product requirements document，产品需求文档）描述业务目标、规则和用户流程。
- AST（abstract syntax tree，抽象语法树）是把代码解析成节点和层级关系的数据结构。
- LLM Wiki 是供 Agent 导航的派生知识层，不是最终事实来源。

**解决什么问题：** 文档可能没有同步最新实现；代码能确认程序实际执行的条件与返回值，但代码本身不一定包含业务原因、运营规则和跨系统约定。

**机制：**

- PRD 与设计文档解释业务语义和预期行为。
- 代码、配置和接口定义确认当前实现。
- LLM Wiki 把两类来源组织成导航页面，并保留反向链接。
- 出现冲突时明确标出「设计预期」与「当前实现」，而不是强行选一个覆盖另一个。

**面试怎么说（30 秒）：**

> 「我说代码是真相，指的是确认当前程序行为时以代码和配置为准，不是说代码包含全部业务知识。PRD 解释为什么有这条规则，代码解释线上现在怎么执行；LLM Wiki 负责把两者连接起来。答案里会把设计预期和当前实现分开，并附上来源。」

> 术语校准：PRD、AST、派生知识层里，哪个术语是你之前没学过的？

## 10. 决策树怎么保证分支完整？需要业务知识吗？

### 当时的回答

先让 Agent 从代码里抽取决策树，再按节点逐步回答。这样可以保证所有分支都被覆盖；基础模型本身已经理解「玩法」等概念，所以没有额外注入业务知识。追问后又承认系统使用 LLM Wiki、PRD 和设计文档。

### 复盘

**技术定义：** 决策树门禁是在生成答案前，把问题拆成有条件分支的检查结构；每个节点要求回答或明确标记不适用。

**解决什么问题：** 大语言模型直接总结长链路时容易漏掉条件分支，导致同一个问题在不同用户状态下给出不完整答案。

**机制：**

- 能从代码和配置中枚举的是**已实现分支**。
- 业务语义来自 PRD、设计文档、运营规则和历史问答。
- AST 能帮助定位条件语句和调用关系，但不能证明隐藏在外部系统、人工流程或未文档化规则中的分支完整。
- 门禁提高覆盖率和可检查性，不能保证答案一定正确。
- 生成决策树后，还要用人工整理的 50 多条评分规则和历史问题做回归。

**面试怎么说（30 秒）：**

> 「决策树不是正确性证明。它把代码和配置中可枚举的分支显式化，再结合 PRD、设计文档和历史问答补业务语义；每个节点都要求回答或标记不适用。这样能减少漏分支，但无法发现所有未文档化规则，所以最终仍靠回归集和人工反馈验收。」

> 术语校准：决策树门禁、可枚举分支、回归集里，哪个术语是你之前没学过的？

## 11. 基础模型和领域微调模型有什么区别？它为什么懂「玩法」？

### 当时的回答

基础模型有通用知识，领域微调模型学习过更垂直的数据，因此更懂业务术语。项目使用基础模型，但模型通常理解游戏里的「玩法」；系统没有专门注入业务知识。后续又提到知识来自 Wiki 和文档。

### 改进后的回答

> 「基础模型可能理解『玩法』这个通用词，但不会自然知道公司内部某个玩法的规则、配置和例外。我们的方案没有对模型做领域微调，业务知识是在推理时通过 LLM Wiki、PRD、设计文档、代码和配置注入的。基础模型负责语言理解和推理，检索到的内部资料负责具体事实。是否需要微调，要看错误来自知识缺失、检索失败，还是模型不会执行固定任务；不能因为模型认识术语就说它懂业务。」

## 12. 为什么要做内部模型网关？

### 当时的回答

团队需要接入 Gemini、Anthropic、OpenAI 等不同模型。它们的 API 协议、提示词缓存和思考内容格式不同，因此做统一网关，并接入 Fornax 做链路追踪。

### 复盘

**技术定义：** 模型网关是在业务 Agent 与多个模型服务之间提供统一调用入口的基础设施。它负责把统一请求转换成各厂商协议，并把响应转换回统一格式。

**解决什么问题：**

- Agent 直接适配每个厂商会重复编写鉴权、流式响应、工具调用和错误处理。
- 多轮工具调用如果丢失厂商要求的思考状态，可能报错或降低连续推理质量。
- 没有统一追踪时，无法比较模型成本、延迟和失败位置。

**机制：**

1. 统一消息、工具定义和流式事件。
2. 分别适配 Gemini、Anthropic 和 OpenAI 请求格式。
3. 保留各厂商需要的**不透明推理状态**，不把它误叫成可自由读取和修改的完整思维链。
4. 对提示词缓存按厂商规则设置断点和生存时间。
5. 记录模型、Agent、工具、延迟、令牌和错误信息，接入 Fornax trace。
6. 给业务层返回统一错误类型，但保留原始错误码方便定位。

**当前协议核验：**

- Gemini 的 thought signature 必须在后续工具调用中原样返回；官方软件开发工具包在保留完整响应历史时会自动处理。
- OpenAI 的推理模型使用不透明 reasoning item，可通过 previous_response_id 或回传输出项维持多轮状态。
- Anthropic 的扩展思考块需要随对话历史保留，提示词缓存则按明确的缓存断点工作。

**面试怎么说（30 秒）：**

> 「网关不只是把 URL 换一下。它统一消息、工具调用、流式事件、缓存和追踪，同时保留各厂商要求的不透明推理状态。例如 Gemini 要原样带回 thought signature，OpenAI 要保留 reasoning item，Anthropic 要保留 thinking block。业务 Agent 面向统一接口，协议差异留在适配层。」

**来源类型与置信度：**

- [Gemini thought signatures 官方文档](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures)：官方文档，高置信度。
- [OpenAI reasoning models 官方文档](https://developers.openai.com/api/docs/guides/reasoning)：官方文档，高置信度。
- [Anthropic prompting 与 extended thinking 官方文档](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)：官方文档，高置信度。
- [Anthropic prompt caching 官方文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)：官方文档，高置信度。
- 项目中具体适配到哪个版本，录音没有给出；以上仅用于校正当前公开协议。

> 术语校准：模型网关、流式事件、不透明推理状态、缓存断点、trace 里，哪个术语是你之前没学过的？

## 13. 不同 Agent 会固定使用不同模型吗？

### 当时的回答

会根据模型能力选择。有的模型更适合规划，有的更适合代码；还提到某些模型「比较懒」，需要反复要求才会调用工具。

### 改进后的回答

> 「不会按主观印象固定模型，而是按 Agent 角色建立任务集。例如规划 Agent 看计划覆盖率和工具选择，代码 Agent 看测试通过率，审核 Agent看错误检出率；再比较质量、延迟和成本。某个模型在工具调用上更保守，只是观察到的行为，要用同一套任务和参数复现，不能用『懒』作为技术结论。」

## 14. 自研 Agent 与 Claude Code、Codex 有什么区别？

### 当时的回答

自研系统针对内部业务，有决策树、LLM Wiki 和网关；Claude Code、Codex 是通用编程 Agent。回答中说 Claude Code 和 Codex 都是开源，可以参考它们的实现。

### 复盘

**技术定义：** Agent harness 是承载模型、工具、上下文管理、权限和验证循环的运行框架。产品能力和仓库许可证是两个不同问题。

**解决什么问题：** 如果只说「我们更垂直、它们更通用」，无法证明自研的必要性；如果把能查看仓库误说成核心代码开源，又会暴露事实核验不足。

**机制：**

- 通用编程 Agent 的核心对象是代码仓库、终端、文件与测试。
- 字节答疑 Bot 的核心对象是业务知识、代码事实、决策树门禁和内部权限。
- 可以复用通用 Agent 的工具循环、上下文压缩和验证思想，但领域知识来源、权限、评测标准和输出结构仍需自建。
- 截至 2026-09-16，OpenAI Codex 仓库采用 Apache-2.0；Anthropic 的 Claude Code 仓库公开可见，但许可证写明保留所有权利，不能笼统说两者都开源。

**面试怎么说（30 秒）：**

> 「我会把产品定位与运行框架分开。Claude Code、Codex 面向通用编程任务，擅长读写代码、调用终端和运行测试；我们的系统面向内部业务答疑，需要把 PRD、代码、配置和权限连接起来，再用决策树与评分规则验收。通用 Agent 的工具循环可以借鉴，但领域知识、权限和评测不能直接复用。许可证方面也不笼统说两者都开源：Codex 是 Apache-2.0，Claude Code 当前仓库是公开可见但保留所有权利。」

**来源类型与置信度：**

- [OpenAI Codex GitHub 仓库](https://github.com/openai/codex)：源码与许可证，高置信度。
- [Claude Code LICENSE](https://github.com/anthropics/claude-code/blob/main/LICENSE.md)：官方仓库许可证，高置信度。
- 社区近期对 Agent harness 的逆向研究只能辅助理解运行结构，不作为产品内部机制的确定结论。

> 术语校准：Agent harness、Apache-2.0、许可证里，哪个术语是你之前没学过的？
