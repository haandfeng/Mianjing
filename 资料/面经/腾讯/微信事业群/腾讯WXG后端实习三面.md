**岗位方向：** 微信事业群（WXG）后端实习

## 1. 基础 & 概念

### Q：为什么要引入协程？解决什么问题？
- 高并发下线程太贵：每个线程 MB 级栈 + 内核态切换开销；万级连接开不起万级线程
- 协程用户态调度、KB 级栈、切换纳秒级 → 用同步写法拿到异步性能（替代回调地狱）

### Q：什么场景适合协程？什么不适合？
- 适合：IO 密集（网络服务、爬虫、RPC 网关）——大量等待，切走干别的
- 不适合：CPU 密集——协程不增加并行度，单线程内算力就那么多，还不如多进程/线程绑核

### Q：协程实现原理？Go 的 GMP 模型？
- 本质：保存/恢复执行上下文（栈指针 + 寄存器 + PC），在用户态切
- GMP：G(goroutine) / M(内核线程) / P(调度上下文，本地运行队列)
- P 本地队列 + 全局队列 + work-stealing；G 阻塞系统调用时 M 与 P 解绑，P 换新 M 继续跑
- 抢占：Go 1.14+ 基于信号的异步抢占，防长循环霸占

### Q：LRU Cache 的基础数据结构？
- 哈希表 + 双向链表：O(1) 查找 + O(1) 移到头部/淘汰尾部

### Q：能用数组实现 LRU 吗？优缺点？
- 能：数组 + 时间戳/计数，淘汰时线性扫最旧
- 优点：实现简单、缓存局部性好、小容量下常数小；缺点：淘汰 O(n)，大容量不可用

### Q：设计题：缓存 100 万条 / 存储 10 亿条，低并发业务持续遍历冷数据，把热数据挤出缓存导致存储抖动，怎么改 LRU？
- 本质是**缓存污染**问题，标准解法是给「进入热区」设门槛：
- LRU-K：访问 K 次才进热端，一次性扫描进不了
- 分代/两段 LRU（如 MySQL InnoDB 5/8 分区 + 停留时间窗口；Redis 近似 LRU + 访问频次）
- 2Q / TinyLFU：新 key 先进试用队列，频次够才晋升
- 也可以按业务隔离：扫描型流量走独立小缓存或旁路不进缓存

### Q：Paxos 和 Raft？选主机制？
- Raft 选主：任期号 + 随机选举超时 → 候选人拉票 → 多数派当选；日志最新者才有资格
- Paxos 无专职 leader（Multi-Paxos 才选）、角色对称、更难实现；Raft 用强 leader 简化

### Q：KV 存储（LevelDB 等）了解吗？
- LSM-Tree：写走 WAL + MemTable（跳表），满了刷 SSTable，后台 compaction 分层合并
- 写快读慢（多层查找），用 布隆过滤器 + block cache 补读性能

## 3. 系统设计：扣款系统

> 题面：企业采购 AI 额度，员工每发一条付费消息扣一块钱。下游金融平台 QPS 极低（~50 QPM）且稳定性差。要求：付费体验不能比免费差（不卡不失败）；用了就扣、不用不扣；余额够才能用。考虑高并发余额扣减、超扣、排队 vs 直接失败。

**答题骨架（核心：本地额度层把下游隔离掉）**
- 读写分离额度：把余额从下游「预扣」到自己系统（类似记账层/额度池），用户扣减只打本地，异步批量与金融平台结算对账
- 高并发扣减：Redis Lua 原子「判断余额够 → 扣减 → 记流水」，防超扣；热点企业可分桶扣减（拆 N 份子额度）
- 用了就扣/不用不扣：消息发送成功才落最终扣费流水；失败走补偿回滚（本地消息表 + 对账兜底）
- 下游又慢又不稳：绝不同步依赖——扣费流水进 MQ 排队慢慢同步；下游挂了积压重放，幂等键防重复扣
- 排队 vs 失败：用户侧永不排队（本地扣，毫秒级）；排队只发生在与下游的异步结算侧
- 边界：余额临界时预扣少量 buffer / 允许小额透支由对账修正，明确讲 trade-off
- 相关：[[Redis分布式锁]] · [[消息队列不丢不重]] · [[缓存一致性]]
