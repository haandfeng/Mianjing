## 4. Memory 是怎么构建的，你负责哪一部分？（07:15–11:51）

**现场问题：** 你是怎么构建这个 Memory 的？

**当时的回答（忠实压缩）：**

## 11. Wiki 和 Memory 哪个帮助更大？（18:25–20:45）

**现场问题：** 看下来 Wiki 的帮助大一点，还是 Memory 更大一点？

**当时的回答（忠实压缩）：**

- 「门禁作用最大，Wiki 实测作用没那么大。」现场理由：谷歌把代码放在一个大仓库，Agent 本身能看到代码，也可能通过代码检索找到 Wiki。
- 有标签和部分监督信号也有帮助：「不一定需要 100% 的 label，给到 50% 的 label，可能有百分之二十的 performance 提升。」
- Memory 腐化是最大问题：可能过于泛化，也可能过于写死规则；像 if/else 一样刚好把答案分出来，但错误规则也会降低性能。
- 「如果能够做到回滚，会有更好的提升。」读论文、看消融实验，再结合自己的测试，觉得门禁比较有用。
- 「真实生产场景不知道 Agent 做得好还是坏，要讨论怎么给它有效的 label、有效信号。如果没有有效信号，可能 Memory 做不好。」

## 14. 为什么想到用决策树，怎么演进出来的？（23:28–28:44）

**现场问题：** 怎么想到选择决策树？

**当时的回答（忠实压缩；合并掉线前后重复回答）：**

- 「一开始的 insight 是，model call、tool call 次数越多，回答准确的可能性越高。」希望延长探索过程，让 Agent 意识到遗漏的分类。
- 先试任务清单工具：「只是在强化它已有的认知」，不够帮助最终总结。
- 看轨迹发现，有时已经找到答案，最后总结仍遗漏；一轮回答可能调用「三四十、四五十次工具」，上下文堆在一起，最后生成时会忘。
- 再试表格：「我作为刚进去的实习生，也不清楚那么多讨论点」，先让它列清怎么讨论，方便自己看和调试。
- 之后认为表格是二维信息，不能把复杂分支路径都展开，于是改成树；希望保留探索路径，引导分类讨论，并在最终回答时按分类总结。
- 代码里需要分情况的地方包括枚举值、if/else、switch/case、抽象函数和类的实现。
- 「跑分从零点七几到零点八几，约 0.10 分提高」，测试有效后保留。

## 19. 为什么 Wiki 在谷歌帮助不大，在字节提升明显？（32:18–35:24）

**现场问题：** 上一个场景 Wiki 没起太大作用，为什么这里有比较大的提升？

**当时的回答（忠实压缩）：**

- 「看场景到底需不需要业务知识。」Wiki 存业务信息，并通过规则让大语言模型维护业务文档。
- 谷歌场景已经给出 bug 错误信息、分类标准；描述转测试操作也有逐步提供的 Skill 引导。「给的信息已经足够它做需要的工作。」

## 29. 上下文管理做过什么优化？（43:33–45:32）

**现场问题：** 上下文管理做过什么优化？字节或其他项目都可以。

- 「Google 没有，字节有。」字节 Agent 工具调用很多，通过关键词检索读代码，单次工具结果太长会占满上下文窗口。
